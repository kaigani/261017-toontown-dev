## C44B-R2S-01 - C44B-R1S-07 not closed

Rule: D-78 item 1; lock design I3 and A1/A6. Location: lock.rs:215-247,
474-478, 758-775 (create_protected, arbiter creation, publication validation).
Input: absent project lock; two live contenders A and R, Unix.
Schedule: A's create_new of the arbitration file succeeds; suspend A before
try_lock. After more than TAKEOVER_STALE, R opens that empty file, locks it,
validates its age and unlinks it. Suspend R before its next acquire iteration.
A resumes, successfully locks its now unlinked inode, writes its token and
returns an Arbiter. It creates and protects the project lock and pauses after
publication. R resumes, sees that protected project lock and returns HeldByOther.
A reads back its own project lock but still_ours is false (no arbiter pathname),
returns HeldByOther and closes the publication. Both calls returned; zero owners.
The stale publication is recoverable by a subsequent call, but no contender in
this schedule retries after returning. No process died and no foreign unlink was
needed. Expected: exactly one owner. Deduced: none. Smallest fix: after obtaining
the creation flock, verify the pathname still identifies the opened inode before
using the handle; treat loss as contention and re-decide. Also protect failed
creation cleanup from deleting a file while another prover owns its flock.

## Lock takeover

Schedules walked (local filesystems implementing the stated primitives):

1. Two contenders, stale readable project lock: the arbiter serializes decisions;
   the winner protects its publication, loser sees Held. Windows delete-pending
   delays create_new until the removing handle closes; Unix unlink precedes close.
2. Three contenders, old arbiter: R opens old inode, S reaps and closes it, D
   creates a successor before R locks. Unix R can lock the unlinked inode but its
   metadata comparison refuses unlink of D. Old inode cannot be reused while R's
   open description exists. Windows deletion is tied to the opened file; legacy
   delete-pending prevents D creating until it is gone. File index reuse cannot
   retarget the deletion handle.
3. Four contenders plus live W: D's stale decision resumes after loss of its
   arbiter, R/S have reaped it, W published. D cannot obtain W's project-file
   protection. No removal, even if valid would accept a copied lockId. Unix flock
   blocks D; Windows W's write handle conflicts with D's non-write-sharing open.
4. Release paused before arbiter unlink: reapers cannot lock its inode on Unix or
   open against its write handle on Windows. Drop removes before close. After
   unlink a new arbiter may coexist briefly with the old open description, but
   the old Drop has no subsequent pathname removal.
5. Heartbeat and release paused after token check: valid arbiter plus persistent
   project-file protection prevent a protocol participant replacing that file.
   Heartbeat writes its handle in place; release unlinks before closing. Neither
   can remove a successor through a conforming participant in this schedule.
6. Unix creation pause before flock: finding 01. Empty does not imply young when
   a live creator is suspended. The design's A1 age argument is false.
7. Unix creator attempts flock while reaper holds aged empty file: after 200
   attempts creator's remove_own can unlink the reaper's protected inode. Reaper
   subsequently sees identity mismatch. This violates the claimed protected-file
   removal discipline; include this window in the creation fix.
8. Crash before protection/token: Unix leaves empty file; Windows closes its
   write handle. Crash at ArbiterTaken leaves token, reaped by next contender;
   crash at AbandonedProven/TakeoverProven releases Unix flock (file remains)
   or completes Windows handle deletion. Crash at TakeoverDecided leaves arbiter
   and stale lock; next caller reaps arbiter then stale lock. Crash after project
   create leaves empty publication, after write leaves marked publication; after
   read-back leaves ordinary dead owner. Crash at heartbeat checks/writes leaves
   marked or unreadable dead publication; release checked leaves marked lock,
   release unlink leaves none. Recovery is exclusive, but an empty Unix file less
   than ten seconds old outlasts the acquire retry window (about two seconds).

Unix identity-check/unlink is safe against conforming removers only when the
opened inode is protected and no unprotected creator cleanup is outstanding;
finding 01 invalidates that universal premise. An open inode cannot be recycled;
the problem is using an unlinked inode, not reuse. Windows creation protects
atomically; reapers exclude writers and delete through the opened handle.
Windows valid failure still deletes an unprotected file: safe for live-owner
exclusion, but weaker than the literal decision-identity requirement of D-78.

Unix I1: holds for returned owners in schedules walked; project proof refuses a live owner.
Unix I2: fails for the arbitration-file protection discipline (schedule 7).
Unix I3: fails (schedule 6, finding 01); also bounded calls need a later retry after a fresh empty crash.
Windows I1: holds in schedules walked under local share-mode semantics.
Windows I2: holds for live owners and arbiters in schedules walked.
Windows I3: holds for stale files with no paused arbiter; literal unconditional liveness is bounded by acquire retries.

## Observations (not findings)

These are static deductions, not runtime receipts. A finite acquire cannot promise
unconditional liveness under arbitrary pauses or unfair scheduling. The finding
uses finite pauses and lets both calls finish; it does not require unfairness.
