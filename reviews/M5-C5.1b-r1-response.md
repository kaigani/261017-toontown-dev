## 3. E-44

- **Known limits.** Three M11 C11.1 tickets in the merge note's §6, with the receipt and the diagnosis: the commit
  checks the whole document (the fix checks the touched entries and the cross-entry rules), `anim.key.add` slows with
  the keys present (1.2 s to 10.8 s for 200 pegs), the undo history's memory grows with the square of the keys added
  (20 GB for 2,500 key additions on 200 pegs).
- **What bounds the undo history today: a level limit, no memory bound.** `crates/executor/src/history.rs`
  (`MAX_STEPS = 1000`, the oldest steps discarded first). 01 §6.1: "At least 200 steps; SHOULD be unlimited subject to a
  memory bound, discarding the oldest steps first." The step count is met; the memory bound is missing, and one step can
  be large: a key added to a curve changes the length of its key list, keys carry no `id`, so the model's diff
  (`crates/model/src/change.rs`, `diff_into`) replaces the whole list and the step keeps it before and after. For the
  ruling the orchestrator makes now: my recommendation is a memory bound on the history, measured by each step's patch
  size, that discards the oldest steps first down to the 200-step floor 01 sets (never below it), with the step-count
  limit kept; and, as the M11 ticket, a key-list diff by frame (keys keyed by their frame, so a step holds the key
  added, not the list).
- **The cell move measured.** The first receipt's cell samples moved cells onto the same drawing's occupied cells (with
  Overwrite Drawings off, nothing changed and nothing was committed). The tool now moves a drawing's last two exposed
  cells 10 frames later into empty cells, and every release sample must commit. Release to commit for a cell move:
  **509.6 ms p95, misses** (bound 50 ms; p50 489.7 ms), the same cause as the bar move (505.5 ms) and the row reorder
  (517.7 ms) in the same run (`reviews/evidence/M5-C5.1b-r2/budgets-kernel.json`, release, 30 samples). The handoff's
  budget table keeps "misses".

## 4. E-45

Search rule first: no reviewer test depends on the read before the save; the lock tests that open read-only do so from
a second session. The cause was a race as well as an order: the `onUnsaved: "save"` save is written at the invoking
command's commit, while the open's job thread, started inside the handler, read the file at once, and the project's own
lock, not yet released, could open it read-only. `project.open` and `project.recovery.open` now wait in their job until
the invocation has finished on the document thread (one request serves the whole invocation, commit included).
`project.backup.open` reads a backup synchronously and installs an untitled copy: not affected. Tests
`c51b_open_saves_first.rs`: a document edit, a history position away from the saved one, session state (a free
playback range and the current frame); each reopened document equals the saved file, the project is clean and
writable, the replaced session's recovery data is deleted, none is offered, a new autosave holds the reopened document,
and the next save keeps the change. With the wait removed, all three fail at the reopened-equals-saved check. The whole
reviewer suite: §7. `74406ea5`, `7ea1ec0c`.

## 5. E-46

`c31_r1_selection_budget` asserted an absolute wall-clock figure: the follow-up read had to answer within the
executor's 200 ms budget counted from its enqueue, which includes the cancelled selection's tail. After C31-R1-14 a
later call costs under a millisecond, so the figure is almost all that tail, a scheduling-dependent quantity; the
3-core macOS runner exceeded it once (run 45243854755: `doc.state.get` timed out at 200 ms). It breaks D-45 (under four
times headroom on the slowest runner, shown by the failure itself). Restated as a shape under the ruling: the time
until the worker answers again, measured by reading until a read answers, must be under half of the same selection run
to completion in the same process, under a 5 s ceiling; every phase is printed on failure (the full selection's time,
the cancelled one's answer, the reads that timed out first and the first one's error), which names the cause next
time. On this workstation it passes (35 s, nearly all of it the full selection run to completion in a debug build,
which the shape needs). `2f50d165`.
