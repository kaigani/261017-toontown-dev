## New findings, ranked

### C14-R2-05 — P1: three other handlers publish files outside atomic commit

**Locations:** `crates/executor/src/commands/agent.rs:396` / `:408`, `crates/executor/src/commands/bundle.rs:381`, `crates/executor/src/commands/doc_io.rs:821`.

`agent.token.regenerate`, file-targeted `doc.export.json`, and `doc.asset.export` still write directly in their handlers. The new `Effect::WriteFile` conversion covers activity export only. An atomic batch containing any of these commands and then `unknown.command` fails while its first step's file survives; token regeneration replaces the previous discovery file. This is a persistence effect outside the successful-commit gate, including commands already reachable through MCP. The HTTP endpoint's M4 deferral does not make the implemented token-file write transactional.

**Repro:** create a project; batch `doc.export.json {scope:"project",path:<new absolute file>}`, then an unknown command. Observe `batch.stepFailed` and the new file. The media fixture and token-file replacement variants reproduce independently. **Requirement:** 11 §7.3; standing staged-effects ruling; `cx.rs`'s own `Effect` contract says failed batches apply no effects. **Permanent tests:** all three rollback tests in `crates/executor/tests/c14_r2_effects.rs`; all fail. `effects-contracts-final.log` retains the failures. The direct-write scan also distinguishes the intended post-call audit append and internal content cache copies from these externally published outputs.

### C14-R2-01 — P1: failed activity-file publication is returned and audited as success

**Location:** `crates/executor/src/run.rs:618`, especially `:636–643`.

Staging can succeed while the final rename fails. `apply_effects` removes the temporary file and discards that error; the caller receives `ok {path,entries,omitted}` and the activity record says `ok`, although no exported file exists. The result is a false persistence outcome and an inaccurate audit record. This is distinct from rollback before commit.

**Repro:** use Autonomous policy, create a directory named `directory.jsonl`, and export activity onto it with `onExists:"overwrite"`. The sibling stage is writable, rename onto the directory fails, the directory remains, and the export reports success. **Requirement:** 11 §11 accurate result status; §7 command envelope; ADR-0015 §11 file-effect/result contract. **Permanent test:** `tests/adversarial/c14-r2-mcp.py::test_export_publication_failure_is_not_a_successful_audit_record` (Cargo-wired by `bins/headless/tests/c14_r2.rs`); fails on the CI release binary and local binary. Report publication failure accurately and retain the transaction/effect outcome needed by audit; do not merely suppress the filesystem error.

### C14-R2-02 — P1: replay drops edits committed by a partially failed sequential batch

**Location:** `crates/executor/src/commands/agent.rs:654–662` (`replay_batch`); sequential commits at `crates/executor/src/run.rs:1087`.

The export excludes every activity entry whose outer status is not `ok`. A non-atomic batch can commit its first patch and fail its second step. Export labels that batch `notCompleted` and omits the committed patch. The original document retains the patch; replay through actual script mode into the same initial document does not.

**Repro:** `batch {atomic:false,steps:[<scene metadata patch>,<unknown command>]}`, confirm the metadata exists, then `agent.activity.export {format:"batch"}`. No patch appears in the export. **Requirement:** 11 §11 and §3; SI-051 / ADR-0015 §11: committed edits only, **all in order**. **Permanent tests:** `test_partial_sequential_batch_keeps_its_committed_edits_in_replay` in the round-two Python suite and `crates/mcp/tests/c14_r2_replay.rs::partially_committed_batch_replays_canonically`; both fail. The Rust test loads the exported file through `tt_mcp::script::load`, runs `script::run`, and compares canonical JSON for every document entry.

### C14-R2-03 — P1: a cached requestId retry becomes an additional replay edit

**Locations:** `crates/executor/src/run.rs:892` (cached outcome), `crates/mcp/src/server.rs:944` (logical-call audit), `crates/executor/src/commands/agent.rs:654` (replay selection).

Exactly one audit record per client call is compatible with recording a retry, but replay must distinguish it from a second execution. The cache returns the original successful envelope, and both calls become executable activity entries. Two metadata patches followed by one undo and an idempotent retry export **two** undo operations. Actual replay goes back one operation farther than the original document.

**Repro:** submit `edit.undo` twice with `requestId:"undo-once"`; both responses are equal and the original executes once. Export to batch and count two `edit.undo` steps. **Requirement:** 11 §7.2 requestId, §11 replay; SI-051 committed edits in order. **Permanent tests:** `test_idempotent_retry_is_not_a_second_replay_operation` and `c14_r2_replay.rs::idempotent_retry_replays_canonically`; fail. A non-retry control with ordinary edits, discovery and dry-run calls replays byte-identical canonical entries successfully. Deduplicating equal params would be incorrect: independently requested identical commands may legitimately execute twice.

### C14-R2-04 — P1: cancelling an active elicitation leaves subsequent tools waiting

**Locations:** `crates/mcp/src/server.rs:212–230` (`Shared::ask`), `:518` (cancellation), `:1046` (`elicit`); timeout `:41` is 300 seconds.

The cancellation notification marks the live request, but the elicitation wait checks only session closure and timeout. Cancelling a call already waiting for the client's answer does not release the sole call worker. Inline `ping` answers while a subsequent `get_state` cannot finish within five seconds. Code inspection establishes that without an answer/closure it waits for the 300-second timeout; the test deliberately does not wait five minutes. This does not ask cancellation to interrupt document-thread work.

**Repro:** negotiate elicitation, request a confirmed overwrite, wait for `elicitation/create`, send `notifications/cancelled` for the tool request, then queue `get_state`. **Requirement:** 11 §4 cancellation, §14.7; ADR-0015 decision 6: cancellation drops a waiting request, with no response. **Permanent test:** `test_cancel_live_elicitation_releases_the_call_worker`; fails with a successful intervening ping and unchanged target bytes. EOF during elicitation still shuts down promptly and passes the original test.

### C14-R2-07 — P1: close-with-save bypasses the agent external-change confirmation path

**Locations:** `crates/executor/src/persistence.rs:379`, `:579`; `crates/executor/src/commands/project.rs:556`.

`project.save` and Save As over the current location call `guard_external_change`. `project.close {onUnsaved:"save"}` instead reaches `save_now` and `check_saveable(..., false)`, which emits the user's `project.changedOnDisk` error even for an agent. No bound `externalChange` token is offered, so the documented agent choice cannot complete through that operation. External content is preserved; this is a confirmation-contract divergence, not an observed overwrite.

**Repro:** dirty a package or folder, change on-disk bytes keeping size and mtime, then close with save as an agent. Expect `needs_confirmation`; observe `error/project.changedOnDisk`. **Requirement:** binding SI-047 ruling, ADR-0014 §12, SI-045 and 10 §8.5 RO-02; this is an explicitly named save boundary that M2 workflows would depend on. **Permanent test:** `test_close_with_save_offers_external_change_confirmation` in the Python suite; both forms fail. Ordinary user quit-with-save refuses the changed file correctly, and agent Save As over the current path correctly returns `externalChange` (new Rust variants pass).

### C14-R2-06 — P2 ticket: the measurement analyzer accepts malformed observations

**Location:** `scripts/analyse-measurements.py:55–69`.

The analyzer recomputes quantiles correctly for the retained valid files, but its documented validation is incomplete. It accepts descending `tMs`, infinite `tMs`, and an empty `series` object. `last_t` is assigned but never compared; finite numbers and a nonempty series collection are not required. Thus CI can accept malformed evidence while reporting zero rejections. This is an evidence-validation robustness issue; no retained measurement is claimed to be fabricated or numerically wrong.

**Requirement:** standing evidence-hygiene ruling and C14-R1-07 fix's explicit malformed-input obligation. **Permanent test:** `MeasurementValidation.test_analyzer_rejects_backwards_time_nonfinite_and_empty_series` in `tests/adversarial/c14-r2-mcp.py`; all three subcases fail, also through the Python suite runner without a real binary. **Ticket owner:** builder, C1.4 evidence tooling, before treating this gate as a malformed-log validator. Validate finite numeric observations, monotonic time, collection shape and a nonempty set of series. No GitHub issue was created.
