## A2 ? Mapping: changes required

### C42A-R1-01 ? P2 ? Published matrices lose precision under accepted pan

Clause: `reviews/M4-design-views.md` ?5 V1 (published matrices and conversions give the same points; inverse identity within float rounding); `spec/02_drawing.md` ?2.2 lines 102?105 (queryable affine mapping).

Reproduction / permanent reproduction: `mapping::independently_derived_mapping_grid`, `crates/executor/tests/c42a_r1_review.rs`. Fails at c745a55: inverse published matrix returns 1000000.000075668 instead of 1000000. Accepted states cover zoom .0625/1/64, rotation 0/90/37.5, centre 0 and (1e6,-1e6), viewport 1920?1080 and 811?423. Absolute comparison tolerance is 1e-5 pixels forward and 1e-5 du inverse. Expected points are independently derived: subtract centre, invert y, rotate clockwise, scale, translate by half viewport. This tolerance is deliberately much looser than direct f64 transform rounding at these coordinates.

Required versus observed: published mapping must agree with the conversion function and round-trip; subtraction of transformed basis points introduces translation-dependent coefficient errors. An agent using the published matrices obtains different drawing coordinates from `view.coordinates.convert`, exceeding the 1e-6 du gesture equivalence scale of 02 ?13.3. Fix direction: construct linear coefficients analytically and derive translation separately; do the same for inverse coefficients. Keep test body unchanged.

`mapping::rotated_colour_pick_and_hit_test_agree_with_independent_point` passes: rotated, zoomed and panned view pick equals drawing-space pick and the independently positioned view point hits content. Supplementary builder evidence `c42/views.rs::m3_item3_refusals_become_implementations_and_agree_with_the_mapping` covers activeView/draft/exclude and raster equality; independently locating a known rendered pixel is added with screenshot review.


## A3 ? Screenshot: changes required

### C42A-R1-02 ? P2 ? Screenshot blocks the document thread

Clause: the review brief explicitly identifies never blocking the document thread as an eligible engineering rule of `plan/IMPLEMENTATION_PLAN.md` ?3.2; `reviews/M4-C4.2-plan.md` ?6 quantifies document-thread holds as ?20 ms per request. Traceability caveat: the actual text of ?3.2 line 153 says ?Never-block watchdog? rather than spelling out the document-thread hold rule; the numerical hold obligation is in the checkpoint plan and the A3 review requirement.

Reproduction / permanent reproduction: `screenshot::screenshot_does_not_block_user_command` in the round's executor binary, fails at c745a55. A worker submits a full 1920?1080 screenshot; after a 10 ms yielding admission interval the user submits `view.transform.get`. Every worker is joined before assertions. Three latency samples in the final full run: 118.7439, 99.4279, 99.4624 ms. Separate screenshot-only run: 129.054, 148.7373, 129.995 ms. The permanent assertion admits 60 ms (three times the hold budget) and uses the minimum of three samples to avoid failing on one scheduler stall; no sleeps. This measures externally observable queue latency, not a precisely instrumented internal hold. Source confirmation: `commands/inspect.rs` lines 1242?1254 calls rasterisation and PNG encoding synchronously inside the command handler.

Required versus observed: a user query should not wait for the entire capture; it consistently waits about 100?150 ms even on this small fixture. Fix direction: snapshot necessary drawing/view state on the executor, then rasterise/encode off-thread with cancellation and a bounded response continuation. Keep the permanent test body unchanged.

`screenshot::png_determinism_crop_limits_and_known_pixel` passes: PNG decodes using the workspace decoder; dimensions and SHA-256 match; repeated captures have identical bytes; crop rows exactly match the full image; the independently known origin pixel contains drawing content; activeView pixels equal screenshot pixels; pan and subsequent drawing edits each change capture bytes; 2049 px refuses before rendering within a generous 500 ms; non-view targets and zero/negative/non-number region values refuse. Source confirms the final software rasteriser is shared with drawing rendering (S4).
