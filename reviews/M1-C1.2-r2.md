## New findings

### C12-R2-01 — P1 — public revision reconstruction can install an invalid live document

`Document::at_earlier_revision(0, &[])` succeeds on a validated fixture whose objects all have revision 1. Passing that returned `Document` to a fresh executor's guarded `open_document` succeeds: the live document reports revision 0 while its element reports revision 1. The new rewind API checks only the supplied stamps; the load transaction checks permissions and unsaved changes, then trusts the candidate without an integrity gate.

Source: `crates/model/src/document/stamp.rs:45`, `crates/executor/src/run.rs:838`, `crates/executor/src/run.rs:884`. Test: `safe_revision_reconstruction_cannot_install_future_object_revisions` (fresh seed `0xc122_9471`). Requirement: 10 REV-01/02 and the standing full-integrity/live-installation boundary. Reject this invalid reconstruction or reject its installation. This is a new non-repair public composition; the C1.3 deferral of disk repair/unchecked assembly does not make invalid live revisions valid. The dirty-project guard itself passes the new stale-snapshot/staging/rewind composition test, and the private capability remains unforgeable.

### C12-R2-02 — P1 — the generated inventory is still incompletely typed

**597 of the 662 generated entries have unconstrained leaves, prose-only schemas, or unresolved named types**, including job final-result schemas. Examples: `anim.pegOnlyMode.set` accepts an object as `enabled`; `anim.function.key.set` accepts `left: {dt:false,dv:[]}`; `capture.device.get` accepts `null`; `library.tree.get` accepts `nodes:[{bogus:42}]`. Other entire results, including `element.get`, are only `type:object` despite explicit owning-section fields. `xsheet.columnWidth.set` leaves map values unconstrained. These holes propagate into the generated frontend contracts.

The metadata also remains incomplete: `library.item.delete`, `.duplicate` and `.move` omit `library.global`; `library.close` and other generated library entries are enabled without a project contrary to 01 §1.3's limited global-library-save exemption. Generic “see spec … for the full rule” enablement strings do not spell out restrictions such as deleting the last camera. These are current declaration obligations under R1-12, even when the handler belongs to a future milestone.

Source: `scripts/gen-command-declarations.py:425`, `scripts/gen-command-declarations.py:525`, plus each exact declaration/schema pointer in `command-register.json`. Tests: all six negative tests in `c12_r2_registry.rs`; all **809 parameter examples separately validate** in `independently_validate_every_declared_parameter_example`. Requirement: plan §3.2, 11 §2/§6.1/§14.2, spec A and owning sections. A schema-valid example cannot establish that a permissive schema rejects invalid inputs/results.

### C12-R2-03 — P1 — checkpoints do not participate correctly in staged execution

Atomic `checkpoint.create → checkpoint.list` returns an empty list; `create → delete` fails `checkpoint.notFound`. A checkpoint between edits setting `meta.phase` to 460 and then 461 restores **461**, rather than the state at its own step. A checkpoint before an edit predicts result `documentRev:1` in a dry run but returns `2` in the real batch. Sequential dry runs also omit the created checkpoint from the following list while the real run includes it.

Source: `crates/executor/src/commands/checkpoint.rs:48`, `crates/executor/src/commands/checkpoint.rs:113`, `crates/executor/src/run.rs:428`. Tests: `checkpoint_is_visible_to_later_atomic_query`, `checkpoint_create_then_delete_in_atomic_batch_succeeds`, `checkpoint_between_edits_captures_its_staged_content`, `checkpoint_before_edit_predicts_same_result_in_dry_run`, `sequential_dry_run_simulates_checkpoints`. Requirement: 11 §7.2/§7.3 and binding R1-08..11: a checkpoint records staged content with its staged revision. Applying a creation effect only to the final committed document, or skipping it in simulation, does not meet that ruling. Stage the checkpoint state and captured snapshot as part of the transaction.

### C12-R2-04 — P1 — paste IDs are nondeterministic and dry-run predictions differ

Copying a peg and previewing `edit.paste` returns a different `createdIds` value from the immediately following real paste. Two identical fixture/command sequences also create different IDs. The shared `new_id` helper constructs a system clock/entropy generator each time, so preview and actual execution cannot agree.

Source: `crates/executor/src/commands/edit_ops.rs:80`. Tests: `paste_dry_run_predicts_created_ids_exactly`, `identical_document_and_paste_sequence_produce_identical_ids`. Requirement: binding R1-02/03, 11 P7/§14.5 and 10 AG-06. ID allocation for these object edits must obey transactional preview and deterministic replay semantics; these are not geometry-dependent approximate previews.

### C12-R2-05 — P1 — edit operations interpret and corrupt opaque metadata

Deleting an element rewrites an ordinary string in another element's `meta`/`ext` when that string happens to equal the deleted ID. Copy/paste of drawing content rewrites a user-owned metadata object shaped like `{type:"stroke",id:…,rev:…}`. Recursive reference cleanup and recursive ID regeneration descend into arbitrary JSON rather than respecting schema-owned reference and object locations.

Source: `crates/executor/src/commands/edit_ops.rs:509`, `crates/executor/src/commands/edit_ops.rs:654`. Tests: `element_delete_preserves_opaque_metadata_and_extension_strings`, `drawing_copy_preserves_object_shaped_opaque_metadata`. Requirement: 10 §2.2 opaque metadata/extensions and C1.1 preservation guarantees. SI-022 can govern real dangling references; it cannot authorize interpreting unrelated strings or model-shaped values inside opaque data.

### C12-R2-06 — P1 — an in-flight `job.wait` does not reserve its request ID

Start a wait on a held job with request ID `r2-pending`; while it waits, invoke `app.frame.set {frame:37}` with the same session/request ID. Both invocations succeed, and the frame changes. `wait_begin` checks the cache but does not reserve the ID; `wait_finish` later overwrites the competing remembered invocation.

Source: `crates/executor/src/run.rs:906`, `crates/executor/src/run.rs:928`. Test: `pending_job_wait_reserves_request_id_against_other_commands`; its assertion permits either invocation to win scheduling, but requires the other to receive `request.conflict`. Requirement: binding R1-06/22 and 11 §7.2. Completed-call caching, session separation and eviction are fixed; in-flight calls still need the same identity contract.

### C12-R2-07 — P1 — `job.wait` in a sequential batch only polls

A held job is released after 150 ms. A sequential batch calling `job.wait` with `timeoutMs:2000` returns `running` immediately instead of waiting for the successful completion. Only direct `ExecutorHandle::invoke` gets the two-phase wait behavior; batch execution calls the polling handler.

Source: `crates/executor/src/run.rs:673`, `crates/executor/src/commands/job.rs:119`. Test: `sequential_batch_job_wait_honours_wait_timeout_contract`. Requirement: binding R1-04/05/13, 11 §7.3 and §15.2. The invocation route must not change a command's waiting semantics.

### C12-R2-08 — P2 — edit envelopes omit resolved targets

Set the staging selection to a peg, then call `edit.copy` without explicit IDs. The command succeeds with `targets:None`; the seven new edit handlers never set resolved targets. The clipboard kind/count does not identify the objects actually selected.

Source: `crates/executor/src/commands/edit_ops.rs:1348` and shared selection/paste paths. Test: `edit_envelopes_report_explicit_or_selection_targets`. Requirement: 11 P4, §7.2 and §8. **P2 ticket in this report:** owner C1.2 executor; populate resolved context/object/destination targets for all seven handlers and assert both explicit and selection-derived invocations. No GitHub issue was opened.

### C12-R2-09 — P1 — wrong-typed paste destinations silently select another target

After copying a peg, `edit.paste {context:"staging",destination:{sceneId:false}}` succeeds and creates an element in the current scene. The destination decoder treats a present non-string identifier like an omitted field, activating the fallback instead of returning `arg.invalid`.

Source: `crates/executor/src/commands/edit_ops.rs:719`. Test: `malformed_paste_destination_is_rejected_without_fallback`. Requirement: 11 P4/§8 and the common parameter validation contract. Validate nested destination fields before resolving defaults; malformed explicit targets must not cause a document mutation elsewhere.

### C12-R2-10 — P1 — `elementProperties` clipboard content validates names but not values

`edit.clipboard.set` accepts an `elementProperties` item whose `columnWidth` is `"not-an-integer"`. The validator checks whether the property name exists in the model schema, then discards the schema without validating the value. The advertised kind-specific content validation therefore remains incomplete.

Source: `crates/executor/src/commands/edit.rs:738`. Test: `clipboard_element_properties_validates_values_not_only_names`. Requirement: 01 §12.1/§12.4 and R1-17. Validate each property value against its schema before accepting clipboard content.

### C12-R2-11 — P1 — JSON-04 materialisation breaks raw inverse exactness and opaque paths

Adding `/meta/r2` to a real object with omitted metadata succeeds, but applying the returned inverse leaves `meta:{}` rather than restoring the original raw JSON. Also, adding `/meta/custom/ext/literal` when `meta.custom` is an ordinary empty object invents the missing `ext` container. JSON-04 default omission does not apply to an arbitrary nested opaque object merely because a key is named `ext`.

Source: `crates/model/src/change.rs:852`, `crates/model/src/change.rs:890`. Tests: `json04_materialised_parent_is_removed_by_raw_patch_inverse`, `json04_materialisation_does_not_invent_opaque_nested_containers`. Requirement: 10 JSON-04/§2.2/§2.6 and the C1.1 exact-inverse contract. Materialise only schema-owned default members and include their creation in the inverse. **Qualification:** canonical model output still omits empty metadata, and the fresh canonical undo test plus every inherited C1.1 reviewer suite pass; the raw inverse and nested-patch guarantees are what regress.

### C12-R2-12 — P1 — `doc.diff` still omits drawing-content revision invalidation

Changing a stroke now correctly returns its containing drawing's new revision in the command envelope and `doc.changed` event. `doc.diff` for the same revision range omits the drawing, because it uses the own-property diff that excludes revision-only changes. An agent catching up via diff receives a weaker invalidation set than an event subscriber.

Source: `crates/executor/src/commands/doc.rs:1298`, versus `crates/executor/src/cx.rs:773`. Tests: `diff_reports_drawing_content_revision_invalidation`; `c12_r2_scale::hundred_thousand_stroke_change_reports_drawing_in_envelope_event_and_diff` (100,000 strokes, seed `0xc122_9461`, stroke 73,481). Requirement: 10 REV-02/AG-09, 11 P6, binding R1-11. The scale test passes its envelope/event assertions and fails specifically at diff.

### C12-R2-13 — P1 — node clipboard edits lose descendant and hierarchy semantics

Copying `Bob-P` omits its descendant `Bob`; cutting the peg leaves Bob in the scene. Copying a complete forest containing effects and their parameter nodes then pasting it fails `tree.invalid`, because each new element is appended at the root with no children. The builder test asserting that a cut peg's children stay confuses generic node cut with the separately specified node-delete behavior.

Source: `crates/executor/src/commands/edit_ops.rs:387`, element deletion around line 561, and root insertion around line 940. Tests: `copying_a_peg_includes_descendants_per_scene_edit_rules`, `cutting_a_peg_removes_descendants_per_scene_edit_rules`, `copying_complete_scene_forest_preserves_effect_parentage_on_paste`. Requirement: **05 §15 explicitly includes all descendants for cut/copy/paste nodes**, plus 01 §6. Preserve the copied forest and remap its internal relationships. A standalone effect-parameter node was not required to paste illegally at a scene root; the final regression includes its parent.

### C12-R2-14 — P1 — cross-bank cell paste overwrites locked drawing content

Create a second drawing bank by pasting cells as a new element, give the original stroke `meta.keepLocked:987`, and lock its drawing. Pasting the copied cells back into the original column succeeds and removes that metadata. The same-name overwrite path replaces `/nodes` without checking the existing drawing's lock.

Source: `crates/executor/src/commands/edit_ops.rs:1029` (same-name overwrite branch). Test: `cross_bank_cell_paste_cannot_overwrite_a_locked_drawing`. Requirement: 04 §13.16 explicitly requires `drawing.locked` for pasting onto locked drawings. Element locks have different semantics: the separate fresh tests correctly allow exposure edits under 04 §10.4 and explicit key edits under 05 §6.6.
