## C03-R2-02 — legitimate slow runs rejected — **fixed**

- **Page** (`CanvasSpike.tsx`):
  - the log is now **version 2**;
  - every run records `phases: { idle: {start, end}, panZoom: {start, end} }`. `start` is the rAF timestamp the
    phase began on: for pan/zoom that is the frame before the first sample, which the old log dropped. `end` is the
    timestamp on which the declared duration was reached, which is also the last sample;
  - raw frames are unchanged and are still the cadence data.
- **Analyzer:**
  - version 2: each span must exist, last at least its declared duration, and its samples must lie exactly on it.
    The idle samples start on the span's start; the pan/zoom samples start after it. The samples of both phases end
    on the span's end, and idle must end before pan/zoom starts;
  - so a complete 1 Hz run passes (10 frames, a 10 000 ms span) and is reported as a missed target;
  - a truncated run fails in either form: samples cut short against an intact span ("do not cover their phase
    span"), or a span that ends early ("incomplete run");
  - version-1 logs (rounds 0–1, no spans) keep the stored-sample rule, so all committed evidence still validates.
    A version-2 log relabelled as version 1 meets that stricter rule, so the relabelling cannot weaken a check.
- **Tests:**
  - the reviewer's three page tests pass: manual save, 60 Hz interactive, and 1 Hz interactive with "missed" in
    stdout;
  - the round-1 truncated-frames control still fails;
  - added to `analyzer.test.ts`: a 1 Hz positive (fps 1, target missed), truncated samples, an early-ending
    pan/zoom span, an early-ending idle span, missing spans, and a short version-1 log.
- **Fresh evidence:** `reviews/evidence/M0-C0.3/canvas-r2-local-windows-rtx4090-auto.json.gz` (+ `.analysis.md`).
  This is a version-2 automatic run of the release build on this machine (WebGPU + WebGL2 × three scenes, plus pixel
  runs), with phase spans in every run. The analyzer exits 0, all six rows meet 60 fps, and there are no long frames.

## C03-R2-03 — encoder accepts an unpaired coordinate and an unknown style — **fixed now, as ruled**

`renderlist::validate` (used by `encode`) gained three typed `EncodeError` variants:
- `UnpairedCoordinate { len }` for an odd point array;
- `UnknownStyle { path, style }` for a style above 2 (stroke);
- `MissingMove { path }` for a line or cubic with no open contour, i.e. no move since the path start or the last
  close. The decoder throws "line/cubic before move" in that case. The reviewer's tests did not ask for it, but the
  ruling asks for an encoder contract equal to the certified decoder's, and this was the remaining difference.

I compared the two contracts check by check. The decoder's other checks (sections within the buffer, finite and
in-bounds points, finite groups, verb/group/point ranges, known verbs, width) already had encoder equivalents.

**Tests:**
- both reviewer tests pass, as do the other nine in the file;
- unit tests for all three variants are added to `encoder_refuses_invalid_geometry`;
- `tests/adversarial/c03-r2-encoder.rs` is now a `[[test]]` target of `tt-desktop` (`c03_r2_encoder`). It runs
  under `cargo test --workspace` locally and in the Windows/macOS check jobs, instead of only through the reviewer's
  standalone `rustc` command. Its manifest directory (`desktop/src-tauri`) is the one its fixture path expects.
