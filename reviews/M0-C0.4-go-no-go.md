## (a) Tablet input in WebView2 / WKWebView — go-with-conditions; architecture not chosen

**Evidence** (synthetic pen on the GitHub Windows runner):
- matrix 5, CI 39116097955, `reviews/evidence/M0-C0.2/tablet-spike-windows-runner-r2-matrix5.json.gz`, cross-checked
  by the reviewers' `reviews/evidence/M0-C0.2/r2-independent-audit.txt`;
- replicates: matrices 3 and 4 (CI 39115272218, 39115685421);
- `reviews/M0-C0.2-handoff.md`; closure `reviews/M0-C0.2-r4-closure.md` (CI 39118529493).

**Established, synthetic input only** (details in ADR-0009):
- The WebView2 DOM delivers only the `pointerdown` of stationary and pressure-only strokes (1 of 1024 frames). It also
  misses repeated-pixel frames and some early frames after the down.
- Twist arrives modulo 180°.
- A plain same-process window's WM_POINTER receives 1024/1024 frames, and a hidden raw-input sink 1046 HID reports
  per run (not decoded).
- RealTimeStylus on the webview window receives 0.
- The web path delivers exact tilt, 1024 pressure levels and coalesced batches (p50 4 per dispatch).
- `octotablet` 0.1.0 has no macOS backend, so plan §2.3's named fallback cannot be used on macOS. The spike's AppKit
  `NSEvent` monitor replaces it, and has never received input.

**Hypothesis, in the reviewers' words** (`reviews/M0-C0.2-r4-closure.md`):
- "C0.4 E1 stays open: the webview's receiving WM_POINTER boundary is unmeasured."
- "Real Windows hardware remains unmeasured: validate physical pen delivery and decoded HID/native fallback
  viability. Stationary/pressure-only suppression, repeated-pixel losses, early post-down gaps and modulo-180 twist
  remain hardware-test priorities."
- The manual-workflow page tests "are synthetic DOM/native-channel fixtures on Windows, not an AppKit/WKWebView
  runtime measurement."
- "A green execution/analysis result for explicitly failed experiments does not prove successful pen delivery."

**Experiments that settle it:**
- **T-W1:** one real-tablet session on Windows (any Windows Ink or Wacom pen),
  `docs/manual-tests/M0-C0.4-tablet-windows.md`. It uses the same six actions A1–A6 as the Mac test, with Space/K
  markers, and records the web path (W) and the native RealTimeStylus path (H). **E1**, a WebView2 DevTools-protocol input trace, runs alongside it on
  the same hardware. Synthetic auto-matrix output is not physical-pen validation.
- **T-M1:** the user's Mac run, `docs/manual-tests/M0-C0.2-tablet-macos.md`, with the same actions, measuring W and
  the AppKit monitor (A).
- **E-R1 / E-D1:** decoded raw HID (R) and a dedicated input window (D). They let those candidates be scored, and
  are run when the orchestrator orders them; the rule set decides from whatever is measured.

**Decision.** Go-with-conditions:
- the shell is kept;
- a single input-source abstraction is built (ADR-0009);
- the platform path is chosen by the rule set below, which is identical to ADR-0009 "Decision" and checked by
  `desktop/src/test/decisionTables.test.ts`;
- the rule set is total: every log maps to one evidence outcome or one decision. `scripts/analyse-tablet-log.py`
  prints that outcome for every manual log, and `scripts/test_decision_rules.py` checks its constants against the
  text.

<!-- tablet-rules:begin -->
**Actions and episodes.** The procedures number the **actions** a person performs:
- A1 pressure ramp;
- A2 speed;
- A3 tilt;
- A4 barrel rotation (optional);
- A5 hover;
- A6 stationary pressure.

The analyzer numbers **contact episodes**. The page records an action marker when the person presses and releases
Space at the start and end of each action, and K to skip it.
- Markers are taken on the **keyup** of a deliberate press. Auto-repeat keydowns are ignored, a keyup needs its own
  keydown, and two transitions are at least 500 ms apart.
- Every Space/K event is logged with what it did (`keyEvents`).

Every row below names an action, never an episode number.

**Only samples inside an action's span are decision inputs** (C04-R4-01).
- Each path's stream is **clipped to the action's span before it is split into episodes**: web samples by the
  page's performance clock, native packets by host wall time.
- Episode detection, the choice of the largest episode, split handling and every statistic use the clipped stream
  only. Row 6's coalescing comes from A2's own clipped samples.
- The native rate clock is chosen **per action from its clipped packets** (C04-R5-01). It is device time if every
  in-span contact packet has a device timestamp, otherwise host time, and the analyzer prints it per action.
- An episode keeps the capture-wide number of the episode its first in-span sample belongs to; that numbering is
  what the manual tests' mapping tables use.
- Samples outside every span never enter any per-action computation, and the analyzer prints how many there were
  per path.
- Per path, an action is "episode n", "split" (the episode with most samples is measured), "performed, no events"
  (done, but no contact on that path), "omitted" (skipped with K) or "unfinished" (saved mid-action).
- Clicks on Save, the form or the listener button fall outside every action and are ignored.
- The manual tests show the expected mapping for a clean run.

**Step 0: is the log evidence?**

| Condition | Outcome |
|---|---|
| `scripts/analyse-tablet-log.py` exits 2; or `source` is not `manual`; or the log has run or simulation records; or the input is synthetic | **not evidence**: repeat the procedure |
| Malformed action markers, including overlap on either clock, or a raw key log that fails its state machine: every transition must be the keyup of a non-repeat keydown of the same key, at least 500 ms after the previous transition, with the label and time of the matching action record (exit 2, naming the event) | **not evidence**: repeat the procedure |
| The log has no action markers (it predates them) | **not evidence**: repeat the procedure with the current build |
| A row's action is omitted, unfinished or not recorded (A4 omitted is fine when "Pen has barrel rotation" is no) | **insufficient evidence: repeat that action** |
| Row 7 or 8: A2 has a single sample (rate null) | **insufficient evidence: repeat A2** |
| Row 4 or 5 fails and the pen's tilt or rotation support is not stated in "About this run" | **insufficient evidence: state the pen's capability** |
| The pen lacks tilt or barrel rotation by specification ("About this run": no) | that row is **n/a** for every candidate |

Any "insufficient evidence" outcome ends the evaluation with that outcome. Otherwise continue.

**Step 1: classify each row for each measured candidate.** Bands are half-open, `[low, high)`, and apply to the
analyzer's **unrounded** value. Row 6 is n/a for native candidates. "Performed, no events" counts as the fail
column.

| # | Capability | Action | Pass | Partial | Fail |
|---|---|---|---|---|---|
| 1 | Pen identity (`pointer` pen/eraser) | A1–A3 | all three actions | one or two of them | none |
| 2 | Pressure ≥ 256 levels | A1 | [256, ∞) levels | [16, 256) levels | [0, 16) levels |
| 3 | Pressure ≥ 1024 levels | A1 | [1024, ∞) levels | [256, 1024) levels | [0, 256) levels |
| 4 | Tilt (`tilt x / y` extrema) | A3 | min ≤ −30° and max ≥ +30° on both axes | a non-zero range, otherwise | zero range on both axes |
| 5 | Twist (`twist range (nonzero)`) | A4 | range width in (180°, ∞) | non-zero samples, width in (0°, 180°] | no non-zero sample, or width 0 |
| 6 | Coalesced events (web only) | A2 | API available, batching observed in A2's samples | API available, no batching in A2 | API not available |

| 8 | Rate ≥ 200 Hz (`Hz`) | A2 | [200, ∞) Hz | [120, 200) Hz | [0, 120) Hz |
| 9 | Stationary pressure-only updates | A6 | more than one sample and pressure value, [60, ∞) Hz | more than one sample and pressure value, rate below 60 Hz or undefined | one sample (the down only), or a single pressure value |

Pressure levels are the analyzer's implied grid when A1 has ≥ 64 distinct values; otherwise they are the distinct
count. In row 9, one sample is the failure the row tests, not missing evidence.

**Candidates and priority.** Each measured candidate is evaluated against every row on its own.
- **Windows:** **W** (web pointer events) > **R** (raw HID; measurable only after experiment E-R1 decodes it) > **H**
  (RealTimeStylus on the main window, the spike's native listener) > **D** (dedicated input window with direct
  WM_POINTER; measurable only after E-D1).
- **macOS:** **W** > **A** (AppKit monitor).

W comes first because it needs no native code, and R next because raw HID was the only path that saw every
synthetic frame. A T-W1 log measures W and H; a T-M1 log measures W and A. A candidate that is not measured is not
scored, and the decision is final for that evidence. Passing a row on a native path proves only that row: native pen
identity says nothing about native pressure, tilt or rate.

**Step 2: select one candidate** (rulings C04-R3-04 and the final C0.4 ranking ruling).
1. A candidate **without any applicable measured row** (not measured, or every row n/a) is excluded.
2. A candidate at **fail on row 2 (pressure) or row 7 (rate)** is **disqualified**. It is listed with its share but
   never selected.
3. A candidate's **share** is the number of its applicable rows at pass divided by its number of applicable rows, as
   an exact fraction. An n/a row is in neither part, so a native candidate is not penalised for row 6.
4. Among the candidates that are not disqualified, the highest share is selected; equal shares go to the higher
   priority (W > R > H > D, or W > A).
5. **Two sources are never combined.** The other qualified candidates may be offered as the "Tablet input interface"
   choice of spec 02 §6.3.

**Step 3: the decision.**

| Result | Decision |
|---|---|
| No candidate has a valid measurement | **not evidence**: repeat the procedure |
| Every candidate with a valid measurement is disqualified | **no-go on this platform: escalate (plan §6 decision 7)**; the candidate with the highest share is named only as the best available evidence |
| The selected candidate passes every row that is not n/a | **go: that candidate** |
| Otherwise | **go-with-conditions: that candidate**, with each row at partial or fail and its mitigation from the table below |

| # | Mitigation when partial | Mitigation when fail |
|---|---|---|
| 1 | pen recognised by pressure > 0; eraser not distinguished | pen not identified on this path: contacts with pressure > 0 are treated as pen; no eraser |
| 2 | accept the measured resolution of 16 to 255 levels; brush response quantised | disqualifies the candidate (Step 2) |
| 3 | accept >= 256 levels | as row 2 |
| 4 | accept the limited or quantised tilt | tilt unsupported on this platform: tilt-driven brush options off |
| 5 | twist limited to the measured range (e.g. modulo 180) | barrel rotation unsupported on this platform |
| 6 | accept one sample per dispatch | accept one sample per dispatch; a floor change is a user decision (ADR-0005) |
| 7 | interpolated sampling off; the >= 200 Hz target is recorded as below target | disqualifies the candidate (Step 2) |
| 8 | recorded as below the 200 Hz target | recorded as below the 200 Hz target |
| 9 | pressure interpolated between updates | pressure changes without movement are ignored |

- a GPU-resident scene with stable identities and per-frame deltas;

- one authoritative render list.

**Conditions (named experiments):**
- E-C1: host delta stream;
- E-C2: sustained edits and upload stalls;
- E-C3: software path on a GPU-less machine (webview software rendering vs tiled host bitmaps);
- E-C4: the user's Mac.

**Rule set for every canvas log**, including E-C4 (`docs/manual-tests/M0-C0.3-canvas-macos.md`). It is identical to
ADR-0007 "Canvas rule set" and checked by `desktop/src/test/decisionTables.test.ts`. `scripts/analyse-canvas-log.py`
prints its outcome for every accepted log:

<!-- canvas-rules:begin -->
**Scenes.** The rule set uses the three C0.3 scenes, with the same threshold for each:
- **paths100k**: one drawing of 100,000 stroked paths;
- **groups1k**: 1,000 transformed groups, the plan's "1 000-element scenes";
- **brush10k**: 10,000 filled brush outlines.

**Step 0: what each cell is.** Every back end × scene cell of an accepted log (analyzer exit 0) is exactly one of:

| Cell status | When |
|---|---|
| **met** | the run completed and fps ≥ 57 over the 10 s pan/zoom (`meetsTarget: true`) |
| **missed** | the run completed and fps < 57 |
| **insufficient evidence** | the run completed but has no cadence estimate (fewer than two samples: `fps` null) |
| **failed** | the run carries an error after the back end started |
| **unavailable** | the error starts "webgpu unavailable" or "webgl2 unavailable", or the page reports no WebGPU API |
| **not measured** (missing run) | the log has no run for the cell: an incomplete interactive capture, or a forced renderer |

A log the analyzer rejects (exit 2) is **not evidence: repeat the run**. Cells that are not measured are listed as
"not measured: repeat with `--spike canvas --spike-auto`", plus `--spike-renderer webgl2` for WebGL2 cells. Cells with
insufficient evidence are listed as "insufficient evidence: repeat with …". Only measured cells are decided.

**Step 1: back-end selection** (the product rule, M4, and its application to a log).
- A back end is **scorable** when all three of its cells are met or missed. Its score is its worst scene's fps.
- The scorable back end with the higher score is selected; a tie goes to WebGPU.
- A back end without a valid measurement (any cell insufficient, not measured, failed or unavailable) is **never
  selected over** one with a valid measurement.
- In the product, both back ends are measured at first launch and after a GPU, driver or webview version change. A
  failed back end is excluded until the next version change, and the user can override the choice in preferences.

So "WebGPU available but slower" selects WebGL2; it is not a fault.

**Step 2: the outcome.** Apply the first row that matches.

| # | Condition | Outcome |
|---|---|---|
| 1 | Both back ends have a failed or unavailable cell | **no-go** for the webview canvas on that platform until investigated |
| 2 | No back end is scorable | **insufficient evidence: repeat the listed runs**; no decision |
| 3 | Selected back end: groups1k missed | **no-go** for the webview canvas as designed: a native-wgpu integration prototype (plan §2.3 fallback) becomes required M4 work |
| 4 | Selected back end: groups1k met, brush10k missed (paths100k met or missed) | **go-with-condition**: M4 pre-tessellates fills in Rust and adds fill level-of-detail, and E-C2 re-measures brush10k. If it still misses, a native-wgpu integration prototype becomes required M4 work |
| 5 | Selected back end: groups1k and brush10k met, paths100k missed | **go**; M4 adds culling and level-of-detail for drawings of that size before they are supported at 60 fps |
| 6 | Selected back end: all three met | **go** as written |

**Overrides on that outcome:**
- **WebGL2 has a failed or unavailable cell** while WebGPU is scorable: WebGL2 is the mandatory path, so investigate
  (driver, OS, WebKit version) before any conclusion for that platform or floor. The row 3–6 outcome for WebGPU is
  the interim decision for that machine.
- **Any cell is not measured or has insufficient evidence** and a back end was selected: the outcome is
  **provisional**, and the listed runs complete it.

`scripts/analyse-canvas-log.py` implements these steps and prints the decision for every accepted log, so every
canvas log maps to an outcome by the analyzer itself.

## (c) WebGPU availability in WKWebView / the WebGL2 path — go

**Evidence:**
- WebGL2 is measured on its own (`--spike-renderer webgl2`, forced-WebGL2 logs) and meets 60 fps on all three scenes
  on this machine.
- Neither CI runner yields a WebGPU adapter. On the macOS runner (macOS 26.6.2, WebKit 21624.5.1.11.3)
  `navigator.gpu` exists but returns no adapter in the VM.
- The page treats a missing adapter as an explicit, labelled outcome ("webgpu is not available …"), not a crash.
  The analyzer requires that failed runs carry their error.

**Hypothesis:**
- WebGPU on a real Mac at the macOS 12 floor, and on recent macOS, is unmeasured.
- WebGL2 performance on a real Mac is unmeasured (E-C4).

**Decision.** Go. WebGL2 is mandatory from day one and feature-equal to WebGPU (ADR-0007). On each machine the
faster back end is used, by the selection rule in (b). The plan's mitigation is confirmed by measurement on Windows
and by design on macOS.

**Conditional on the macOS run:** decided by the rule set in (b). In summary:
- WebGPU unavailable, failed or slower → WebGL2 is selected, and nothing changes;
- WebGL2 unavailable or failed → investigate before any macOS or floor conclusion (WebGPU is used meanwhile);
- both unavailable → no-go for the macOS webview canvas until investigated;
- no back end with a valid measurement of all three scenes (missing runs, one-sample runs) → insufficient evidence: repeat the listed runs.

No CI run has shown WebGL2 failing.

## (d) CPU rasteriser determinism — go

**Evidence** (ADR-0006):
- **Per-configuration identity:** all 234 entries (39 scenes × 6 configurations) are byte-identical across Windows
  x86-64, macOS arm64 and Linux x86-64, two processes each.
  - CI 39126106552 (golden source), 39126796883, 39129350790 (Windows AVX-512) and 39131376596 (closure: "234
    entries × 6 reports, plus 1,404 PNG byte comparisons").
  - Hashes and goldens: `crates/render/examples/c03_raster/hashes.json`, `.../goldens/`.
- **Compiler variation:** default release and `target-cpu=native` reproduce all 234 entries, per the reviewer
  (`reviews/M0-C0.3-r2.md`).
- **Opacity:** the f32 pipeline keeps opacity on the full corpus; the u8 pipeline does not (alpha 250).

**Established vs hypothesis** (`reviews/M0-C0.3-r4-closure.md`):
- "Scalar and SIMD are not pixel-equivalent; successful per-configuration hashes do not prove universal determinism.
  AVX2, NEON and full-corpus AVX-512 evidence exists; SSE4.2-only hardware remains untested."
- "The 55/38/146 ms at 1080p scalar-f32/SIMD-f32/ttraster figures are area extrapolations, not output-size
  measurements or export budgets."
- "Neither current adapter is spec-complete; extend correctness and determinism goldens before adoption."
- The f32 cost is "approximately −3% to +15%, not a bound."

**Decision.** Go. The final-quality renderer is `vello_cpu`'s f32 pipeline pinned to `Level::fallback()`,
single-threaded, behind our adapter, with `ttraster` kept as an independent reference.
- "Deterministic" means identical bytes across OSes and CPUs for the same application version.
- The pins and the CI golden gate are listed in ADR-0006.
- Scalar's cost (about 55 ms per 1080p frame, extrapolated) is accepted.
- The C03-R1-04 SIMD ticket is resolved by this policy.

**Experiments:**
- R-1: Windows-on-Arm and Intel-Mac runners;
- R-2: an SSE4.2-only CPU or emulator;
- R-3: a multithreaded scalar configuration before any use;
- the M3 C3.3 adapter feature matrix.

No macOS user dependency: macOS arm64 is covered by CI.

## (e) Printing and scanners — go-with-conditions: plan only, no spike was done

**Evidence.** None. **No print or scanner spike was done in M0**, and plan §2.3 did not schedule one. What exists is
the plan's mitigation: "Print = our page layout → PDF → OS print API (`windows` crate GDI/XPS, `objc2`
NSPrintOperation). Scanners/tethered cameras deferred to the end of M10." Decision 5 makes scanners and tethered
cameras a stretch goal.

**Hypothesis.** Everything:
- that the OS print APIs accept our PDF with correct page setup, copies, collation and the three layouts of spec
  09 §7.2;
- that `pdf-writer` output prints identically through both OS paths;
- that scanner acquisition (spec 09 §9.12) is reachable through WIA/TWAIN on Windows and ImageCaptureCore on macOS
  without the device UI, which spec 09 §9.12 requires to be optional.

**Decision.** Go-with-conditions. Nothing measured contradicts the plan, and nothing measured supports it. Print
stays in scope as planned; scanners stay a stretch.

**Experiments:**
- **P-1 (before the M10 C10.2 print work):** print a two-page PDF from our layout through `windows`-crate XPS/GDI and
  `NSPrintOperation`, with copies, collation and print-to-PDF, on both OSes. The macOS half needs the user's Mac.
- **S-1 (end of M10, with C10.3 capture; stretch):** acquire one page through WIA (Windows) and ImageCaptureCore (macOS) without the
  device UI.

## FFmpeg / encoder licensing — go (plan; ADR-0008)

**Decision.** The plan implements decision 3 (ADR-0008):
- **The build.** An LGPL-2.1-or-later FFmpeg sidecar that we build ourselves, never with `--enable-gpl`,
  `--enable-nonfree` or `--enable-version3`. Every component is enabled explicitly from `--disable-everything`.
- **Encoders.** Platform `h264_mf` / `h264_videotoolbox`; AAC through `aac_mf` / `aac_at`, with FFmpeg's native
  `aac` as fallback; PNG-in-MOV and `prores_ks` for alpha.
- **Lossless output** is PNG image sequences and FFV1 (MKV; MOV once verified), checked by decoded-pixel comparison.
  ProRes is labelled "visually lossless".
- **Movie determinism** is three separate properties:
  - raster determinism (ADR-0006);
  - **repeat-encode determinism** (spec 09 §11.1(6) `deterministic: true`), which we must meet: metadata is stripped,
    and a software path is used where a platform encoder varies. If no allowed path can meet it, it is escalated as
    SI-002;
  - cross-platform movie identity, which is not required.
- **Supply chain.** The sidecar is built in CI from a verified source tarball, fetched by SHA-256 at app build time,
  and shipped as a signed Tauri `externalBin` next to the executables. The LGPL text, configure line and source
  offer go in the notices.
- **Milestones** (ruling C04-R1-07):
  - sidecar build, fetch/verify and decoders at **M8 C8.3**, since movie import needs them first;
  - encoders and export at **M10 C10.1**;
  - printing at M10 C10.2.
- **Licence gates.** `cargo deny` and the JS licence gate are unchanged. They check declared licences only, so a
  **native-linkage check** is added: `links` keys and `rustc-link-lib` directives against an allow-list. It is an
  M10 C10.1 obligation, run from M8 C8.3. A sidecar gate compares `-buildconf`, `-L` and the exact component lists
  with the manifest.

No code exists yet.

**Hypothesis.** All of it, until **E-FF0** (M8 C8.3: build, gates, fetch, import decode) and **E-FF1** (M10 C10.1:
encode, lossless pixel comparison, repeat-encode SHA-256 comparison) have run. Two risks are found but not measured:
- Windows N/KN editions lack Media Foundation;
- spec 09 §4.4's "≈ CRF 18 equivalent" has no x264 CRF in the platform encoders (SI-001, open for that question
  only).

**Escalation.** Two policy questions: the decoder posture for imports (needed before M8 C8.3), and Windows N/KN
editions (below).

## M0 diagnostics gating (the C0.1 obligation)

**Done.** `--ipc-bench`, `--spike tablet|canvas`, the spike modules and their 12 host commands are compiled only with
the Cargo feature **`m0-diagnostics`**. The front end mirrors it with the define `__TT_M0_DIAGNOSTICS__`. One overlay
config, `desktop/src-tauri/tauri.diagnostics.conf.json`, switches both halves on together.
- **The default build:**
  - registers `ping` and `app_info` only;
  - refuses the flags with "`--ipc-bench` is an M0 diagnostic and this build has none";
  - ships a bundle without the spike pages or any diagnostic command name, source maps included.
- **Proof:**
  - **Registry:** `desktop/src-tauri/src/lib.rs::tests::default_build_registers_no_diagnostic_commands`. One
    `command_registry!` list generates both the Tauri handler and `COMMANDS`, so they cannot disagree.
  - **Bundle:** `desktop/src/diagnostics/gating.build.test.ts` bundles the real app in both modes. The diagnostics
    mode is the control that shows the scan sees the names.
  - **Executable:** `scripts/check-diagnostics-gating.py` checks a built executable. Locally the default build has
    0/12 names and the diagnostics build 12/12.
  - **Dist boundary:** `boundary/check-dist.mjs` passes for both bundles.
- **CI:**
  - the bundle jobs build and check the default build first (registry scan plus refusal of both flags), keep it in
    `default-build/`, then build the diagnostics variant for the measurements and the manual-test artifacts;
  - the check jobs lint and test the feature build.
- **How to verify:** `reviews/M0-C0.4-handoff.md`.
