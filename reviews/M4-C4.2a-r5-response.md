## 1. The matrix's `elementId` + `frame` cells name an element that is not the current one

- **The strengthening.** `world()` now also creates a second drawing element, `Other`. Each `elementId` + `frame` cell
  first moves the context to `Other` at frame 1 and asserts that it is current. Then it names Bob and Bob's other
  frame. A command that ignored `elementId` (and used the current element with `frame`) addresses `Other`, which has
  no drawing there, so the cell fails.
- **The canonical comparison** leaves out one value: `Other`'s `createdAt`, which the clock stamps each time a world is
  built. Every other byte is compared, `Other`'s entry included, so a stray edit there still fails the cell.
- **The defect it found.** Six cells failed: `draw.point.add`, `draw.point.set` and `draw.segment.move`, in both spaces.
  Each answered `drawing.noTarget`.
  - Their handler resolves the naming correctly (`contour_target`).
  - Their shared precheck (`draw.rs::precheck_contour`) read only a drawing-qualified stroke id and ignored
    `drawingId`, `elementId` and `frame`, so it checked the current drawing.
  - The round-4 matrix missed this because Bob was the current element in those cells.
- **The fix.** The precheck resolves the target as the handler does: a qualified stroke id names its drawing; else
  `drawingId`; else `elementId` + `frame`; else the current drawing.
- **Result.** All 264 cells pass, and the reviewer's `second_element_eight_families_and_refusals` passes.

## 2. The capture waiter test asserts what its name claims

`c42_isolated.rs::a_waiting_capture_honours_its_cancellation_and_budget_and_starts_nothing_afterwards` now counts capture
jobs at two moments:
- when the waiter answers;
- after the holders have returned and every capture job has ended.

The two counts must be equal in both halves:
- **cancellation:** two at the answer and two at the end, so the cancelled waiter started nothing, then or later;
- **budget:** the end count equals the count at the waiter's answer, whichever legitimate outcome it met. It is the
  count before the waiter for `limit.exceeded`, and that count plus one when the waiter took a freed slot before its
  answer.

Twenty local runs: 20 passed, 0 failed. Every budget waiter answered `limit.exceeded`: capture jobs 2 at its answer,
2 at the end, peak running 2.

## 3. The probed wait (new product code; see above)

Run 43632661801 attempt 1 failed only on the known macOS margin `c34_r1_contract::sequential_wait_timeout_retains_job_identity`.
Its rerun (attempt 2) passed that test but failed the reviewer's
`c42a_r2_review::cancelled_capture_jobs_finish_after_request_returns` on macOS: a cancelled capture answered its
**result**.

- **Cause.** A probed wait (`wait_sliced`, shared by `wait: true`, `job.wait`, waited batch steps and the screenshot)
  consulted the caller's cancellation only after a 20 ms wait slice expired without the job ending. A job that ended
  within the first slice was answered as a result, although the caller had cancelled before the wait began. The speed
  of the job, not the order of the events, decided the answer. The small fixture capture is that fast on the macOS
  runner.
- **Fix.** The wait checks the caller's cancellation before each slice. A caller that has cancelled is answered
  `command.timeout` with `reason: "cancelled"` and the `jobId` (the job continues, ADR-0020 decision 8).
- **Regression test.** `c42/screenshot.rs::a_cancelled_capture_answers_the_cancellation_even_when_its_job_ended_first`
  runs a 1 × 1 capture whose probe reports the cancellation only after the job has ended. Without the fix it answers
  the result (it fails); with the fix it passes.
- **Every probed-wait suite passes:** all 17 `c34_*` binaries, `c33_r2_wait`, `c33_r1_contract`, `c41_r1_review`,
  `c42a_r2_review`, `c42_isolated`, and the MCP crate.
