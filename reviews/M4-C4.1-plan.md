Builder: Claude Opus 5.5. Branch `m4-desktop-shell` off `main` at `c49cfbf` (M3 merge). Checkpoint scope (plan §4 row
M4): start screen, project wizard, menus, preferences, keymap editor, themes, workspaces, docking, history panel,

## 1. Where the shell starts from

What exists at `c49cfbf`:
- **Kernel state, already registered and tested.** Window, panel and workspace state (`crates/executor/src/ui.rs`,
  `commands/window.rs`, `commands/workspace.rs`): 21 panels, dock areas, floating geometry, tool palettes, main
  toolbar, corners, full-screen arrangement, four built-in workspaces, persisted to `workspaces.json`. App context
  (`app.*`), edit and history (`edit.*`), the agent hub (`agent.*`), settings files (`preferences`, `recent`,
  `state`, `workspaces`; `tt-persist::settings`).
- **Stubs owned by C4.1.** `window.geometry.get/set`, `window.minimized.set`, `window.raiseAll.run`,
  `workspace.export/import` (hand-written, `command.notImplemented` "M4 C4.1"); every generated `prefs.*` (5),
  `keymap.*` (8), `ui.*` (13) and `view.*` (9) entry (namespace rule of `tt_registry::owner_of`).
- **The desktop host is still the M0 shell.** `tt-desktop` holds an `Engine` facade with no executor; its only product
  commands are `ping` and `app_info`; the native menu is built from `desktop/src/ui-bindings/menu.json` and forwards
  most items as "pending". The front end shows three placeholder panels in dockview and a latency status bar.
- **Attached mode is missing.** Streamable HTTP, several clients per instance, the agent indicator and in-app
  confirmations (`askInApp`) were deferred to M4 (ADR-0015 §10; C1.4 handoff gap 1). The engine restart after a
  non-returning handler is C1.4 gap 3, owner M4.

So C4.1 builds the shell end to end: the host becomes a client of the executor, the front end becomes a renderer of
executor state, and every GUI action becomes a command invocation.

## 2. Architecture and module layout

### 2.1 One rule

The front end never holds authoritative state. Everything a command can read or set — layout, views, preferences,
keymap, theme, start-screen visibility, status-bar texts, modal state, agent sessions, history — lives in the executor
session (attached and headless alike). The front end:
1. renders a mirror of that state, refreshed by engine events;
2. turns every user action into a command invocation (`Origin::User`) through one IPC entry point;
3. reports *sensor facts* the executor cannot observe (§3.3) through a host API that is not a command and cannot change
   the document or any persisted setting.

A GUI path that changes project state, a setting or a layout without a command is a defect. A lint test scans
`desktop/src` for direct calls of anything but the command entry point and the sensor API (§8.2).

## 3. State ownership

### 3.1 Three kinds of state

| Kind | Lives in | Persisted | Undoable | Examples |
|---|---|---|---|---|
| Document | executor document | project package | yes | everything of section 10 |
| Session / view state | executor session (`Session`) | no, except what §11 lists | no | current frame and element, selections, mode, views and their transforms, focused panel, modal state, start-screen visibility, context-help mode, status-bar texts, agent sessions |
| User settings | executor `Env.settings`, written by the executor at its acceptance boundary | per-user settings files | no | preferences, keymap overrides, workspaces (with toolbars and full-screen arrangements), window geometry, recent projects, last-used values, suppressed messages, first-run flags |

Settings writes are deferred effects accepted with the call (ADR-0015 history C23-R3-01), so a dry run, a failed atomic
batch or a cancelled request never writes a settings file.

### 3.2 Native window state (shell effects)

`window.fullScreen.set`, `window.geometry.set`, `window.minimized.set`, `window.raiseAll.run` and floating-panel
geometry change kernel state and stage a **shell effect**. The executor never calls the window system: after
acceptance the effect is published as an event, and the host applies it on its main thread. In headless mode the same
state is a virtual window (default 1280 × 800 on one virtual screen), so the commands behave identically and stay
deterministic. When the user moves or resizes the window or a floating panel, the host invokes `window.geometry.set`
or `window.panel.set {geometry}` as the user (the gesture produces the command); equal values are no-ops, so an echo
cannot loop. Geometry is clamped to the reported screens on restore (01 §5.4 visibility guarantee).

### 3.3 Sensor facts (not commands)

Some facts exist only in the webview or the OS: a modal dialog or a gesture is in progress, a text field has focus, the
pointer's view coordinates and the hovered item's description, each view canvas's size in logical pixels, the screens,
the OS appearance. The host reports them through `Engine::report_shell(report)`, a kernel API like `grant_roots`, not a
registered command (spec A has no such id and the inventory test keeps the registry equal to spec A). A report cannot
change the document, a setting or a layout; it feeds `app.state.get.modal`, `ui.statusBar.get`, `view.list` sizes and
the `ui.busy` arbitration. Agents cannot reach it. Recorded as an SI (§9).

### 3.4 `ui.busy` and agent coexistence

While the reported modal state is a dialog or a gesture, a document-changing agent command that conflicts waits up to
the session's `waitForUserMs` (default 10 s; 0 = fail at once) and then fails with `ui.busy` (`details.blockedBy`);
queries and non-conflicting commands run (01 §12.1 rule 8, 11 §6.4). The wait happens on the caller's side of the
executor (the MCP request thread), never on the document thread, so user commands keep flowing. C4.1 implements the
arbitration and its deterministic tests (scripted sensor reports through the kernel API); E6 (C4.3) proves it end to
end with a scripted drag in the running application.

### 3.5 Request cancellation (ADR-0020 decision 8)

- Every GUI call goes through `run_command`. The front end marks a call cancellable when it can offer Cancel (a waited
  call behind a progress window). The host then keeps an `AtomicBool` per request token and calls
  `invoke_served_until` with a probe that **only loads the flag**; `cancel_request` stores `true`. Calls that cannot
  cancel use the plain entry point (no link, no cost).
- A cancelled request answers `command.timeout` with `details.reason: "cancelled"` (SI-111). The front end shows it as
  "Cancelled", never as a timeout or an error box. A real watchdog timeout is shown as a timeout with the hint.
- Request cancellation never cancels a job. Progress windows of jobs offer `job.cancel` separately and show the job
  until it is terminal.

### 3.6 Engine not responding (C1.4 gap 3)

A handler that never returns cannot be preempted. The host watches a heartbeat (`app.state.get` with a short budget
answered off the user path). After repeated watchdog timeouts it shows "The engine is not responding" with **Wait** and
**Restart engine**. Restart spawns a fresh executor over the same user folders; the stuck thread is abandoned; the
project reopens from its last autosave as recoverable work (01 §3.7), and the window says what was lost. A design note
`reviews/M4-design-engine-restart.md` is committed before the code; the test uses the dev-only never-returning
handler of `c12_never_block` in an executor embedding test, not the product binary.

## 5. Menus: one manifest, live state

- `desktop/src/ui-bindings/menu.json` stays the single source for the native menu and the parity test. Each command
  item is a command reference (`command`, optional fixed `params`), its label, platform filter and
  `enabledWithoutProject`. The `handler`/`pending` fields go: every item is dispatched through `run_command`;
  an item whose command is not implemented yet stays visible, disabled, with its owner in the status-bar
  description (01 §9.1) — never silently missing.
- Items that need parameters the user must give (New Project, Save As, Rename Workspace, Paste Special, Project
  Properties) name a dialog id instead of fixed params (`"dialog": "newProject"`); the dialog collects the
  parameters and runs the command once (01 §0).
- **Live state.** The host recomputes enablement after every `app.state.changed`, `edit.history.changed`,
  `project.dirty.changed`, `workspace.changed` and `keymap.changed`, from the registry's enablement rules evaluated by
  the kernel (`ui` state snapshot carries `enabled: [commandId]` for the manifest's ids), and updates labels ("Undo
  Add Stroke — agent: …"), check marks (panels, status bar, full screen, side panels) and accelerators.
- **Accelerators.** Shown in native notation from the keymap. On macOS menu key equivalents are registered and the
  menu dispatches them (WKWebView offers key equivalents to the menu first). On Windows the menu shows the shortcut
  text and the webview's key handler dispatches through the kernel (§6.3); the pure dispatch-policy function that
  decides which side handles a key is unit-tested per platform, and the macOS behaviour has a manual script.
- **Parity (11 §14.1).** `c12_registry::ui_binding_manifest_parity` (builder) gains the GUI half: every command
  reference in the manifest, toolbar items, keymap defaults and dialogs is registered; every registry entry has a
  manifest binding, a declared GUI location or an `agentOnly` justification. C4.3 closes the gate over views and
  tools.

## 6. Preferences, keymap and themes

### 6.1 Preferences

- The catalogue (01 §7.3 and the `agent.*` keys of 11) is data: `crates/executor/src/prefs.json`, one entry per key
  with type, default, range or values, `applies` (`live` / `nextLaunch` / `restart`), category and description. The
  generated `prefs.*` schemas stay; values are validated per key at run time (`prefs.unknownKey`,
  `prefs.invalidValue`, `prefs.outOfRange`).
- `prefs.set` is atomic: one invalid value changes nothing. Only values that differ from the defaults are stored
  (`preferences.json`, unchanged format). `prefs.changed {keys, source}`.
- Keys other sections own (for example `staging.*`, `drawing.onionSkin.*`) are registered now with their defaults so
  that `prefs.list` is complete; their consumers arrive with their owners.

### 6.2 Keymap model

- **Binding** = (canonical key sequence, context) → command reference (`commandId`, optional `params`), exactly the
  01 §12.4 shape. Contexts `global`, `drawing`, `staging`; a mode-context binding wins over `global` at dispatch.
- **Canonical sequences** (01 §12.1 rule 17): modifiers in the fixed order `Primary+Ctrl+Alt+Shift+<Key>`, key names
  from one table, letters upper-case. On Windows and Linux `Ctrl` is `Primary` and is written `Primary`. Stored keymaps
  are platform-neutral.
- **Defaults** are data (`keymap-default.json`): the platform-standard shortcuts of 01 §8.2 (platform-specific ones
  carry a platform filter) plus single-key defaults for the frequent operations 01 §8.2 lists (frame, drawing and
  element stepping, zoom, view rotation, panel show/hide; tool keys arrive with the tools in C4.2). A test proves them
  conflict-free per context and per platform.
- **Overrides**: `keymap.json` in the settings folder stores only `added` and `removed` bindings relative to the
  defaults (01 §8.1), so new defaults reach users who did not touch them.
- **Rules**: reserved keys per platform (`keymap.reservedKey`), conflicts (`keymap.conflict` with the other binding's
  command and context, or `onConflict: override`), unknown commands (`keymap.unknownCommand`), malformed sequences
  (`keymap.invalidSequence`), every command rebindable, commands unavailable on the platform omitted from the editor.

### 6.3 Dispatch (one path)

The kernel resolves a key sequence to a command (`keymap::resolve(sequence, mode, focus)`): the mode context first,
then `global`; a disabled command consumes the key silently (01 §8.4); shortcuts are suspended while a modal dialog is
reported open; while a text field has focus unmodified keys are not dispatched. Real key presses (front end → host
`dispatch_key`) and the MCP `key` tool use this one function, so the agent's key and the user's key run the same
command with the same parameters.

### 6.4 Shortcut editor

01 §8.3 in full: browse by category with search over label, description and shortcut; details with bindings per
context; Remove; capture control (native notation, Shift + printable accepted, bare modifiers refused, focus loss
ends, Escape cancels); reserved keys refused with the message; conflict dialog with Override / Cancel; Reset and Reset
all (confirmed); Import / Export (native dialogs). Edits are staged and applied on OK with the preferences.

### 6.5 Themes

`light`, `dark` and `system` (follows the OS appearance live) ship; user theme files in `<settings>/Themes/*.json`
(validated: id, name, dark flag, a closed set of colour tokens; invalid files ignored with a logged warning and an
entry in `ui.theme.list`'s diagnostics). A theme is a set of CSS custom properties applied at once, no restart. Canvas
colours stay preferences (01 §5.8). Element and storyline default colours are checked for distinguishability in both
themes (01 §13.10) by a test.

## 7. Workspaces and docking

- The dock adapter renders the kernel `Layout`: `corners: sides` → root row [left, column[top, central, bottom],
  right]; `topBottom` → root column [top, row[left, central, right], bottom]. Dock areas stack their tab groups along
  their long side; `size` on an area's first group is its width or height.
- User gestures become commands: a drop is intercepted before dockview mutates anything and becomes
  `window.panel.move {panelId, area, relativeTo, position}`; the view re-renders from the kernel's answer. Splitter
  drags end in `workspace.layout.set`. Tab bar context menu = panel checklist (`window.panel.set {visible}`).
  Double-click on a tab toggles floating. Dragging inside a view never starts docking (dock gestures start only on tab
  and title bars).
- **Floating panels are separate OS windows** (01 §5.4): the host opens one webview window per visible floating panel
  (`index.html?panel=<id>`), which renders that panel from the same engine events; window moves and resizes become
  `window.panel.set {geometry}`. Floating tool palettes likewise.
- Full screen applies the workspace's full-screen arrangement (kernel) and the native full-screen state (shell
  effect).
- The main toolbar renders `mainToolbar.items`; the Customise Toolbar dialog edits through `window.toolbar.items.set`.

## 8. Test strategy

### 8.2 Front end (Vitest + jsdom, runs in `check`)

### 8.3 The running application on both CI operating systems

New job **`desktop gui`** (Windows and macOS) downloads the default (product) build from `bundle`, so nothing is built
twice, and runs `scripts/c41-gui-e2e.py`:
1. launches the real `toontown` binary with `--user-dir <fresh temp folder> --mcp-http 127.0.0.1:0
   --mcp-discovery <file>` (attached mode; the product build, no test hooks);
2. connects the official Python SDK client over Streamable HTTP (`mcp==2.0.0`) with the token from the discovery
   file;
3. drives the shell through the spec's own tools: `inspect_ui` (panels, menus, status bar, start screen, dialogs
   with fields and the command id each widget invokes), `key` (shortcuts through the kernel dispatch), `run_command`
   (`ui.preferences.open`, `prefs.set`, `keymap.set`, `workspace.select`, `window.panel.move`, `project.create`,
   `edit.undo`, …), `get_state`;
4. checks that the GUI reflects each change (`inspect_ui` after every step), that typed errors surface as message
   boxes with their ids, and that a cancelled GUI-style request is shown as Cancelled;
5. **settings persistence across a real restart:** sets preferences, a keymap override, a user workspace and window
   geometry, quits through `app.quit`, relaunches over the same user folder, and reads them back; corrupts one file
   and checks `prefs.corrupt` is reported once;
6. records receipts under the artifact `desktop-gui-<os>`: the JSON transcript, the UI trees, OS screen captures of
   each step (best effort: `CopyFromScreen` on Windows, `screencapture` on macOS; a capture failure is reported, not
   gated), and a manifest. The handoff copies them into `reviews/evidence/M4-C4.1/` with human-readable names.

What jsdom covers and the real app does not need to repeat: layout arithmetic, form validation, editor state machines.
What only the real app shows: the native menu, native windows, the webview's keyboard path, real persistence, the HTTP
transport.

### 8.4 IPC freshness

`generated/commands.ts`, `wire.ts` and `model.ts` are regenerated and compared in `check` (existing gate, extended to
the new commands). The mirror store's sequence numbers make staleness observable: the e2e script compares
`app.state.get` with the front end's mirror (exposed in the UI tree) after bursts of agent commands.

### 8.5 Manual checks for the user (`reviews/manual/M4/`)

spec): `C4.1-macos-menu-and-shortcuts.md` (application menu, key equivalents, Cmd+, / Cmd+Q / Cmd+W, no double

## 12. Where the pending UI conventions attach (nothing built that blocks them)

| Convention (pending amendment) | Attach point |
|---|---|
| One Properties panel following the active tool, fixed anatomy (preview/size, presets, toggles, operation buttons) | `panels/properties` renders a tool-options descriptor from `tool.options.get` in four named slots (C4.2); no other panel holds tool options. |
| Element properties apply live | Properties edits issue one command per committed edit (no OK); dialog-style apply is used only where 01/02 say so. |
| Tap a tool key to switch, hold to borrow, override in the status bar | The front end sends key **down and up** to the kernel dispatch (not only presses), so a hold rule can be added to `keymap::resolve`; the status bar's description segment is the display slot. |
| Bundled keymap sets | Defaults are a named set (`default`); overrides record their base set; a second set is a second data file. |
| Fit to view, quick close-up, mirror view, middle-button pan, keyboard zoom anchor | View window transform state is kernel state with room for extra internal fields; navigation tools live in one view-navigation module (C4.2). |
| Focused-panel indicator, focus-follows-pointer | Focus is kernel state (`window.panel.set {focus}`); the panel chrome draws it; follow-pointer would be a preference. |
| Add-panel control with dock-target preview, collapsible dock areas, maximise one panel | Dockview header action slots are reserved and empty. |
| Panel menu in every header duplicating the context menu | Same header slot; context menus are data (command references), so one list feeds both. |
| Start screen with user-saved resolution presets | `project.presets.list` kinds; the start-screen form reads presets only through it. |
| Message log panel; undo reveals the changed object | The message store keeps every shown message; history entries keep their change sets from the envelopes. |
| About dialog, shortcut sheet, preferences export/import | About exists (platform standard); the keymap list and the preferences catalogue are queryable data a sheet or an export can read. |
| Drawing conventions (three current colours, paint modes, select modifiers, onion-skin ranges, guides, stabilizer, presets, canvas rotation) | C4.2 plan. |
