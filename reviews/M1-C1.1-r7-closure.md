**Forward patches and exact redo**

The public signature remains `with_patched_entry(&self, key, patch) -> Result<(Document, Vec<PatchOp>), Vec<ModelError>>`. **It returns a document and an undo patch; it does not return a forward patch at all.** The borrowed input is the caller's original patch and is neither mutated nor replaced with a canonical diff. `apply_with_inverse` remains the raw JSON utility; it cannot account for later document canonicalization.

For an input patch `P`, the supported sequence is `(next, U) = pre.with_patched_entry(key, P)`, `(back, R) = next.with_patched_entry(key, U)`, then `(again, _) = back.with_patched_entry(key, R)`. `back` is byte-identical to the canonical pre-state, and `again` is byte-identical to `next`. Replaying `P` through `back.with_patched_entry` also reproduces `next`; the fresh probes assert this separately from the inverse-of-inverse path. Applying `P` only through `change::apply` can yield the uncanonicalized intermediate entry: the merge, append, normalization and nested probes explicitly demonstrate that difference. **Redo through the staged API is exact; the original raw caller patch is not guaranteed to directly produce canonical JSON.** C1.2 should retain the redo returned by undo, or derive and verify a forward patch from actual canonical snapshots. The initial method does not supply a canonical forward patch for a history record automatically. This is an integration requirement for the accepted C1.2 work, not a new C1.1 blocker.
