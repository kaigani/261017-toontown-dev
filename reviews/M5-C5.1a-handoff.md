### 3.2 The transfer-option store (E-19, E-20)

One store per operation (the 01 §7.3 keys), kept **field by field**: the members that were set, as a partial object
under the key. A member never set reads its family's default, two named constants side by side in
`transfer_options.rs`:

| | `EDIT_DEFAULTS` (01 §6.3) | `CELL_DEFAULTS` (04 §11.14) |
|---|---|---|
| Read by | `edit.cutSpecial`, `edit.pasteSpecial`, paste special again (and the dialogs, C5.1b) | `cell.clipboard.set`, `cell.clipboard.apply`, `cell.range.move`, `timeline.transferOptions.get`, the drag-and-drop set |
| Overwrite existing drawings | on | off |
| Update colours | on | off |
| The other ten members | equal | equal |

- One write path, `store_members`: `prefs.set` on the three keys, `timeline.transferOptions.set` and the special
  commands' `remember` (which stores the members given; the dialog will give every member it shows). A stored member
  governs both families. `prefs.reset` stores no member.
- The store applies a set object even at `prefs.json`'s values, since it still governs the 04 family (an exception to
  01 §11's "only values that differ from the defaults", for these three keys only); the empty set removes the key.
- `prefs.changed` names a key when its effective value (the 01 side, what `prefs.get` answers) changes.
- `prefs.json`'s defaults, `TimelineEditOptions::default` and `TransferOptions::default` stay as on `main`; a unit test
  (`the_two_default_tables_differ_in_two_members_and_the_fallbacks_follow_them`) prints the differing members
  (`["overwriteDrawings", "updateColours"]`) and keeps each fallback equal to its table.
- E-20: `cell.clipboard.set {cut: true}` records the set it applied (01's names) in the clipboard's `options`, as
  `edit.cutSpecial` does; a copy records none.
- Each command's options description names the default it reads (the generated `commands.ts` carries them).

## 9. Residual risks

- **A stored member at the edit family's value raises no `prefs.changed`.** Storing *overwrite existing drawings* on
  through `prefs.set` changes what the 04 family applies but not the key's effective value, so no event is raised. The
  C5.1b dialogs read the store when they open; a surface that caches the 04 family's set must read
  `timeline.transferOptions.get` again after its own writes.
- **A preferences file written before E-19** holding a whole transfer-option object (any non-default value) now counts
  every member as stored, so the 04 family follows those values. M4 had no dialog writing these keys; only an agent's
  `prefs.set` could have.
- **The kernel note's §4 and §7 describe the plan before E-13 to E-20;** §10 records what holds.
- **The rows-list ratio** at 1,000 elements is CI's shape (D-45); the workstation receipt is C5.1b's, with the window's
  budgets (plan §6.2, E-11).
