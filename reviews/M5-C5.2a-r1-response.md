## 2. From the observations

- **A panicking render** left the worker marked running for ever. The render is caught (as E-29 for handlers): the key
  is recorded as failed (the read's new `failed` member, not queued again at that revision), the worker goes on, and a
  guard lets a later read start a worker however the thread ended. Test with a dev-only panicking render: the unit
  test `thumbnails::tests::a_panicking_render_is_contained_and_the_worker_goes_on` (`ad6fad39`; moved into a unit
  test, where clippy allows the panic, after the test-hooks form flagged `panic_any` in the hooks module).
- **The history: the bound after a replay.** A replayed step is measured again (its redo can be larger) and the bound
  now applies once every transaction of the call is accepted (`History::apply_bound`, called at the end of the accept
  loop). Not inside `replace_edit`: a multi-step undo's replays carry step indices fixed before the call, so a discard
  between them would shift the indices. Unit test `a_replayed_step_measured_again_is_held_to_the_bound` (`43bfa853`).
- **The history's counted size against the memory held** (`crates/executor/tests/c52a_history_size.rs`, test-hooks,
  a counting allocator; a receipt that prints its numbers):
  - A patch step of 5,000-character notes: the bound counts **10,073 B**; the history holds about **47,300 B per step
    (4.7 times)**: a `serde_json::Value` in memory (its tree, strings with capacity, map nodes) against its serialised
    text. The revision log holds another **22,500 B per change** (each change's back patches, for 10,000 revisions),
    outside the bound.
  - A snapshot step (a checkpoint restore) counts only the entries it changed (**6 KB** here). Once later edits replace
    the entries it shared with the live document, it holds them alone: on the sample with a 20,000-stroke drawing, edited
    once and pushed past the revision log's 256-revision window, the step holds **24 MB** the bound never counted
    (1.4 MB with the 1,000-stroke drawing the test runs with in CI).
  - **Found while measuring:** every commit rebuilds the document's derived data, its object index included
    (`Document::rebuild_derived`), and the revision log keeps the `before` document of each of its last 256 revisions
    while the objects their changes touched fit its budget, which weighs the touched objects, not the index each holds.
    On the 20,000-stroke sample, 300 note changes hold about **3.1 GB** (about 10 MB per change). Recorded in the merge
    note §6 with E-44's commit cost (the same rebuild; M11 C11.1); not changed here.
  - What follows for the bound: it counts serialised sizes, so 1 GiB counted is several GiB held in the worst case; the
    floor of 200 steps and the step limit still hold. A truer count (in-memory sizes, and a snapshot step charged for the
    entries it holds alone) is possible; I propose it with the index-sharing fix, as ruled.
- **`c52a_availability.rs` left out rows**: now every row and type of 04 §13.20 (E-67, §3).
- **The dialog rule (11 lines 236-241)**: the behaviour is kept (M4's arbitration) and the two statements recorded as
  **SI-221** for the user.
