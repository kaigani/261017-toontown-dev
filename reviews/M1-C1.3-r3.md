## New findings

### C13-R3-01 — P1: Lock ownership publication and heartbeat remain unsafe at interrupted-writer boundaries

Locations: `crates/persist/src/lock.rs:181` (`acquire`), `:202` (`settled`), `:237` (takeover recheck), `:116` (`refresh`). Specification: 10 §8.6 LOCK-01/LOCK-02; ADR-0014 §11; standing C13-R1-02 exclusive-ownership/save-lock ruling.

`caf9c06` fixes the observed short empty-file race, but elapsed mtime is only a heuristic for writer death. An opener first creates an empty file exclusively, then writes/syncs its JSON, then returns `Acquired`. A live process paused between creation and writing for longer than two seconds has its lock removed and replaced. On resuming, its original file operations can complete successfully and `acquire` has no final publication/ownership validation. The two-second threshold therefore does not make “a lock being written is never taken over” true. This is distinct from the specified five-minute expiry of a **valid** lock.

Independently, `refresh` refuses only a **readable different token**. Missing or unreadable replacement content falls through to `write_atomic`, which republishes the old owner's token. This can occur during another takeover's remove/create/write boundary. Even a readable matching-token check and later atomic replacement are not serialized with takeover; a takeover can win between them. The new grace period is applied to acquire, not heartbeat publication.

Permanent reproducers: R3F `a_live_writer_paused_beyond_two_seconds_is_not_taken_over` **fails**: an open `create_new` writer is held for 2.2 seconds and a contender returns `Acquired`. R3F `heartbeat_refuses_an_unreadable_replacement_lock` **fails**: keep the old `LockHandle`, reproduce takeover's remove/exclusive-empty-create boundary, and invoke its heartbeat; `refresh` returns `Ok(())` and republishes old ownership. These are deterministic public-filesystem boundary fixtures. They do **not** claim an instrumented pause inside a real `acquire` thread, two simultaneously true `held()` observations, or a reproduced lost project save. The unsafe return/write paths are established by those fixtures plus source order; ordinary scheduler stress alone cannot close them.

Required closure: make ownership publication and heartbeat replacement participate in one ownership/arbitration protocol. A resumed writer must not announce success for a removed/replaced publication, and an old heartbeat must not recreate/replace another claimant's publication. Test these boundaries, including a paused writer and a heartbeat racing takeover, before carrying lock guarantees into headless/multi-client hosts. Waiting longer or repeating only the contention suites is not sufficient evidence.

### C13-R3-02 — P1: Asset replacement rewrites unrelated document text

Location: `crates/executor/src/commands/bundle.rs:868` (`substitute`), applied at `:1374`. Specification: 10 §6.8 / §10.2 `doc.import.json`; spec A `doc.import.json`; ADR-0014 §7 describes repointing **references**. Object names and other strings are independent values, not references merely because their bytes equal an ID.

Repro: start from a valid fixture whose scene display name equals the existing sound asset's ID (a legal name); import a same-named replacement sound asset. Import succeeds, but the scene is renamed to the new random asset ID. `substitute` replaces **every** matching string outside `meta`/`ext`, including names and other non-reference properties. Generic scene rename is not used; this happens implicitly as part of asset import. A save will persist that unrelated content change.

Permanent test: R3E `asset_replace_preserves_unrelated_strings_equal_to_the_old_id` **fails**, showing the old scene name versus the newly generated ID. Fixture installation succeeds through the executor's full integrity gate; this is not an invalid-input case. Update actual typed/reference-bearing positions, preserving display text and unknown non-reference values. Keep placements, media sequences, pens, opaque metadata and one-step undo coverage. This finding keeps Interchange and `doc.import.json` divergent even though the original append-instead-of-replace reproducer passes.

### C13-R3-03 — P2 ticket: Every export duplicates omitted media into unused cache files

Locations: `crates/executor/src/persistence.rs:198` / `:209`, `crates/executor/src/commands/doc_io.rs:1216` (export uses `write` and drops the returned carried list). Owner: **M1 C1.3 persistence/cache lifecycle**, with C1.4 long-running-session regression coverage. No GitHub issue created.

Repro: open a package holding embedded media, remove the asset, and export repeatedly without switching the live source. Every call copies the same omitted source bytes into a fresh random cache directory. Export never consumes `Written.carried`, so these files are not undo sources and subsequent exports cannot reuse them. R3E `repeated_exports_do_not_duplicate_omitted_media_in_session_cache` **fails**: one observed cached payload becomes four after three more identical exports. The fixture uses 4096-byte payloads; cost scales as omitted bytes × export count. Failed writes after carrying can also leave unused copies by source inspection; that failure variant is not independently fault-injected here.

There is no per-project/content bound during a session, and closing a project does not clear this environment-wide cache. Executor stop does remove it (`maintenance.rs:214`), so the builder's “ends with the session” statement is valid only for executor lifetime, not project close. No lost undo bytes were reproduced; keep severity P2. Avoid unnecessary carrying on export, or reuse/refcount carried data and clean it on failure/project lifecycle without evicting live history dependencies.

## Lock-state adjudication

`read` returns `None` for missing, malformed, oversized and otherwise unreadable content. Explicit read-only opens bypass acquisition and do not own/refresh a lock; a normal open also becomes read-only on `HeldByOther` or `NotWritable`. Heartbeats are scheduled every 60 seconds, and project saves check `held()`; these checks reduce the opportunity for stale writers but are not atomic exclusion with another filesystem actor.

| File state | Acquire / normal open | Takeover | Existing handle heartbeat / ownership implication |
|---|---|---|---|
| No file | Exclusive create, JSON write/sync, returns acquired | No stale warning | Existing handle with missing path also recreates it through `refresh`; not exclusive with an in-flight opener. |
| Empty file actively being written, age ≤2 s | Sleeps 5 ms and retries, up to 400 attempts | Recheck also refuses until settled | Short writer is protected from acquisition; heartbeat still treats unreadable content as permission to write (R3-01). |
| Empty file, live writer paused >2 s | Classified settled/unreadable | Arbitration removes it and exclusively creates replacement | Cannot distinguish pause from death; original writer has no final ownership validation (R3-01). |
| Settled empty file, writer dead | Stale candidate | Taken over under `.takeover` | Abandoned initial publication is recoverable; builder unit test passes after 2.1 s sleep. |
| Valid lock, fresh heartbeat, live PID | `HeldByOther`, read-only | Refused on recheck | Matching token refreshes; different readable token refuses, and maintenance converts old session to read-only. |
| Valid lock, heartbeat >300 s old | Stale even if PID remains alive | Token + stale recheck under arbiter | Old handle may race heartbeat publication against takeover; old token is not authority after another wins. |
| Malformed/unreadable file | Recent mtime waits; settled becomes stale; metadata/permission errors may exhaust loop or return not-writable | Same settled test under arbiter | `refresh` does not fail closed on unreadable contents (R3-01). Genuine permission failures can stop replacement rather than grant ownership. |
| Valid same-host dead PID | Stale immediately, irrespective of heartbeat age | Normal arbitrated takeover | Existing actual-child process-death tests pass. Unknown process-liveness result is treated as alive. |
| Valid reused PID | Reused live PID looks alive while heartbeat fresh | Eventually taken after heartbeat expiry | PID identity has no start-time token; stale detection can be delayed and clock changes affect it. C1.4 obligation. |

“Settled” means **mtime older than two seconds**, not continuous observed stability and not a monotonic deadline. A fresh empty file abandoned by a crashed writer becomes eligible after approximately two seconds under a stable wall clock; one acquisition may instead exhaust its retry loop near that threshold and return not-writable, with a later attempt succeeding. There is no strict wall-clock bound around filesystem calls. A future mtime/backward clock change can keep it unsettled indefinitely across calls. An abandoned arbiter expires after ten seconds, but one acquire only tries roughly two seconds of sleeps; a paused original arbiter can resume after another has removed its file. These are not resolved by `caf9c06`.

Stress evidence: **50 runs of the unchanged 8-session suite and 50 runs of the unchanged 32-session suite, zero failures** (`lock-stress.json` / `.log`). Each 8-session run includes 64 stale trials; each 32-session run includes 64 stale and 64 initially absent trials: **9600 trials / 230400 acquisition attempts** in total. Results stay alive until owner counting. No claim is made that zero observed failures proves every interleaving safe.

## Watchdog test adjudication

The declared retry in `c12_kernel_state::the_watchdog_answers_within_its_budget` is **acceptable for its caller never-block test**, with a narrower setup claim. The measured query loop is unchanged: a 1 ms budget eventually produces `command.timeout`, reports that budget, and each caller invocation returns within the existing 500 ms assertion. Setup now permits the first `open_document` to finish after its caller times out. Accepting `project.unsavedChanges` is consistent with a prior attempt having installed the identical untitled/dirty fixture; it does not establish that any open succeeded within 1 ms. The assertion message claiming “within the budget at least once” overstates that evidence.

Measured **20 individual `open_document` calls on that same seed-1 in-memory fixture**, using a normal budget and constructing the fixture before the timer: min/median/max are recorded in `open-latency.json` (approximately **1.09 / 1.15 / 1.25 ms** on the final run). This explains why a 1 ms setup assumption is fragile. It is not a measurement of filesystem `project.open` jobs, and there is no historical latency baseline here from which to claim either a latency regression or its absence. The retry can hide increased **setup latency**; it does not weaken the existing timed query assertion. C1.4 must retain caller timeout tests for actual open jobs and queue congestion; the present test is not proof of every never-block requirement in 11 §14.5.

## Concrete C1.4 obligations

1. **Resolve R3-01 before presenting cross-session write exclusivity.** Deterministically suspend a publisher and a heartbeat at each ownership boundary, then race takeover. Assert at most one authorized writer, resumed stale writers fail closed, and save/clean markers cannot advance under lost ownership. Run on NTFS and APFS; keep 8/32-session stress as additional coverage.
2. **Define PID reuse and clock behavior.** Distinguish process identity from a recycled numeric PID, bound process-liveness subprocesses, and test heartbeat/arbiter/mtime behavior under backward and forward clock jumps. Include a crashed empty publisher, future mtime, ten-second abandoned arbiter, and a paused arbiter resuming after expiry. Document expected read-only/retry results and a measurable liveness bound.
3. **Certify normalization on macOS.** Create NFC/NFD colliding unknown entry names in a package, attempt folder conversion on the actual APFS configuration, and require preflight refusal or a specified lossless representation. Verify no overwriting of either payload, sibling journal collisions, or altered unknown data. Individual Unicode-component acceptance on Windows does not establish this.
4. **Measure fingerprint cost and define the remaining blind spot.** On a stated large-file-count fixture, record O(files) traversal cost at the default two-second watch interval and caller watchdog latency while it runs. Test size+mtime-preserving external edits explicitly; either detect them (e.g. additional hashing/event policy) or obtain a documented spec-owner ruling for RO-02. Preserve nested hidden content and root-control exclusions.
5. **Establish autosave latency.** Trigger autosave during a long atomic batch, then under queued MCP requests, large preserved media and background save work. Recovery may contain only a pre/post-transaction committed snapshot, never intermediate edits; assert the ≤50 ms typical snapshot budget of AUTO-02 on a defined fixture and set an explicit maximum scheduling delay. Retain untitled, recovered-source deletion and undo-byte tests.
6. **Close SI-044 / implement SI-045.** Obtain the spec-owner decision on non-undoable Repair on Open without installing an invalid revision. Convert `project.changedOnDisk` to `needs_confirmation`, test reload/keep-mine decisions, expiration/replay and headless responses, and recheck file identity and lock ownership after confirmation rather than trusting an earlier observation.
7. **Preserve transaction/host contracts.** Actual MCP/headless `project.open`, save, close, quit and batch-script paths must preserve `LoadGrant`, staged integrity/frozen gates, one committed revision per atomic batch, deferred effects, filesystem roots/scopes, idempotent request envelopes, and exactly one correct audit/commit record. Test caller timeouts without asserting that a timeout cancels document-thread work; measure queued-call responsiveness and eventual job state separately.
8. **Bound session resources.** Carry R3-03 into long-running MCP/export scenarios. Repeated exports/failures/project switches must not multiply unused cached bytes, and cleanup must not discard blobs still required by undo, checkpoints or in-flight snapshots. Observe cache size before/after project close and executor stop.

Windows durability remains the accepted ADR-0014 write-through deviation. These tests do not establish physical power-loss durability, UNC/multi-machine locking, or constant memory for valid gigabytes of JSON. The orchestrator should decide the open findings and SI-044, then request only scoped closure checks under plan §5.
