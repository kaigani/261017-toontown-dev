## New findings

### C14-R3-01 — P1: a committed atomic batch disappears from replay after publication fails

**Location:** `crates/executor/src/lib.rs:477`; `crates/executor/src/commands/agent.rs:668`.

After the integrity gate commits an atomic batch, a failed file rename changes its envelope to `error`, preserving its document changes and undo step. `audit_logical_call` nevertheless sets `committedSteps` to an empty list because it tests only `status == Ok`. Export then classifies this batch as `notCompleted`. The audit status is truthfully error, but its commit accounting and replay are inaccurate.

**Repro:** make an ordinary metadata edit; run an atomic batch containing another metadata edit and `doc.export.json` targeting an existing directory with overwrite permitted. The batch fails publication but its metadata edit remains in the live document. Export activity as batch and replay through script mode into the same initial document: canonical entries differ because that committed edit was omitted. The sequential control preserves the prior committed step and passes.

**Requirement:** 11 P8, §11; SI-051; ADR-0015 §12 explicitly preserves committed changes after publication failure and requires replay of every committed edit. **Regression:** `crates/mcp/tests/c14_r3_replay.rs::atomic_publication_failure_keeps_committed_edits_in_script_replay` (fails), with the sequential test as a passing control. **Owner/deadline:** builder, C1.4 scoped closure before M1 merge. Commit metadata must come from the actual commit, independently of response/publication status.

### C14-R3-02 — P1: replay loses atomic transaction boundaries, revisions and undo semantics

**Location:** `crates/executor/src/commands/agent.rs:707` and `:721`.

A successful atomic batch is flattened into separate steps of the exported sequential batch. Two changes that originally committed at one revision become two commits on replay. The canonical scene revision is 3 instead of 2 even though its metadata values agree. A later one-step undo also acts on only the second replayed edit, whereas it originally undid the whole atomic batch.

**Repro:** snapshot the initial project, run one atomic batch with two distinct metadata changes, export activity, and run that export through script mode on the initial document. Compare canonical JSON byte for byte, including revisions. **Requirement:** 11 P7, §7.3, §11; SI-051's explicit same-document-entry replay promise. ADR-0015's flat sequential representation does not satisfy that promise for multi-edit atomic batches. **Regression:** `crates/mcp/tests/c14_r3_replay.rs::two_edits_in_one_atomic_batch_replay_with_the_same_revision` (fails). **Owner/deadline:** builder and orchestrator, C1.4 scoped closure before M1 merge; decide a replay representation that preserves commit and history boundaries. The additional `undo_after_an_atomic_batch_replays_the_same_document` and `checkpoint_restore_after_an_atomic_batch_replays_the_same_document` regressions also fail; redo remains a required closure variant.

### C14-R3-03 — P1: a cancelled elicitation accepts a late answer and overwrites a file

**Location:** `crates/mcp/src/server.rs:234` and `:949`.

`ask` checks cancellation only when `recv_timeout` times out. An accepted answer arriving after the cancellation takes the unconditional `Ok(r)` branch; `call_tool` then re-invokes the overwrite with its confirmation token. Sending cancellation first and acceptance second in one ordered pipe write overwrites the original bytes. A queued ordinary tool answers, so this variant releases the worker, but it violates the explicit cancellation/confirmation contract.

**Repro:** under Assist with elicitation enabled, request activity export over an existing file. Wait for `elicitation/create`, send `notifications/cancelled` for the owning request, then immediately send `accept` with boolean `confirm: true` for the elicitation. **Requirement:** 11 §6.3, §14.7; ADR-0015 §12: cancellation withdraws the ask, its token stays pending, and nothing is authorised. **Regression:** `tests/adversarial/c14-r3-mcp.py::test_cancelled_elicitation_does_not_authorize_a_late_accept` (fails against the exact-head Windows CI binary). **Owner/deadline:** builder, C1.4 scoped closure before M1 merge. Recheck cancellation before consuming the answer and before the confirmed re-invocation; preserve no-response behavior for the dropped request.

### C14-R3-04 — P2: malformed boolean measurement summaries pass validation

**Location:** `scripts/analyse-measurements.py:87`–`:90`.

The sample values correctly reject booleans, but stored summaries are compared with Python equality without type checks. With one observation of value 1, any of `n`, `p50`, `p90`, `p99` or `max` may be `true` and the file is accepted. This does not invalidate the retained numeric observations: all 19 local/CI files independently recompute successfully.

**Requirement:** evidence hygiene, C14-R2-06 malformed-observation gate. **Regression:** `tests/adversarial/c14-r3-measurements.py::test_boolean_summary_fields_are_not_valid_numeric_evidence` (five failing subcases). **Owner/deadline:** builder, C1.4 closure or explicit orchestrator P2 disposition before M2 C2.1. Require numeric summary types, with an integer count, before comparing values.

### C14-R3-05 — P2: one new product lint suppression violates the standing rule

**Location:** `crates/executor/src/lib.rs:457`.

The response adds `#[allow(clippy::too_many_arguments, reason = "one activity entry")]` to `audit_logical_call`. It suppresses a style lint rather than introducing a safety defect, so this is P2. The claim that no new product `#[allow]` exists is false; no new `unwrap`/`expect`/`panic`/`unsafe` candidate was found.

**Requirement:** standing product-code rule. **Regression:** `tests/adversarial/c14-r3-measurements.py::test_no_new_product_allow_attributes_since_round_two`. **Owner/deadline:** builder/orchestrator, C1.4 closure before M2 C2.1: remove it through an entry/options struct or explicitly rule on this narrow exception.
