## 2. C42B-R1-04: the long stroke on the large drawing

**The difference from the round-1 receipts.** The receipts' 125-146 ms long strokes ran on the *small* drawing
(before the large one was built), so they never measured the budget case; the reviewer's 216-229 ms ran on the
50,000-point drawing. A second difference made the window's figure optimistic: the canvas counted a commit as drawn
at the first frame after the *scene* answer arrived, while the old geometry was still resident; at that frame the
overlay ink was already cleared, so the committed stroke briefly disappeared until its reload was drawn. Both are
fixed: the measure script now measures the long stroke on the large drawing, and the canvas times a commit (and keeps
the gesture overlay) until every drawing of the scene is resident at its scene revision (`settledVersion`).

**Where the time went** (release profile, kernel, the reviewer's fixture and 9,998-event gesture; 30 samples, each
undone; `c42/budgets.rs` `long_stroke_on_the_large_drawing`): the commit (the `pointer` call) p50 170 ms, p95 176 ms;
the scene and the full reload only 24-26 ms. Inside the commit, `draw.stroke.add`'s handler took 107 ms, of which 80 ms
was the document's general commit path re-serialising, patching, re-parsing and diffing the whole 50,000-point drawing
for one appended layer, and 22 ms its change records (a whole-drawing own-view diff on both sides). Every edit of a
large drawing paid this, the ordinary ones too. The reload was not the problem, so a changed-region payload would not
have met the budget.

**The fix: incremental commits for the commonest edit.** `Document::with_patched_entries_undo_only` takes a fast path
when a commit only appends nodes to a drawing (the Brush and Pencil tools' new layer) or strokes to one layer: the
appended objects pass the full object input path on their own, the typed drawing is extended and checked as a whole,
and the undo is the general path's for an append. `change::diff` takes the matching fast path for appended nodes. Both
are checked against the general path on every use in debug builds (`assert_eq!` on the document, the undo patch and
the change records), so every test that adds a stroke compares them: every debug `cargo test` since the fast path, the `check` jobs of both OSes included. Any other shape, and anything the
general path would refuse, takes the general path unchanged.

## 7. C42B-R2-01: the long stroke on WebGL2

**Cause.** The WebGL2 back end uploaded and drew the whole tool overlay (the gesture's ink, every sample's triangles)
again on every frame, whether or not it had changed. While the window waits for a 9,998-sample stroke's commit, the
overlay is the unchanged stroke, so each frame re-uploaded about ten thousand quads; that work sat on the same thread
as the commit's answer and the reload, and showed as 165/218/219 ms (p50/p95/max) in the reviewer's run. WebGPU keeps
its overlay buffer between frames, so it did not pay this. The fix: WebGL2 draws the overlay again only when its
triangles, the target size or the sample count change (`59aae58`); otherwise the cached overlay is composited as the
static layers already were.

**Two further changes, and what each measured.**
- *The first agent stroke of a run* (`be8ee43`). Every reviewer `d1-long` run had a first sample of 150.8 to 152.3 ms
  (the rest at most 145.7): an agent's `pointer` naming a tool activated it only at the commit, so the window had
  played the stroke with the previous tool and then restyled and redrew the long overlay while the commit was being
  drawn. A workstation experiment with the Brush already active gave a first sample of 132.9 ms. The host now makes
  the named tool active as the call arrives, before the window plays it (11 §7.6: the tool, then the gestures;
  headless runs them in that order); the commit's own `tool.active.set` changes nothing, the answer's shape is
  unchanged, and a refused activation is the call's answer. Host test
  `a_routed_gestures_tool_is_active_before_the_window_plays_it`. On the final build the round-1 probe's first samples
  were 132.8 (WebGL2) and 135.5 ms (WebGPU).
- *The final hover's hit test* (`224d701`, `3a830b9`). The answer to the user's own window gesture named the objects
  under the final pointer, which the window never reads; the user's window gestures now go through
  `pointer_in_window` and skip that hit test (agents' calls keep it; test
  `c42 pointer::a_window_played_user_gesture_answers_without_the_hover_objects`). It removes unused work but made no
  measurable difference to the long stroke (WebGL2 p50 128.9 before, 128.5 after): I do not count it as a saving.

**Why the rule set may prefer WebGL2.** ADR-0007's rule set (step 1) ranks the scorable back ends by the worst of
three *static* redraw scenes (paths100k, groups1k, brush10k: pan and zoom over a fixed scene, no tool overlay, no
commit). On the workstation both back ends meet all three by a wide margin, so the run's higher worst scene wins and
either is "go as written" (row 6): the builder's first run selected WebGPU, the reviewer's round-1 run WebGL2. The
scenes do not exercise the overlay or a commit, so they could not see the WebGL2-only overlay cost; that is why a
machine could select WebGL2 and miss the long-stroke budget. With the overlay drawn only when it changes, both back
ends meet the plan §6 bounds on the workstation (table below), so whichever the rule set selects is within plan §6.
The rule set is unchanged (it is normative and mirrored); ADR-0007's amendment records this, and adding an
interactive scene to the rule set is an ADR change I can make if the owner wants one.

## 8. C42B-R2-02: the active view when a float has focus

The e2e's float comparison renders `activeView`; with the Camera view central, the active view was the Camera view
(whose `activeView` render is C4.3), so the comparison refused with `render.compositionUnavailable`. The e2e now runs
`view.active.set drawingView` first (`e2adfc8`); the reviewer's `gui` mode passes unchanged.

**What the active view is when a float has focus.** Focus does not change it. The active view is the view window last
activated (`view.active.set`, or `app.mode.set`, which activates a view of the requested type) while it is shown, else
the central view (`ui.rs` `active_view`). A float's window taking the OS focus runs `window.panel.set {panelId, focus:
true}` (`floats.rs`), which moves `focusedPanel` and nothing else; so with a floated Drawing view focused and the Camera
view central, `app.state.get` reports `focusedPanel: "drawingView"` and `activeView` the Camera view, the mode is
staging, and `activeView` renders refuse until the Drawing view is activated. The float's canvas still draws and its
gestures commit, because the canvas addresses its own view id, not the active view. 01 §12's GUI column gives "Click
into a view window" as the GUI path of `view.active.set`; the window does not do that yet (the doc comment claiming
"focused last" is corrected, `ui.rs`). Declared in the handoff as a residual: wiring a click into a view window to
`view.active.set` changes what agents observe (mode, `activeView` renders) on every first click, and it touches the
three-way comparison the reviewer runs unchanged, so I propose it for C4.3, where the Camera, Top and Side views make
the active view matter for drawing; it is one line in `CanvasView`'s press handler if the owner wants it now. The rule is now written in the views note
(`reviews/M4-design-views.md` §1), and SI-142 records that an `activeView` render's result does not name the view
(the screenshot's does). Found while testing R2-03: the Drawing view panel switched to another type (`view.type.set`) still shows the drawing canvas, because the panel shows its canvas by
panel id; the Camera, Top and Side views' own canvases are C4.3, and this is declared with them.
