### C04-R1-01 — P1: tablet outcome tables do not define a decision for partial or slower success

**Location:** ADR-0009 lines 73–92; go/no-go tablet outcome tables. **Requirements:** plan §2.3 / M0 C0.2 and C0.4;

The same hole exists at 240 Hz without coalescing, and when both paths deliver pressure but neither delivers tilt.
The manual test explicitly calls a sub-200-Hz result below target rather than a failure. The report's summary also
omits ADR-0009's coalescing precondition, so the two tables can disagree. On Windows, a pen without barrel rotation
cannot establish “full twist”; a DOM path with pressure but incomplete tilt/twist and unusable fallbacks has no
terminal row, because no-go tests only pressure. H is selected from pressure/tilt alone while promising twist.

**Reproduce:** `python reviews/evidence/M0-C0.4-r1/decision_probes.py`; see the first three cases in
[decision-counterexamples.json](evidence/M0-C0.4-r1/decision-counterexamples.json). These apply the written

**Required:** define capability-relative success (including devices without tilt/rotation), rate-only misses,

### C04-R1-03 — P1: ProRes 4444 is incorrectly selected as a lossless export format

**Location:** ADR-0008 line 97; SI-001 lines 17–18. **Requirements:** spec 09 §4.4 quality and §4.3 format capabilities.

Both documents place ProRes 4444 in the formats offered for lossless export. Its colour channels use lossy coding;
the alpha channel's exact preservation does not make the whole frame mathematically lossless. Apple distinguishes
these properties in its [ProRes white paper, page 18](https://www.apple.com/final-cut-pro/docs/Apple_ProRes.pdf).
The spec recommends ProRes as an **alpha-capable** codec, not as a lossless colour codec. Likewise, “image sequences”
is too broad: the required sequence formats include JPEG.

**Required:** keep alpha capability separate from lossless colour/alpha round-trip capability. Restrict lossless
selection to verified formats/configurations (for example PNG sequences/PNG-in-MOV) and require decoded pixel
comparisons in E-FF1. Correct SI-001 before asking the spec owner to approve its proposed interpretation. Primary
source URL/hash/date receipts are [retained](evidence/M0-C0.4-r1/primary-source-receipts.json); no encode measurement
is claimed for the unbuilt sidecar.

### C04-R1-04 — P1: ADR-0008 excludes encoded files from determinism without addressing spec 09 §11.1(6)

**Location:** ADR-0008 lines 103–104 and E-FF1; go/no-go FFmpeg decision. **Requirements:** spec 09 §11.1(6),
`export.movie.run` in §11.2; plan §5.3 (raise spec conflicts rather than narrow requirements).

The ADR cites 06 §6.7 to say determinism covers frames, not encoded files. That citation is valid for raster
pixels, but it does not discharge 09 §11.1(6): `deterministic: true` on movie export strips variable metadata so
repeated exports have identical checksums. The parameter is in the command schema. Cross-OS movie equality need
not follow from that clause; **repeatability within a fixed build/platform/configuration still must be addressed**.
E-FF1 checks streams, playback, quality, fast start and Windows N, but never repeats an encode or compares files.

**Required:** distinguish raster determinism, repeat movie determinism and cross-platform movie identity. Add
repeated process/encode checks for the chosen H.264/AAC/muxer paths, including metadata, and define the action if
platform encoders cannot satisfy the required mode. Escalate an actual incompatibility to the spec owner; do not
silently remove the parameter's guarantee. This finding is an omitted obligation, not a claim that a particular
platform encoder has already failed the test.

### C04-R1-05 — P1: shell no-go logic assigns every unsigned-app launch failure to signing

**Location:** go/no-go lines 45–50. **Requirements:** plan §2.3, §2.4, M0 C0.4 and §6.7; ADR-0005's untested floor.

The report says a failure to launch the unsigned app is a signing/Gatekeeper matter for M11 and cannot be a shell
no-go. No cited experiment establishes that cause. An app can fail after quarantine is resolved because of a
missing library, unsupported OS/runtime/API, architecture mismatch or a startup crash. The Mac manual shell run
is still pending, and current-arm64 CI does not test the minimum OS. Automatically deferring such a result could
approve a shell that does not run on the promised platform.

**Reproduce:** apply the published rule to a user report that the unquarantined app crashes before opening its
window; it still assigns M11 signing. **Required:** distinguish confirmed Gatekeeper/signing failures from
unexplained launch/runtime failures. Route the latter to a named diagnostic/retest and withhold the affected
platform/floor conclusion until resolved. Preserve Tauri and the user's Qt-only/both-platform restriction; this
finding does not recommend a shell change or claim an observed Mac crash.

### C04-R1-06 — P2: the asserted FFmpeg linkage gate is stronger than `deny.toml`

**Location:** ADR-0008 lines 78–80; `deny.toml` licenses/bans. **Requirements:** ADR-0003 rule 3; plan §6.3.

“Any Cargo crate that links FFmpeg fails the existing gate” is false in general. The gate evaluates package SPDX
metadata, not the licence of every library selected by a build script. A standalone MIT-declared package with
`links = "avcodec"` and a `cargo:rustc-link-lib=dylib=avcodec` build script passes the unchanged licenses, bans and
sources checks. The bans list names Electron only. This is a metadata probe, not an allegation that current
product code links FFmpeg, nor that a named third-party crate falsely declares its licence.

**Reproduce:** `python reviews/evidence/M0-C0.4-r1/probe_license_gate.py`; exact fixture and commands in
[license-link-probe.json](evidence/M0-C0.4-r1/license-link-probe.json). **Required:** correct the existing-gate claim
and assign explicit native-linkage/dependency checks before sidecar adoption. Keep LGPL out of the Cargo/npm
allow-list. Also make the intended component whitelist explicit: upstream `--disable-autodetect` controls
external discovery, not all built-in codecs; [FFmpeg's encoder documentation](https://ffmpeg.org/ffmpeg-codecs.html#Encoders)
describes the separate encoder enable/disable switches. The proposed sidecar presence checks alone are not an
exact capability whitelist.

### C04-R1-07 — P2: follow-up milestones are inconsistent with the approved plan
