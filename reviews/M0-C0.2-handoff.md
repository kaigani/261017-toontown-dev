# M0 C0.2 handoff — tablet input spike

Branch `m0-foundations`, commits `44998c9..HEAD` (on top of the C0.1 round-5 merge). Builder: Claude Opus 5.5.
**Everything in this checkpoint is spike code** (`desktop/src/spikes/`, `desktop/src-tauri/src/spikes/`), reachable
only with `--spike tablet`, and is rewritten before anything moves into product code.

## Hardware statement (read first)

- **This Windows machine has no pen or tablet hardware** (no pen/digitizer devices; `SM_TABLETPC` false). All Windows
  numbers below come from **synthetic pen input** (`CreateSyntheticPointerDevice(PT_PEN)` +
  `InjectSyntheticPointerInput`), clearly labelled as such. They exercise the Windows pointer stack, WebView2 and
  Windows Ink with known values. They are **not** evidence about real tablet hardware or drivers.
- **The synthetic run could not execute on this machine's desktop.** Two **Windows Security** prompts have been
  pending since 2026-10-17 17:11 and 17:55 (processes `PickerHost`). Their system dimming layer (`Shell_SystemDim`,
  topmost) covers the whole screen. The injector's safety check correctly refused to inject, because the canvas was
  covered. I did not touch the prompts; they belong to the user.
- The Windows numbers were therefore measured on the **GitHub `windows-latest` runner**: a VM without a GPU, 2 vCPUs,
  WebView2 154, display at ~64 Hz. It runs as a non-blocking CI step (`ci.yml`, bundle job), in two runs. Runner
  load affects some results (see "Losses").
- macOS: built and compiled on CI, not exercised with input. **Pending user**:
  `docs/manual-tests/M0-C0.2-tablet-macos.md`.

## How to run

Windows (needs an uncovered desktop for synthetic input):
```sh
pnpm --dir desktop tauri build --no-bundle -- --locked
target/release/toontown.exe --spike tablet --spike-log tablet.json               # interactive: draw, "Save log"
target/release/toontown.exe --spike tablet --spike-log tablet.json --spike-auto  # synthetic 240 + 500 Hz, saves, exits
python scripts/analyse-tablet-log.py tablet.json
```
macOS (user): see `docs/manual-tests/M0-C0.2-tablet-macos.md`. The one command is
`~/toontown-m0/desktop/Toontown.app/Contents/MacOS/toontown --spike tablet --spike-log ~/toontown-m0/tablet-mac.json`.

| **Native path (`octotablet`/Ink RTS) packets** | **0** (initialised: 1 ms granularity, 0 tablets) | **0** |

Notes:
- Injection → event latency compares the host's and the webview's wall clocks (same machine). The small negative
  values are clock-reading noise, so treat the sub-millisecond figures as "≈ 0". Event → handler ≈ one display frame:
  WebView2 delivers pointer events at frame cadence (frame interval 15.6 ms on the runner), with the intermediate
  samples in `getCoalescedEvents`.
- **Losses** (frame numbers are 1-based; frame 1 is the `pointerdown` and is always counted "missing" because only
  `pointermove` samples are matched, so it is a matching artifact, not a loss):
  - Four frames (93, 422, 605, 934) are missing in **every** stroke of both runs, at both rates. Each is a one-frame
    hole in time. This is deterministic, not load: a synthetic-injection quirk whose cause I have not identified.
  - The remaining losses are **load-correlated** and mostly in the 240 Hz strokes (the first stroke of each run):
    - a block at stroke start (frames 4–10 in run 1; almost all of frames 2–94 in run 2, with injection → event
      latency spiking to 381 ms);
    - a ~40-frame block mid-stroke (frames 837–875 in run 1, 847–886 in run 2) during a ~168 ms stall.

    The 500 Hz strokes lost only 1–8 frames beyond the four above. I cannot separate runner/VM stalls from WebView2
    behaviour without a normal desktop.
- Against the C0.2 pass criteria (Windows, synthetic input):

  | Criterion | Result |
  |---|---|
  | pressure ≥ 1024 levels | met (1024 implied) |
  | tilt present | met (exact) |
  | coalesced events delivered | met (p50 4 at 240 Hz, 8 at 500 Hz) |
  | **no dropped samples at ≥ 200 Hz** | **not met on the runner** (0.6–13 % lost, mostly in load stalls). Needs a real-hardware run on a normal desktop. |

## Findings for the C0.4 go/no-go (escalations)

1. **`octotablet` cannot provide the macOS native fallback**; it has no macOS backend. The spike's macOS native path
   uses AppKit `NSEvent` directly through `objc2-app-kit`, already in the dependency graph via Tauri. Plan §2.3 names
   `octotablet` for this; C0.4 should record the substitution. **Pending user** measurement.
2. **On Windows, a native listener in the host process cannot see pen input over the webview.** The window that
   receives pointer input, `Chrome_RenderWidgetHostHWND`, belongs to `msedgewebview2.exe`. Verified by enumerating
   the app's window tree: `WRY_WEBVIEW` (ours) → `Chrome_WidgetWin_0` (ours) → `Chrome_WidgetWin_1` /
   `Chrome_RenderWidgetHostHWND` (msedgewebview2 process). Ink RealTimeStylus attaches to windows in its own process,
   and it received 0 packets in both runs. Strong indication from synthetic input; real hardware is routed the same
   way. A Windows native fallback would need a different design: WebView2 **composition hosting** (the host receives
   input and forwards it with `SendPointerInput`; not supported by wry/Tauri today), an input overlay window, or
   wintab.
3. **`getCoalescedEvents` exists only from Safari/WebKit 18.2** (MDN compat data: also `getPredictedEvents` and
   `altitudeAngle`; pressure, tilt and twist since 13). Under the declared floor (macOS 12 / Safari 15, ADR-0005),
   WKWebView on older systems delivers one sample per dispatched `pointermove`, so strokes lose intermediate
   samples. Options: native AppKit path for drawing on macOS, or raise the floor (to a WebKit with 18.2). This
   strengthens the open "raise the floor?" question to the user.
4. **WebView2 web path on Windows looks viable on input fidelity**: pen type, pressure at 1024 levels, exact tilt,
   twist, coalesced events at 240–500 Hz. Latency is about one frame to the handler. Open: whether losses on a
   normal desktop are zero (runner stalls blur this).

## Known gaps

1. **No real tablet measured anywhere yet.** Windows numbers are synthetic and from a loaded VM; macOS is pending the
   user.
2. **The macOS native path has never received input.** It compiles and the monitor installs on the main thread, but
   correctness of coordinates (window points, bottom-left origin, converted on the page), tilt conversion
   (asin → degrees) and event coverage are unverified until the user's run.
3. **Local Windows synthetic run blocked** by the pending Windows Security prompts. After they are dismissed:
   `target/release/toontown.exe --spike tablet --spike-log tablet.json --spike-auto`.
4. **Four deterministic missing synthetic frames**, cause unidentified (above).
5. **Spike-page drawing is per sample and not optimised.** It is a measurement tool, not the M4 canvas.
6. **The spike commands are registered in release builds** (gated by the launch flag, like `--ipc-bench`). Remove or
   dev-gate them with the other M0 diagnostics.
