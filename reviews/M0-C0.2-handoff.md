Branch `m0-foundations`, commits `44998c9..HEAD` (on top of the C0.1 round-5 merge). Builder: Claude Opus 5.5.
**Revised after review rounds 1 and 2** (`reviews/M0-C0.2-r{1,2}.md`; responses `reviews/M0-C0.2-r{1,2}-response.md`).
The measurements come from log version 3, validated and recomputed by the analyzer, and are cross-checked with the
reviewers' independent `reviews/evidence/M0-C0.2-r2/audit-matrix.py`. The listener-matrix findings are stated as what

only with `--spike tablet`, and is rewritten before anything moves into product code.

## Hardware statement (read first)

- **This Windows machine has no pen or tablet hardware** (no pen/digitizer devices; `SM_TABLETPC` false). All Windows
  numbers below come from **synthetic pen input** (`CreateSyntheticPointerDevice(PT_PEN)` +
  `InjectSyntheticPointerInput`) and are labelled as such. They exercise the Windows pointer stack, WebView2 and
  Windows Ink with known values. They are **not** evidence about real tablet hardware or drivers.
- **No synthetic run executed on this machine's desktop.** Two **Windows Security** prompts (processes
  `PickerHost`, open since 2026-10-17 17:11 and 17:55) were still present when re-checked on 2026-10-18 before this
  round. Their topmost dimming layer covers the screen, so the injector's ownership check refuses to inject. I did
  not touch the prompts; they belong to the user.
- The Windows numbers were therefore measured on the **GitHub `windows-latest` runner**: a VM with 4 logical CPUs,
  no WebGPU adapter (`navigator.gpu` unavailable), WebView2 154.0.4258.62 and Windows 10.0.26100.33438 (all recorded
  in the log). The measurement runs as a non-blocking CI step (`ci.yml`, bundle job). Runner load affects some
  results.
- macOS: built, clippy-clean and unit-tested on CI, not exercised with input. **Pending user**:
  `docs/manual-tests/M0-C0.2-tablet-macos.md`.

## Measured — Windows, synthetic pen, GitHub runner

**Primary evidence: matrix 5** = CI run 39116097955, `reviews/evidence/M0-C0.2/tablet-spike-windows-runner-r2-matrix5.json.gz`.
Printed by `python scripts/analyse-tablet-log.py <that file>`. The numbers agree with the reviewers' independent
`audit()` (`reviews/evidence/M0-C0.2/r2-independent-audit.txt`). Matrices 3 and 4 (CI 39115272218, 39115685421) are
replicates with the same geometry. In both, the webview pressure-only run was refused; the cause is explained below.
Frame indices are 0-based. Each run injects 1046 frames: 1024 contact frames, plus 10 hover frames before, an up,
10 hover frames after and a final update.

**Controls, matrix 5:**
- **Geometry:** every run uses the same physical rectangle `[16, 109, 1012, 275]` (CSS 1012 × 275 from the canvas
  origin, DPR 1). On it the sine path repeats a pixel at exactly frames 92, 421, 604 and 933, on both targets.
- **Varying axes:** `sine`, `zigzag` and `stationary` vary pressure (1024 values), tilt X and Y (121 each) and rotation
  (360). `pressureOnly` varies pressure only. The `stationary` runs are therefore **non-position-changing updates**,
  not pressure-only.
- **Rates:**
  - the saved `achievedHz` equals the host estimator recomputed from the logged endpoints in every run (relative
    tolerance 1e-9);
  - the first-to-last estimator `(frames−1)·1000/(last−first)` is printed beside it, e.g. sine 500 Hz: host
    499.235 Hz, first-to-last 499.309 Hz.
- **Focus (recorded, not assumed):** at the start and end of every run, the foreground window was this app's main
  window (`Tauri Window`), and keyboard focus was in the WebView2 process (`Chrome_WidgetWin_1`, msedgewebview2 PID).
  For native-window runs the probe popup was **not** foreground (`WS_EX_NOACTIVATE`); it received input because it
  was topmost at the hit-tested point.

"Not measured" means that the WebView2 input window belongs to `msedgewebview2.exe` and this process does not observe
its WM_POINTER stream. The raw-input listener is a **hidden, page-wide background sink** (`RIDEV_INPUTSINK |
RIDEV_PAGEONLY`). Its count shows what that listener received, **not** what the webview's input window received.

What was measured (synthetic input only):
1. **RTS positive control.** RTS on a plain same-process window receives injected pen input. RTS and WM_POINTER
   together account for 1024/1024 frames: RTS takes over after 0–23 frames, varying by run, across matrices 1–5. RTS
   on the main (webview) window received 0 in every run of every matrix. *Hypothesis:* the difference is due to
   input being routed to the cross-process WebView2 child window. Not measured: RTS registration on that child.
2. **WM_POINTER on a plain window delivers every frame**, including the four repeated-pixel frames of the identical
   sine trajectory, all non-position-changing updates and all pressure-only updates (1024/1024 each).
3. **The DOM in the webview** receives:
   - only the pointerdown of a stationary or pressure-only stroke;
   - none of the four repeated-pixel frames on the same rectangle, at either rate (missing 4/4 at 240 Hz and 4/4 at
     500 Hz in matrices 3–5);
   - not all of frames 1–3 after the down: at least one of them is missing in all 15 moving webview strokes of
     matrices 1–5, and frame 1 itself in 14 of 15. The cause is not identified.
4. **Raw input:** the background sink received 1046 HID reports per run, from one device per synthetic pen
   (`\\?\Microsoft HID RID\000D_0002\<n>`). That matches the number of injected frames. The reports are logged
   (16 bytes each) but **not decoded**.
5. **Press-and-hold:** the canvas received one `contextmenu` at the end (lift) of each stationary and pressure-only
   stroke, and none during the moving runs. Before the page suppressed it (matrices 3 and 4), WebView2 left a
   top-level `Chrome_WidgetWin_2` window (the msedgewebview2 PID) over the canvas centre. That window caused the
   pressure-only refusals there, and the refusal message names it.

**Hypothesis, not established:** non-position-changing pen updates are lost on the way into, or inside, the WebView2
input path, because the same updates reach a plain window's WM_POINTER. This is target-dependent delivery: the
synthetic stream reaches every same-process listener measured, but not the DOM. Whether WebView2's input window
receives the WM_POINTER updates and Chromium discards them, or they are never delivered to that window, is **not
measured** (open experiment E1 under "Known gaps"). For real tablets, the risk is that pressing harder or lighter
without moving may produce no `pointermove` in WebView2. That needs hardware to test.

## Findings for the C0.4 go/no-go (revised after review round 2)

1. **`octotablet` 0.1.0 has no macOS backend**, so it cannot be the macOS native fallback named in plan §2.3. The
   spike's macOS native path uses AppKit `NSEvent` directly through `objc2-app-kit` (already in the graph via
   Tauri), with every accessor gated on its documented event type. It has never received input: **pending user**.
2. **Windows native path (synthetic evidence only).** Measured:
   - RTS attached to the app's main window received no injected pen input over the webview; RTS on a plain
     same-process window did;
   - a hidden, page-wide raw-input sink received one HID report per injected frame in every run. The reports are not
     decoded, and this says nothing about what the webview window received.

   This does **not** show that an in-process listener cannot see real pen input. Nor does it show that raw input
   carries usable pressure/tilt from a real tablet, or that main-window RTS fails with real hardware. Synthetic
   injection is not documented to behave like a driver in either respect. The candidates to test with one physical
   tablet:
   - raw input (`WM_INPUT` digitizer collection, decoded via the report descriptor);
   - RTS on a dedicated same-process window over the canvas;
   - for comparison: composition hosting (not available in wry/Tauri today), an input overlay, wintab.

   `RegisterPointerInputTarget` requires UIAccess and redirects rather than duplicates input. No architecture choice
   follows from this checkpoint.
3. **WKWebView API surface is not tablet value delivery.** `getCoalescedEvents`, `getPredictedEvents`, `altitudeAngle`
   and `azimuthAngle` arrive in Safari/WebKit 18.2 (MDN BCD, WebKit release notes); pressure/tilt/twist properties
   exist since 13. That dates the API; it does not establish that a Mac tablet's pressure, tilt, twist or even
   `pointerType = pen` reach WKWebView. Evidence points the other way:
   - Wacom's Safari results report no pen pressure in Safari 15 on macOS 12.1;
   - current Mac WebKit derives mouse-event force from `NSEventTypePressure` (Force Touch) in `WebEventFactory.mm`,
     not from tablet pressure.

   The user's Mac run is the measurement. **ADR-0005 stays at macOS 12.0 / Safari 15.0**; any floor change is the
   user's decision, after that measurement.
4. **WebView2 web path on Windows (synthetic input).** Delivered:
   - pen type, exact tilt and a pressure grid of 1024 levels;
   - coalesced events (p50 4 samples per dispatch);
   - event timestamps within ~0.3–0.9 ms of injection (p50); handler one frame later (oldest sample p50 13.9 ms).

   Reproducible input-fidelity risks:
   - non-position-changing updates (stationary, and pressure-only with tilt and rotation fixed) produce no
     `pointermove` after the down;
   - repeated-pixel frames are missing;
   - some of the first frames after the down are missing;
   - twist arrives modulo 180°.

   The layer that drops the updates is a hypothesis (above), not a measurement. Block losses on the runner are
   unattributed (stall vs delivery). Real-hardware behaviour is untested.

## Known gaps

1. **No real tablet measured anywhere.** Windows numbers are synthetic and from a VM; macOS is pending the user.
2. **The macOS native path has never received input.** Accessor gating is checked against the reviewers' contract
   doubles, not AppKit. Still unverified until the user's run:
   - coordinates: window points, bottom-left origin, nil-window events, 1×/2× backing, resizing, multiple displays;
   - tilt calibration (raw tilt is now logged next to the converted value);
   - eraser and button mappings.
3. **Raw HID report contents are not decoded** (needs `HidP_*` with the device's report descriptor).
   **E1 (open experiment for C0.4): observe the webview's own input boundary.** Within this round's constraints (no
   cross-process hooks, no subclassing) it is not feasible:
   - `GetPointerFrameInfoHistory` and the other pointer-info functions return data only for pointer messages that the
     calling thread retrieved;
   - the webview's input window and its thread belong to `msedgewebview2.exe`;
   - our top-level window would get at most a `WM_PARENTNOTIFY` at pointer-down, and only through a subclass.

   Candidates that respect the boundary:
   - a WebView2 DevTools-protocol trace of browser-process input events (CDP `Tracing` with the `input` /
     `latencyInfo` categories), aligned with injection times;
   - an elevated ETW Win32k input trace on the runner.
4. **Local Windows synthetic run blocked** by the pending Windows Security prompts. Once the user has dealt with
   them: `target/release/toontown.exe --spike tablet --spike-log tablet.json --spike-auto`.
5. **WebView2 DOM delivery (synthetic):**
   - no `pointermove` for non-position-changing and pressure-only updates, or for repeated-pixel frames;
   - early frames after the down are missing;
   - twist arrives modulo 180°.

   The responsible layer is not identified (E1).
6. **Spike-page drawing is per sample and not optimised.** It is a measurement tool, not the M4 canvas.
7. **The spike commands are registered in release builds** (gated by the launch flag, like `--ipc-bench`). Remove or
   dev-gate them with the other M0 diagnostics.
