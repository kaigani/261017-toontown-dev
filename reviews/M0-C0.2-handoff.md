## Hardware statement (read first)

- **This Windows machine has no pen or tablet hardware** (no pen/digitizer devices; `SM_TABLETPC` false). All Windows
  numbers below come from **synthetic pen input** (`CreateSyntheticPointerDevice(PT_PEN)` +
  `InjectSyntheticPointerInput`) and are labelled as such. They exercise the Windows pointer stack, WebView2 and
  Windows Ink with known values. They are **not** evidence about real tablet hardware or drivers.
- **No synthetic run executed on this machine's desktop.** Two **Windows Security** prompts (processes
  `PickerHost`, open since 2026-10-17 17:11 and 17:55) were still present when re-checked on 2026-10-18 before this
  round. Their topmost dimming layer covers the screen, so the injector's ownership check refuses to inject. I did
  not touch the prompts; they belong to the user.
- The Windows numbers were therefore measured on the **GitHub `windows-latest` runner**: a VM with 4 logical CPUs,
  no WebGPU adapter (`navigator.gpu` unavailable), WebView2 154.0.4258.62 and Windows 10.0.26100.33438 (all recorded
  in the log). The measurement runs as a non-blocking CI step (`ci.yml`, bundle job). Runner load affects some
  results.
- macOS: built, clippy-clean and unit-tested on CI, not exercised with input. **Pending user**:
  `docs/manual-tests/M0-C0.2-tablet-macos.md`.

## Measured — Windows, synthetic pen, GitHub runner (CI run 39111989749; matrix 1 = run 39111452505)

All numbers are printed by `python scripts/analyse-tablet-log.py reviews/evidence/M0-C0.2/tablet-spike-windows-runner-r1-matrix2.json.gz`.
Frame indices are 0-based; each run injects 1024 contact frames plus 10 hover frames before, an up, 10 hover
frames after and a final update (1046 injected frames in all).

|---|---|---|---|---|
| webview, sine | 970 (matrix 1: 966) | not observable: WebView2's input window belongs to `msedgewebview2.exe` | **0** (attached to the main window) | 1046 |
| webview, sine 500 Hz | 1000 (926) | not observable | **0** | 1046 |
| webview, zigzag, shifted rectangle | **1023** (1022) | not observable | **0** | 1046 |
| webview, stationary (pressure only) | **1** (1) | not observable | **0** | 1046 |
| plain native window, sine, RTS attached | n/a | frames 0 only (matrix 1: 0–22) | frames 1–1023 (matrix 1: 23–1023) | 1046 |
| plain native window, stationary, RTS attached | n/a | none (matrix 1: 0–16) | all 1024 (matrix 1: 17–1023) | 1046 |
| plain native window, sine, **no RTS** | n/a | **1024 / 1024** (1046 messages, 1046 history entries) | not attached | 1046 |
| plain native window, stationary, **no RTS** | n/a | **1024 / 1024** | not attached | 1046 |

What the matrix shows, for **synthetic input only**:
1. The **RealTimeStylus sees injected pen input on a plain same-process window**. On that window, RTS and
   WM_POINTER together account for every frame. Once RTS is attached it takes over the stream after a variable
   number of frames (0–23); WM_POINTER carries the frames before that. On the webview window, RTS saw **0** frames in
   every run. So the zero on the webview is not explained by "synthetic input is invisible to RTS"; it is consistent
   with the input being routed to the WebView2-owned child window.
2. **Raw input (HID digitizer page) received 1046 reports in every run, including during the webview runs**. That is
   one per injected frame, through a hidden same-process sink window, while the webview had the input. The device
   is `\\?\Microsoft HID RID\000D_0002\<n>`, a new instance per synthetic device. The report bytes are logged but
   **not decoded**: that needs the HID report descriptor. So the values (pressure/tilt) carried this way are
   unverified.
3. **Stationary pressure-only updates:** WM_POINTER on a plain window delivers all 1024; raw input sees all of them;
   the webview delivers only the pointerdown. They are therefore dropped inside the WebView2 process, between the OS
   pointer layer and the DOM `pointermove`. Which component does it (Chromium's input window or its event routing)
   is not identified.

No conclusion is drawn about real tablets from this. In particular, whether a real tablet driver exposes a digitizer
HID collection to raw input, with what permissions and values, and whether RTS on a dedicated overlay or child
window would work beside WebView2, needs one physical tablet (see "Findings").

### Four missing frames (reviewer's experiment)

The frames missing in every stroke of the v1 runs (0-based **92, 421, 604, 933**; the review's 1-based 93, 422,
605, 934) are exactly the four sine-path frames whose rounded screen position repeats the previous frame's. In the v2
runs:
- the sine strokes again miss exactly those four ("repeated-pixel frames 4, of them missing 4");
- the zigzag path in a shifted rectangle (no repeated pixel) misses none of them: 1023 / 1024 received; the one
  missing frame is frame 1, see below;
- the stationary stroke delivers only frame 0.

**Layer:** dropped inside WebView2, not by injection or the OS pointer stack (matrix point 3). For real tablets this
means a pen pressing harder or lighter **without moving** may produce no `pointermove` in WebView2. This is a web-path
risk to test with hardware.

Frame **1** (the first update after pointerdown) is missing in every v2 webview stroke of both matrices (trivially
in the stationary one). Cause not identified; it is not a repeated pixel.

## Findings for the C0.4 go/no-go (rewritten after review round 1)

1. **`octotablet` 0.1.0 has no macOS backend**, so it cannot be the macOS native fallback named in plan §2.3. The
   spike's macOS native path uses AppKit `NSEvent` directly through `objc2-app-kit` (already in the graph via
   Tauri), with every accessor gated on its documented event type. It has never received input: **pending user**.
2. **Windows native path (synthetic evidence only).** The runner matrix shows that RTS attached to the app's main
   window received no injected pen input over the webview, while RTS on a plain same-process window did. Raw-input
   HID reports reached a same-process sink in every run, with the webview focused. The report contents were not
   decoded. This does **not** show that an in-process listener cannot see real pen input. It also does not show
   that raw input carries usable pressure/tilt from a real tablet, or that the main-window RTS fails for real
   hardware. Synthetic injection is not documented to behave like a driver in either respect. The candidates to
   test with one physical tablet are:
   - raw input (`WM_INPUT` digitizer collection, decoded via the report descriptor);
   - RTS on a dedicated same-process window placed over the canvas;
   - for comparison, the ideas recorded earlier: composition hosting, which is not available in wry/Tauri today;
     an input overlay; wintab.

   Note `RegisterPointerInputTarget` requires UIAccess and redirects rather than duplicates input. No architecture
   choice follows from this checkpoint.
3. **WKWebView API surface is not tablet value delivery.** `getCoalescedEvents`, `getPredictedEvents`, `altitudeAngle`
   and `azimuthAngle` arrive in Safari/WebKit 18.2 (MDN BCD, WebKit release notes); pressure/tilt/twist properties
   exist since 13. That dates the API; it does not establish that a Mac tablet's pressure, tilt, twist or even
   `pointerType = pen` reach WKWebView. There is evidence pointing the other way:
   - Wacom's Safari results report no pen pressure in Safari 15 on macOS 12.1;
   - current Mac WebKit derives mouse-event force from `NSEventTypePressure` (Force Touch) in `WebEventFactory.mm`,
     not from tablet pressure.

   The user's Mac run (web and native side by side, with OS/WebKit/tablet/driver recorded in the log) is the
   measurement. **ADR-0005 stays at macOS 12.0 / Safari 15.0**; any floor change remains the user's decision, after
   that measurement.
4. **WebView2 web path on Windows (synthetic input):**
   - pen type, exact tilt, twist and a pressure grid of 1024 levels are delivered;
   - coalesced events are available and used (p50 4 samples per dispatch);
   - the event timestamp is within ~0.1–0.4 ms of injection (p50), and the handler runs one frame later (oldest
     sample p50 13.9 ms; newest 2.1 ms).

   Two delivery defects are reproducible:
   - **pressure-only updates at a stationary position are dropped**, as are frames at a repeated pixel;
   - the first update after pointerdown is dropped.

   Block losses on the runner are unattributed (stall vs delivery). Real-hardware behaviour, including whether a
   real pen at rest produces stationary updates, is untested.

## Known gaps

1. **No real tablet measured anywhere.** Windows numbers are synthetic and from a VM; macOS is pending the user.
2. **The macOS native path has never received input.** Accessor gating is checked against the reviewers' contract
   doubles, not AppKit. Still unverified until the user's run:
   - coordinates: window points, bottom-left origin, nil-window events, 1×/2× backing, resizing, multiple displays;
   - tilt calibration (raw tilt is now logged next to the converted value);
   - eraser and button mappings.
3. **Raw HID report contents are not decoded** (needs `HidP_*` with the device's report descriptor).
4. **Local Windows synthetic run blocked** by the pending Windows Security prompts. Once the user has dealt with
   them: `target/release/toontown.exe --spike tablet --spike-log tablet.json --spike-auto`.
5. **WebView2 drops** stationary pressure-only updates and the first update after down (synthetic). The responsible
   component is not identified.
6. **Spike-page drawing is per sample and not optimised.** It is a measurement tool, not the M4 canvas.
7. **The spike commands are registered in release builds** (gated by the launch flag, like `--ipc-bench`). Remove or
   dev-gate them with the other M0 diagnostics.
