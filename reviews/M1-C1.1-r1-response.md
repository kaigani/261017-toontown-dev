## P1

### C11-R1-01 — duplicate split entries — **fixed** (`eedbbf4`)

`Document::assemble` now builds its entry maps with a duplicate check. When an entry ID is given twice, the first
entry is kept and an `id.duplicate` error issue names the dropped entry. `from_parts` fails on that issue. The
issues come from `Document::issues()` before any other check, so C1.3's repair (10 §7.2) gets every duplicate,
not only the last one. `crates/model/src/document/mod.rs` (`assemble`, field `assembly`).

### C11-R1-02 — the validated constructor accepted schema-invalid entities — **fixed** (`eedbbf4`)

`Document::from_parts` no longer trusts its parts. Every entry goes through `object::revalidate` (= `from_json` of
`to_json`): the depth limit, input normalisation, the full schema (so `minSize: 101` is rejected), the canonical form
and the object-local rules. Errors carry `details.objectId`. `assemble` stays the explicitly unchecked load/repair
API. Cost: the 121 092-object scale document now takes 1.25 s to `from_parts` (it was 0.14 s), measured in
`reviews/evidence/M1-C1.1-r1-response/`. For that reason the C1.2 executor must derive snapshots by revalidating
only the entries a transaction touched. ADR-0010 §4 records this.

### C11-R1-03 — opaque data interpreted, rewritten and dropped from diffs — **fixed** (`eedbbf4`)

- The recursive name pass is gone. The new `tt_model::input` follows the type's generated schema, resolving `$ref`s,
  alternatives and the `if` branch the value selects. It normalises only declared positions. Opaque values (`meta`,
  every `ext` namespace, `importOptions`, anything whose schema declares no structure) are never interpreted. No
  string inside them changes and no embedded `type`/`name` is read. The only change is that object keys are put in
  lexicographic order (C11-R1-06), which does not change a JSON value. The reviewer's
  `{"type":"element","name":"  é  "}` comes back unchanged from both `meta` and `ext`.
- `change::diff_json` treats an array as a child collection only at the type's declared child-list slots (`slots_of`,
  `Split`/`Inline`). Every other array is an ordinary value, so the `meta.items` edit becomes a `replace` that applies.

### C11-R1-04 — inversion and elision lost data — **fixed** (`eedbbf4`)

- An `add`, `move` or `copy` that overwrites an object member carries the overwritten value as `oldValue`. `apply`
  checks it: a mismatch is an error, and so is an `oldValue` on an array insertion, which overwrites nothing. Its
  inverse puts the value back: add/copy → `replace`; move → `move` back + `add` of the old value.
- `apply` refuses an elided operation (10 §2.6: the consumer rereads). It also refuses an `add`/`replace`/`test`
  without a value, a range replace without `value`/`oldValue`, and a root `move`. It never writes `null` for a
  missing value. `invert` keeps the elided flag, so the inverse of an elided patch is refused as well.
- RFC 6902 root `add`/`replace` (`path: ""`) replaces the document. Whether `doc.object.patch` may replace a whole
  object is a command decision for C1.2 (ADR-0011 §7).

### C11-R1-06 — canonical JSON depended on insertion history — **fixed** (`eedbbf4`)

The input pass writes object keys in schema order. The keys of maps (`paletteStyles`, swatch `values`,
`channels`, untyped `params`) and of every object inside opaque values go in lexicographic (code point) order,
recursively. `from_parts` revalidates every entry, so the order is a pure function of content for every validated
object and document. Swatch values are no longer sorted into style order, which only existed for a palette, not
for a standalone swatch. The palette rule now checks "exactly one value per style". ADR-0011 §3 replaces the old
"stored order is document state" rationale. JSON-02 does not cover map keys, so this is recorded as SI-014. One
golden entry changed (an `ext` object's key order).

### C11-R1-07 — the Rust text path rounded large integers — **fixed: typed error** (`eedbbf4`)

The ruling allows "lossless or typed error". The new `tt_model::json_text` reader, which `from_wire_json` uses,
accepts an integer literal only when it fits `i64`/`u64` or is exactly a double. Any other literal, such as
`-18446744073709551615`, is `arg.invalid` with `details.offset` and is never rounded. Lossless `Value`s would need
`serde_json`'s `arbitrary_precision`, which changes number handling workspace-wide and breaks the untagged model
enums (`SwatchValue`, `DynamicParam`), so it was not adopted. Accepted doubles that are exact integers from 2^53 to
1e21 are now written as their exact digits, e.g. 2^64 as `18446744073709551616`. Every accepted literal therefore
round-trips byte for byte, and both writers agree; `numbers.json` changed in the 7 affected vectors.

**Test amendment (per ruling, as in C01-R1-04):** W `opaque_json_integer_outside_u64_is_not_silently_rounded` keeps
the reviewer's lossless assertion whenever the text is accepted. If the text is rejected, the error must be the
typed `arg.invalid`. Rounding still fails the test. The amendment is commented in the test.

### C11-R1-08 — conditional schemas broke large-double readback — **fixed** (`eedbbf4`)

`coerceNumbers` collects every schema that applies to a container: `allOf`/`anyOf`/`oneOf` members and the
`if` branch the container selects, evaluated once per container. A member is coerced when any of its schemas asks
for a double. The drop-shadow `origin.x = 1e20` is certified. A value with no `bigint` is returned unchanged, with
no schema walk. This also made the reviewer's 10 MB TypeScript validation faster: **1 054 ms**, against 1 871 ms in
the review run (uncontrolled comparison; `ts-10mb-drawing-node.log`).

### C11-R1-09 — accepted objects deeper than the writer's limit — **fixed** (`eedbbf4`)

The limits nest and are enforced where data enters:

- objects: at most 100 levels at model input (`input::MAX_MODEL_DEPTH`, checked first in `from_json`, so also in
  `from_parts`), giving `doc.limitExceeded`;
- text: both readers (Rust `json_text`, front-end `parseWireJson`) accept at most 128 levels, the same count on both
  sides;
- writers: the canonical writer and `canonical::to_value` allow 128 levels below the root.

An accepted object can therefore always be written, wrapped in a reply and read back. The front-end `MAX_DEPTH`
went from 64 to 128.

### C11-R1-16 — non-finite numbers serialised as null — **fixed** (`eedbbf4`)

`canonical::to_value` runs a non-allocating `Serializer` (`canonical::check_finite`) before `serde_json::to_value`.
It rejects NaN/±∞ in any `f32`/`f64` as `arg.invalid` and nesting beyond the writer limit as `doc.limitExceeded`.
`canonical::to_canonical`, `object::to_json` and `wire::to_wire_json` all use it. The front-end writer already
rejected non-finite numbers.

### C11-R1-20 — cloned ID generators duplicated IDs — **fixed** (`eedbbf4`)

`IdGenerator` keeps its monotonic state in `Arc<Mutex<…>>`, and `Clone` returns a handle to the same sequence. IDs
drawn through any clone, from any thread, are distinct and increasing in drawing order. The type stays `Clone` (the
review test clones it). A poisoned lock is recovered (every state update happens after the last fallible step, so the state is always
consistent), so there is no panic path. New unit test: `clones_share_one_sequence` (system and seeded).

## P2

### C11-R1-10 — deep library paths unusable — **fixed** (`eedbbf4`)

Paths may have `MAX_SEGMENTS = MAX_MODEL_DEPTH` (100) segments and 64 KiB. Every accepted object is at most 100
levels deep, so its canonical path is always within the parser's limits. The 34-folder leaf resolves.

### C11-R1-11 — stubs vs. schemas — **fixed** (`eedbbf4`)

Every object schema is now `if {required: [rev]} then {full requirements and kind rules} else {only
id/colourId, type, name}`, together with its `const` type (10 §2.2 "a full object always contains `rev`"). Child
slots reference the child type itself instead of the shared `Stub`. A depth-0 result validates, and a `scene` stub in
the `palettes` slot is rejected. The schema sweeps of the review pass on the new structure: top-level `required`
removal, unknown keys, wrong types, nested closed objects through `then`, and derived properties.

### C11-R1-12 — swatch `id` alias — **fixed** (`eedbbf4`)

The input pass maps `id` → `colourId` before validation. If both are present and equal, they are kept as one. If
they differ, both are left in place, and the schema then rejects the unknown `id`, so contradictory IDs never pass.

### C11-R1-13 — annotations — **fixed** (`eedbbf4`)

Every property of every definition carries `x-since: "1.0"`. The envelope `type` is `readOnly: true`.

### C11-R1-14 — `int` bounds — **fixed with the spec's bounds** (`eedbbf4`)

10 §1.1: "`int` | number (integer) | 32-bit signed range unless stated". Integer fields typed `u32` in Rust (frames,
durations, counts, loops, indices, derived lengths) are bounded by 0/1…2 147 483 647 (2^31 − 1). The stated
exceptions keep their range:

- revisions and byte sizes are 64-bit (10 REV-01, §5 entries over 4 GiB);
- the particle seed is 0–2^32 − 1 (06 §3.8.3, "Seed (0–2^32−1)"), now an explicit `maximum`.

### C11-R1-15 — NFC beyond names — **fixed** (`eedbbf4`)

Every string at a declared position is NFC-normalised (the element note `é` becomes `é`). Strings inside
opaque values are left untouched (C11-R1-03).

### C11-R1-17 — Rust and TypeScript disagreed on hostile JSON — **fixed: one shared corpus** (`eedbbf4`)

- Rust: `tt_model::json_text` checks every request text before `serde_json` reads it (`disable_recursion_limit`, since
  the check bounds depth with the front end's count). It rejects duplicate keys after unescaping, unpaired
  surrogates, depth > 128 and inexact integer literals.
- TypeScript: `parseWireJson` additionally rejects unpaired surrogates, escaped or raw, and integer literals the
  engine could not hold. `stringifyWireJson` refuses to write unpaired surrogates.
- `tests/fixtures/wire/hostile-json.json`, generated by `make-hostile-json.py` beside it, contains 61 texts both sides
  must reject, 24 texts both must accept and write identically, and 4 invalid UTF-8 bodies. It is run by
  `crates/engine/tests/wire_corpus.rs` and `desktop/src/ipc/wireCorpus.test.ts`, and both pass. The corpus records the
  shared depth limit, and each side asserts it against its own constant.

### C11-R1-18 — validator pin — **fixed** (`eedbbf4`)

`jsonschema` was upgraded to 0.59.0 (default features off). `MIT-0` is on the single allow-list in `deny.toml`,
`tests/adversarial/guards.mjs` (approved list; MIT-0 removed from the rejected controls, with a comment citing the
ruling) and ADR-0003 (amended). The review's `multipleOf` test is ported to the 0.59 API
(`jsonschema::options().with_draft(Draft202012).build`) with a comment; schema, draft and both assertions are
unchanged, and it passes. All conformance, property and schema-sweep tests pass on 0.59. The vello dependency audit
was regenerated (`scripts/audit-vello-deps.py`; c03-r1 tooling test green). Performance is recorded below.

### C11-R1-19 — `property_schema` traversal — **fixed** (`eedbbf4`)

The lookup resolves `$ref`s and searches `anyOf`/`oneOf`/`allOf` members and both conditional branches for the next
token. It follows `prefixItems` for tuple positions, `items` for other array positions and `additionalProperties`
for map keys. `/channels/rotation/keys/0/value` and `Stroke /points/0/0` (`number`) resolve.
