## Finding

| Item | Status | What changed | Commit | Proving tests |
|---|---|---|---|---|
| C14-R4-01 (C14-R3-02, `expectRev`) | fixed as ruled | See below. | `b16a39a` | reviewer: `c14_r4_closure.rs::group_accepts_a_matching_expect_rev`, `::group_expect_rev_is_supported_and_conflicts_atomically`; builder: `crates/mcp/tests/c14_r4_expect_rev.rs` (3 tests) |

**Cause.** In round three, ADR-0015 §13 said the group step had `expectRev` "exactly like `batch {atomic: true}`".
But `BatchRequest` had no `expectRev` at all. The group's params are parsed as a batch with `deny_unknown_fields`, so
`expectRev` was refused as an unknown field, whether it matched or not. My round-three claim about this was untested
and false.

**Fix.** `BatchRequest` gains an optional `expectRev` (`{ref: rev}`; omitted from the serialized form when empty). The
`batch` tool, `--run` scripts and group steps share it and run the same code:

- **Schema.** `expectRev` is in `BatchRequest` and in the `batch` tool's `inputSchema`, with the same shape as on
  `run_command`. The group step takes the batch's params, so a group's `params` accepts it too.
- **Execution** (`Core::batch_atomic`, which runs both atomic batches and groups). The precondition is checked once,
  with the single-command `check_expect_rev`, before the first step and against the state the transaction starts
  from:
  - **match:** the steps run as one transaction and one undo step, unchanged;
  - **mismatch:** the whole transaction is refused with `rev.conflict` (`details.currentRev`, `expectedRev`), with
    no step run and nothing changed. In a script, that is the group step's error, so the outer sequential batch
    reports `batch.stepFailed` with `details.error.code: "rev.conflict"` and `stopOnError` applies.
- **Sequential batches** refuse `expectRev` with `arg.invalid` (`pointer: /expectRev`). They commit step by step, so
  one precondition would guard only the first commit. The hint points to an atomic group step.
- **Export.** A committed atomic batch whose call carried a non-empty `expectRev` is written as a group with the same
  `expectRev`. Replay reproduces revisions, so the precondition holds again on the same initial document.
- **Docs.** ADR-0015 §14 (new), the agent guide (`app://docs/guide`, "Act"), SI-051 (round 4) and a traceability row.

Nothing else about groups changes: label, one transaction, one undo step, relative references, `batch.nestedGroup`
and the `atomic: false` refusal stay as before.
