## Findings
### C52A-R2S-01 - P2 - Delayed read restores an earlier generation
Citation: E-70 and E-71, reviews/M5-C5.2-plan.md section 17:
nothing of an earlier generation answered or announced after replacement.
Path: crates/executor/src/host.rs:875-892 takes snapshot on document
thread, then calls Service::read on caller thread; thumbnails.rs:181-196
unconditionally follows any unequal generation, including an older one.
Concrete sequence: request A's drawing; pause caller after snapshot returns
at host.rs:891. Close A and create B on a second caller; flush at lib.rs:1087
sets service to 0 then B. Resume A's caller. Its read sets service back to A,
queues A's drawing, and worker accepts/announces it because service is now A.
Thus a closed project's drawing is announced after B's creation completed.
No further document request is needed for the worker to finish.
Correct: a stale snapshot cannot change current generation or queue work;
generation ownership must remain with project installation. Reject stale
reads under the same synchronization used for replacement.

### C52A-R2S-02 - P2 - Notice publication escapes generation protection
Citation: E-71, reviews/M5-C5.2-plan.md section 17: nothing of an earlier
project generation is announced once the project is replaced.
Path: crates/executor/src/thumbnails.rs:277-299 checks generation and
updates cache under state lock, then 300-307 broadcasts outside that lock.
Concrete sequence: worker completes A, passes line 281 and releases lock
at 299; pause it before 300. Close A, create B and let both replies finish
(lib.rs:1087 follows generations before replies). Resume worker: it sends
shell.thumbnailsReady for A while B is open, with no second check.
Correct: completion publication must be serialized with generation change,
or delivered through a generation-aware dispatch that rejects stale notices.
A second unlocked check alone still leaves the same check/send race.
