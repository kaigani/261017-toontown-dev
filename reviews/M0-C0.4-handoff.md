## Diagnostics gating — how to verify

**One switch.** The Cargo feature `m0-diagnostics` (tt-desktop) and the Vite define `__TT_M0_DIAGNOSTICS__` (true in
build mode `diagnostics` and in tests) are switched on together by `desktop/src-tauri/tauri.diagnostics.conf.json`:
`build.features` plus `beforeBuildCommand: pnpm build:diagnostics`.
- `desktop/src-tauri/src/lib.rs` declares the commands with one `command_registry!` list per build. Each list
  generates both the Tauri handler and the `COMMANDS` const.
- `spikes/` and the bench commands are compiled only with the feature. Unit tests always compile `spikes/`, so its
  tests keep running.
- A default build given `--ipc-bench` or `--spike` stops with `DesktopError::DiagnosticsNotBuilt`. The message is
  "`--ipc-bench` is an M0 diagnostic and this build has none; …", with exit status 1.
- In the front end, the default bundle drops the spike pages, the spike/bench API (`spikeApi.ts`) and the mock's
  diagnostic handlers (`mockDiagnostics.ts`). The spike schemas are annotated pure so that their module is dropped
  too.

**Commands.**

```sh
cargo test -p tt-desktop --locked                                  # default_build_registers_no_diagnostic_commands
cargo test -p tt-desktop --locked --features m0-diagnostics        # diagnostics_build_registers_the_m0_commands
cargo clippy -p tt-desktop --all-targets --locked --features m0-diagnostics -- -D warnings
pnpm --dir desktop exec vitest run --config vite.config.ts src/diagnostics/gating.build.test.ts   # bundles both modes
pnpm --dir desktop build && pnpm --dir desktop build:diagnostics   # both pass the IPC boundary dist check
cmd //d //c "pnpm --dir desktop tauri build --no-bundle -- --locked"
python scripts/check-diagnostics-gating.py target/release/toontown.exe --expect default        # 0/12 names
target/release/toontown.exe --ipc-bench out.json                   # refused, exit 1, no file written
cmd //d //c "pnpm --dir desktop tauri build --no-bundle --config src-tauri/tauri.diagnostics.conf.json -- --locked"
python scripts/check-diagnostics-gating.py target/release/toontown.exe --expect diagnostics    # 12/12 names
target/release/toontown.exe --ipc-bench "$PWD/out.json" --ipc-bench-count 50                   # frontend.ok = true
```

Locally (Windows 11) these give:
- the default build: 0/12 diagnostic names, both flags refused;
- the diagnostics build: 12/12 names, and a real `--ipc-bench` run with `frontend.ok = true`.

**CI.**
- The bundle jobs first build the default bundle. They scan it (`--expect default`), check that both flags are
  refused, and keep it in `out/default-build/`.
- They then build the diagnostics variant (`--expect diagnostics`), which runs the IPC benchmark, the tablet and
  canvas spikes, and is the top-level `desktop-<OS>` artifact used by the manual tests. The three macOS manual-test
  scripts now say so.
- The check jobs build both front-end variants (each with the dist check), and lint and test the feature build.
