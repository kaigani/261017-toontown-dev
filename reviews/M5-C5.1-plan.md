## 6. The Timeline view

### 6.1 Sizes and rendering

Sizes the spec states: at least 1,000 elements per scene (10 §5 line 666), frames to 9,999 in every cell parameter
(04 §13.4-§13.6) and scenes to 100,000 frames (the 10 §5 limit the kernel enforces), drawing banks of 10,000 (10 line
667). At 1,000 rows by 9,999 frames nothing can be one DOM node per cell or per row:

- **Layer list:** DOM, virtualised: only the rows in view plus a margin exist (about 40 at the default row height).
- **Ruler and tracks:** one 2-D canvas each, redrawn for the visible window only (rows in view × frames in view), with
  device-pixel scaling. The WebGL back ends of the drawing views are not needed: a frame of the tracks is at most a few
  thousand rectangles and glyphs.
- **Reads are windowed:** `timeline.rows.list {from, to}` for the visible frames (bars and keyframes clipped to the
  window), `element.get` for the visible rows only, `xsheet.exposures.get {elementIds, from, to}` for the visible cells.
  A scroll that leaves the margin reads again; every read goes through the surface's read gate.
- **Zoom:** a ladder of cell widths from `timeline-layout.json`; below the narrowest readable width one cell covers 2, 5
  or 10 frames (04 line 650); the zoom control, the wheel over it, and View › Zoom In / Out with the Timeline focused
  (01 §6.5) send `timeline.view.set {zoomLevel}`.

### 6.2 Budgets (D-33 form; D-45 for CI)

| Quantity | Bound (workstation receipt, release, 30 samples, 60 Hz with the D-33 control) | CI shape |
|---|---|---|
| Work per frame while scrolling, zooming and dragging on 1,000 rows × 9,999 frames (200 pegs keyed every 4 frames) | p95 ≤ 8 ms; ≤ 1 % of intervals over twice the control median | Vitest: the draw of the 1,000-row scene ≤ 3 × the 10-row scene's (fake 2-D context, operation counts, not time) |
| `timeline.rows.list` for a 120-frame window, 1,000 elements | ≤ 20 ms p95 | ratio to 10 elements ≤ 150, ceiling 200 ms |
| `xsheet.exposures.get` for 60 rows × 200 frames | ≤ 5 ms p95 | ratio and ceiling 50 ms |
| Click to the selection drawn; wheel to the scrolled repaint | ≤ 2 display frames p95 (the control median times two) | — |
| Release to the committed frame (bar move, row reorder, cell move) | ≤ 50 ms p95 | ceiling 1 s |
| Playback at 24 fps, Force Frame Rate off, sample scene | every frame of the range presented; interval p95 ≤ 1.5 periods | stepped clock: every tick advances one frame, the range and loop rules |

**Equivalence (D-32).** Three ways per row: the window's command and resulting document equal the direct command's
exactly; the headless replay of the window's recorded samples through `timing_gesture::to_command` with the window's
own layout gives the same command, compared exactly (the layout is the window's, so no tolerance applies). There is no
`pointer` form for the Timeline: 11 §6.4 line 354 addresses views (SI-205, question 7).

### 6.4 Selection model (Timeline, Exposure Sheet, views)

The kernel's contexts (01 §6.4 lines 573-580): `drawing`, `staging`, `timeline`, `xsheet`, `functionEditor`,
`library`, each with its own selection. `cell.select` writes the `xsheet` context and mirrors it into `timeline`
(`commands/cell.rs:1911`): one cell selection, as 04 line 694 requires. `element.select` writes the Timeline's rows and
mirrors them into `staging` (`commands/element_read.rs:542`): a row selected in the Timeline is the element selected
in the Camera view, and the reverse (04 line 692). The current element and frame are one position for every view (04
line 671). The edit commands act on the focused panel's context (`resolve_edit_context`): with the Timeline focused,
rows or cells as `cell.selection.get`'s `rowsSelected` says; Deselect All clears that context, and an Exposure Sheet
cell selection too (04 §12.5 design decision). The window never keeps a selection of its own: it draws
`cell.selection.get` after `cell.selection.changed` and `edit.selection.changed`. "Selection always visible" already
keys on these selections (D-85).

### 6.5 Keys

The single-key defaults of 04 §16 and 09 line 104: previous / next frame and drawing exist (`,` `.` and Shift);
Play / Stop (Enter, Shift+Enter) exists; added in the keymap default: Add / Remove Exposure, Insert / Delete Blank
Cell, Set Exposure 1 / 2 / 3, Extend Exposure (C5.2, the commands' checkpoint), Previous / Next Element, Show Timeline
Selection (C5.1). Arrow keys in the Timeline move the current cell (rows and frames). The text-field key rule (D-69,
D-73) applies to the in-place rename editor.

## 8. Interactive playback (C5.1a kernel, C5.1b window; question 1)

The playback clock advances the current frame at the playback rate within the playback range (09 §2.3-§2.8), stops at
the range end or wraps with Loop, stops on navigation and on a scene change (09 lines 137-138, 210), and with Force
Frame Rate skips frames to keep real time. `timeline.currentFrame.changed` is throttled to 10 per second during
playback (04 line 1466); the window's views follow every frame through a host-only notice carrying what
`playback.state.get` answers (D-57; never sent to an MCP client, tested; SI-207). Sound is M8; capture pause is M10.

## 9. Test strategy

- **Kernel (C5.1a):** per command its examples under the watchdog (existing harness) and a test of every parameter's
  effect through the real path (D-27); the overlapping pairs proven to share one state and raise the same event
  (SI-202, SI-203); the playback rules on the stepped clock (range, loop, rate, force rate, stop on navigation, scene
  change); the interpreter's D-23 table, every row with its spec line, including rows that must make no step; the
  headless replay equal to the direct command; prechecks resolving targets as handlers do (a matrix over every command
  and target kind); availability inventory rows (`scripts/check-availability-inventory.py`); the CI shapes of §6.2.
- **Vitest (C5.1b):** geometry (frame ↔ x at every zoom step, frames per cell, the visible window, hit tests at bar
  edges and handles), the virtualised list, the draw on a fake 2-D context (operation counts), each menu model (items,
  availability, the command each sends, disabled with reason), each dialog through the modal manager, the read gates
  (an older read answering after a newer one), an agent's change reflected per control, the keys.
- **Parity:** the collector renders the Timeline in every state (no project; rows; each context menu; each dialog;
  collapsed parent; a drag in progress), so every action is in the manifest; `reads.json` declares the panel's reads.
- **D-39** (one row per control, MCP form in CI, OS form on the workstation) for every Timeline control, menu item and
