## 6. Known limits, in plain words (tickets for M11 C11.1, ruling E-44)

- **On a large animated scene every change takes about half a second to commit.** On the plan's §6.2 scene (1,003
  rows; 200 pegs with 100 keys each) any document change, a Timeline bar move or row reorder, a rename, a lock, an
  undo, takes 450 to 520 ms (release, p95: bar move 483 ms, row reorder 519 ms, against the Timeline's 50 ms budget;
  receipt `reviews/evidence/M5-C5.1b/budgets-kernel.json`; in round 1 a cell move that changes cells, 510 ms,
  `reviews/evidence/M5-C5.1b-r2/budgets-kernel.json`). The same rows without keys commit in 6 ms. The Timeline's
  own part is under a millisecond (press 0.8 ms, the interpreter's replay 0.9 ms). Diagnosis: the model's staged commit
  (`Document::with_patched_entries`, M1 C1.2) rebuilds the derived data and runs the whole document's integrity check
  (`Document::issues`, which walks every element's keys: 266 ms alone); the executor adds about 200 ms. The fix checks
  the entries a commit touched and the rules that cross entries, not the whole document.
- **Each recent revision keeps its own copy of the document's index.** Every commit rebuilds the document's derived data,
  its object index included (`Document::rebuild_derived`, M1 C1.2), and the revision log keeps the `before` document of
  each of the last 256 revisions while their changed objects fit its budget (`SNAPSHOT_WINDOW`, `SNAPSHOT_OBJECT_BUDGET`,
  which weighs the objects a change touched, not the index each snapshot holds). On the sample with a 20,000-stroke
  drawing, 300 note changes hold about 3.1 GB (about 10 MB per change; measured locally with
  `crates/executor/tests/c52a_history_size.rs` at 20,000 strokes, which runs with 1,000 in CI; found while measuring the
  history for ruling E-70). The same rebuild is the commit cost above; the fix shares the index of
  the entries a commit did not touch. Outside the undo history's bound, which counts its steps only (measured with it:
  a patch step holds about 4.7 times the size the bound counts, and a snapshot step holds the entries it shared with the
  live document once later edits replace them there: 24 MB counted as 6 KB in that test).
- **Keying many nodes slows down as keys accumulate.** `anim.key.add` on 200 pegs at one frame takes about 1.2 s with
  no keys yet and about 10.8 s with 75 to 100 keys on each peg (release). Each addition costs in proportion to the keys
  already on the curves it touches (the commit above, plus the undo record below).
- **The undo history's memory grows with the square of the keys added.** A key added to a curve changes the length of
  its key list; keys carry no `id`, so the model's diff (`crates/model/src/change.rs`, `diff_into`) replaces the whole
  list, and the step keeps every touched curve's list before and after. A step's size is proportional to the keys
  already on the curves it touches, so n additions hold memory proportional to n squared: building the §6.2 scene with
  2,500 key additions on 200 pegs in one history reached 20 GB. What bounds it today: a level limit of 1,000 steps
  (`crates/executor/src/history.rs`, `MAX_STEPS`, the oldest discarded first) and no memory bound. 01 §6.1 asks for
  "at least 200 steps; SHOULD be unlimited subject to a memory bound, discarding the oldest steps first": the step
  count is met, the memory bound is missing (its ruling is outside M11: the C5.1b round 1 response).
