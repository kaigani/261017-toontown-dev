## C44B-R3S-01

Rule: lock design I3; D-84 requires I3 with other handles open.
Location: crates/persist/src/lock.rs:519-531, 624-658, 933-946.
Input/order (Windows): a stale project lock and an abandoned, token-bearing
.takeover file. F opens the latter read-only, sharing read/write/delete, and
keeps reading through its handle. A opens the project, successfully opens the
abandoned arbiter with DELETE_ON_CLOSE and closes that proof. The arbiter name
is now delete-pending until F closes. A retries; every create gets access denied;
folder_writable succeeds. Its two-second round expires: state is stale, probe
of the pending arbiter cannot open it, and the folder is writable. A starts
another round. Repeat forever with A running and F retaining its read handle.
B, C and D can join and repeat exactly this decision. No holder exists.
Expected: exactly one opener acquires the stale project under I3.
Deduced: no owner and no result, for arbitrarily many rounds, even though F
has no ownership role. The design note section 4.1 silently adds the condition
that the foreign handle eventually closes; I3 does not contain that condition.
Smallest fix: provide a safe name-freeing protocol for abandoned arbiters too,
with identity-bound removal/rename and serialization of competing proofs.
Do not simply enable the existing by-name aside rename for multiple provers.

## C44B-R3S-02

Rule: D-85 item 2, every surface reads current session state on mount;
01 section 12.1 rule 9, show agent acting while its command runs.
Location: crates/executor/src/host.rs:180-199;
crates/executor/src/commands/app.rs:67; desktop/src/state/store.ts:120,198-209.
Order: agent starts a long request; host broadcasts acting=true before the
window store subscribes. Mount the window during that request. The store starts
with acting=[]; app.state.get reports acting=false; no replay/query supplies
the active request. Until the command ends, the indicator falsely shows idle.
The final acting=false event cannot repair the missing interval.
Expected: the mounting indicator shows the current active request.
Deduced: an event-only state with no current-state read loses it. The handoff
section 6 acknowledges this, but no ruling exempts the indicator.
Smallest fix: keep active requests in host state, expose a host snapshot and
subscribe before reading it, with sequence/version reconciliation.

## Project file lock

Orderings walked (protocol participants, except the explicitly named foreign reader):
1. A creates an empty helper and pauses before flock; R ages, proves and unlinks
   it; A locks its old inode. C2 rejects it; R or A retries and acquires. The old
   round-2 zero-owner ordering is impossible on Unix; Windows creation already
   has write access and prevents R's proof open.
2. Creator C gives up while prover P holds the empty helper's flock. C removes
   nothing; P unlinks its own proven inode. Another opener can publish.
3. Two reapers R/S compete for an abandoned helper. Unix exclusive flock makes
   proofs serial; identity rejects a delayed proof after unlink/replacement.
   Windows compatible proof handles bind deletion to the opened old file;
   pending deletion bars successors until those proof handles close.
4. Three openers R/D/W: delayed R cannot unlink D's protected helper. With a
   test-forced removal of D's helper, W publishes first; D's removal proof is
   refused by W's protected project file. D never removes W's publication.
5. Four openers A/B/C/D plus live H: every project-file probe sees H protected;
   no stale-removal proof can obtain H's protection. They cannot replace H.
6. H heartbeat obtains arbiter, checks token, writes through its protected
   file, validates publication. Release obtains arbiter, checks token, removes
   while holding the file, closes it, then drops helper. Delayed takers cannot
   interpose a replacement between identity and unlink under Unix flock.
7. Unix inode reuse: an open proof/creator keeps its inode allocated, so the
   identity check cannot match a reused inode until that handle has closed.
8. Windows stale project file with a foreign reader: proof renames aside,
   freeing the name; delete-on-close deletes the aside when all handles close.
   Process exit immediately after rename closes the proof too. A second opener
   never scans aside names. Random suffix collision makes rename fail and
   retries; aside names persist only while foreign handles retain old files.
9. Windows abandoned helper with persistent foreign reader: finding 01. More
   openers do not help. The two-second limit bounds a round, not acquire.
10. Windows reader refusing delete on the stale project file: proof fails,
    ordinary read probe says free, so retry rather than false HeldByOther.
    Acquisition progresses after the reader closes. This is an external access
    restriction; case 9 instead involves a reader explicitly sharing deletion.

Unix I1: holds for cooperating protocol participants on locking file systems.
Unix I2: holds for cooperating protocol participants on locking file systems.
Unix I3: holds with fair progress and successful file operations.
Windows I1: holds for cooperating protocol participants on supported file systems.
Windows I2: holds for cooperating protocol participants on supported file systems.
Windows I3: FAIL with the persistent helper reader in finding 01.

Windows names() is a constant true, not volume/file-index comparison. Its
justification is exclusion of protocol removals by a live write handle; it is
not protection against arbitrary external unlink/rename (sharing delete permits
that). No new external-tampering safety claim is made here. Unix identity plus
flock prevents repointing by protocol participants between check and action.
HeldByOther reflects a sampled state, not an atomic promise at return: a holder
can release immediately after a probe. No protocol can promise otherwise.
NotWritable classification probes the folder for permission failures; write
failures through a newly protected publication are still reported as I/O errors.
Unsupported locking remains outside these guarantees, as documented.

## Case assessments
### S1 - FAIL
Protocol and both platform implementations read; finding 01 above.

### S2 - PASS
Named Schedule keys and armed/held/seen lists replace time-based ordering.
W's joined Acquired outcome and held() precede D's resume. Windows legacy
pending-delete has a separate test. Child-process termination covers the eleven
lock boundaries; process exit bypasses cleanup. Foreign-reader reproduction and
delete-refusing reader are present. Randomized outcomes retain every acquired
handle through all joins, requiring exactly one and that it remains valid;
thus any simultaneous acquisitions among these retained results fail the count.
Seed is in assertion diagnostics (success receipts print it in the loop runner).
The 60-second waits are hang guards, not performance measurements or schedule
ordering. The two-second rounds have no CI acquisition-time assertion.
Missing ordering: S1 case 9 with a persistent reader on the arbiter, rather
than on the project lock. Hooks are feature-gated by tt-persist/test-hooks;
without it boundary is a no-op. c13_r1_persistence.rs has no diff.
