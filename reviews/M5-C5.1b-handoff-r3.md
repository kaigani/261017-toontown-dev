**Does 200 ms for that preview point at a product cost?** Not at the 3,000 strokes: `draw.inspectorPreview.set` renders
nothing and reads no drawing (`draw_select.rs`: it stages one preference through `prefs::stage_stored` and returns). Its
cost is the preferences file's durable write inside the call (`tt-persist` `fsx`: a temporary file, `sync_all`, then a
rename over the target), which depends on the disk. That is read from the code, not measured: the call's only work is
that write and the commit around it, and a loaded runner's disk sync can plausibly pass 200 ms. That does point
at something worth a ticket, smaller than a drawing cost: **a preference change waits for a durable file sync on the
document thread**, so every command queued behind a toggle (the preview, a display option, a panel's state) waits for the
disk. Proposal for M11 C11.1, in the merge note's §6 when you agree: measure `prefs.set` on the workstation and a runner,
and, if a sync can pass the never-block budget, write preferences after the reply (the session's value is already the
new one; the write is ordered and durable before the next write or exit).
