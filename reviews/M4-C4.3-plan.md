## 3. Architecture

### 3.1 One rule, kept

Every change to the document goes through a registered command, from the window as from an agent; the window draws
locally and commits once (ADR-0007 decision 1). The Camera view adds no new path to the document.

### 3.2 The Camera view's composition (part A)

The camera is rigid (translation and roll only, 05 line 236), so a drawing on a plane facing it projects as a 2-D
similarity (scale by focal over depth, roll, translate) composed with the element's own transform chain; a node
rotated out of the plane projects as a plane homography. Either way the projection of a drawing occurrence is one
3×3 matrix, so the canvas keeps one resident geometry per drawing (C4.2b's TTRD payload, unchanged) and the scene
answer for a Camera view lists **occurrences**: drawing id, revision, form, a 3×3 matrix from drawing units to camera
output pixels, opacity, and its place in the depth order (05 §2.8, ties by Timeline order). The camera frame, pivots, the selection box and handles, and the current-on-top and
selection-display options (02 lines 946, 959-961) are overlay records drawn after the occurrences. A drawing shown
in several elements is uploaded once and drawn once per occurrence. Elements behind the near plane (0.1 field, 05
line 241) or hidden (visibility, ancestors) are omitted by the kernel's walk, which is the final renderer's camera
walk (`render_list`) in the colour-slot mode C4.2b added, so the two cannot disagree on what is shown. The Camera view
is not byte-bound (ADR-0006 decision 7); the byte gate keeps comparing exports.

TTRD's scene message gains an occurrence table (a minor version: TTRD 1.1, `docs/canvas-format.md` amended first;
1.0 decoders read 1.1 per the version rule, V1-V10 unchanged, new validation rules for the table).

### 3.3 Coordinates (part B)

One mapping function per view type in the kernel (the views note's V1), extended to the Camera view: view pixels ↔
camera output pixels (the view transform) ↔ scene (the camera's inverse at a given depth) ↔ a drawing's units (the
element's inverse full scene transform at the current frame). Scene space in the addressing parameters, in
`view.coordinates.convert`, in `inspect.hitTest` and in `pointer` uses it; a point in scene space addressed to a
drawing maps through that element's inverse transform (02 lines 66-73). `camera` space is SI-109's (fields from the
camera centre, roll applied). The canvas receives the matrices; it never recomputes the projection.

### 3.4 Tools in the Camera view (part C)

- **Scene tools (Select, Transform).** The kernel's gesture driver (`gesture.rs`) gains the Camera view: a press picks
  by 05 §3.5's priority within 4 view pixels (locked elements skipped); a click or rubber band ends in
  `edit.selection.set`; a drag past 3 px ends in one `anim.transform.set` (Select: `target: static`; Transform: keyed
  at the current frame, only the changed channels), X/Y converted to the node's parent space at its depth so the
  element stays under the pointer; the bounding-box handles scale, rotate (15° snap with the modifier) and skew;
  Transform adds the pivot. One drag is one undo step; Escape restores; arrow nudge 1 view pixel (×10).
- **Live feedback.** The window previews the drag locally (the occurrence's matrix updated per frame) and commits once;
  this is the first live transform preview (C4.2 deferred it for the Drawing view's Select; §14 question 6).
- **Drawing tools in the Camera view.** The same gestures as the Drawing view (C4.2), their samples mapped through the
  current element's inverse full scene transform into drawing units (02 line 61): one mapping, the same commands.
- **The scene tool and the drawing tool are separate** (05 lines 29-31): the Camera view's toolbar chooses between the
  scene tools and the drawing tools; §14 question 2 asks whether `anim.tool.set`/`get` are built now.

### 3.5 Renders and captures (part D)

`render.frame.run {composition: "activeView"}` with the Camera view active renders the camera composition with the
view's display quality (SI-107's interim, now resolved for the Camera view); its result names the view if SI-142 is
answered that way. `inspect.screenshot` of the Camera view: the window's capture attached (D-6, C4.2b), the virtual
Camera view headless (the SI-069 virtual view's size).

### 3.6 The parity gate (part E)

One UI-binding manifest for every GUI action, generated from the front end's declarations (`data-tt-command` on
every actionable element, the menu manifest, the tool rail, tool options, context menus, view chrome, panel actions,
the keymap's defaults), checked both ways against the registry in `check` (a Rust test reading the manifest) and in
Vitest (the manifest equals what the rendered UI tree exposes, so a button without a declaration fails). Every
registry command is bound in the manifest or declared `agentOnly` with its justification. The manifest and the gate
replace the menu-only test; the C4.1 test stays as a subset.

### 3.7 E6 (part F)

A running-application scenario on both CI OSes: a scripted user drags an element in the Camera view through the
window's real input path (OS input on Windows, the window-played pointer on macOS, as C4.2b's three-way); during the
drag an agent session's `anim.transform.set` waits; after the release it succeeds; the user then makes a later step;
the agent's `edit.undo {ifTop: <its step>}` answers `undo.notTop` and the user's step survives. Timings recorded; the
wait bounded by `waitForUserMs`.

## 4. Design notes before code (each pushed before its code; one builder test per invariant)

1. **`M4-design-camera-view.md` (new; amends the render-transport and frame-loop notes).** (CV1) the Camera view
   shows exactly the occurrences the final renderer's camera walk draws at the same frame, in the same depth order;
   (CV2) one resident geometry per drawing whatever its occurrence count; (CV3) an occurrence's matrix is the
   kernel's, never recomputed in the window (a homography's flattening tolerance is the view's, SI to record); (CV4) overlays (camera frame, pivots, selection) never reach a render.
2. **The views note, amended.** (V4) the Camera view's mapping round-trips view ↔ scene ↔ drawing within 1e-6 field at
   any depth in front of the near plane; (V5) the kernel and the canvas agree on every matrix (the canvas receives
   them); (V6) a click into a view window activates it, if §14 question 4 says so.
3. **The gestures note, amended.** (G7) a scene-tool gesture ends in exactly one command (`edit.selection.set` or
   `anim.transform.set`) or none; (G8) the window path, the headless `pointer` path and the command sent directly are
   equal for the Camera view (the three-way); (G9) a drag keys only the channels it changed; (G10) a drawing-tool
   gesture in the Camera view produces the same command as the equivalent gesture in the Drawing view.
4. **`M4-design-parity.md` (new).** (PA1) every GUI action is in the manifest; (PA2) every manifest entry names a
   registered command; (PA3) every registered command is bound or `agentOnly` with a justification; (PA4) the
   manifest is generated, never hand-edited.
5. **The busy-arbitration note, amended for E6.** (E1) an agent mutation during a user gesture waits at most
   `waitForUserMs` and succeeds after the release when the wait suffices; (E2) `undo ifTop` never undoes another
   origin's later step.
