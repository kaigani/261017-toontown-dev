## C02-R2-01 — analyzer accepts obsolete/incomplete evidence — **fixed**

`scripts/analyse-tablet-log.py`:
- **Versions.**
  - An explicit `version: 1` exits 2 with "log version 1 is obsolete (no raw injection report)…". The committed
    round-0 logs `tablet-spike-windows-runner-run{1,2}.json.gz` are now rejected; they stay as history.
  - Versions 2 and 3 are accepted; anything else is rejected.
  - A log **without** `version` is accepted only when it has no synthetic runs and no simulations, because the
    immutable round-1 reviewer fixture `test_C02_R1_03_*` is such a log. With synthetic runs it is rejected. This is
    the only legacy acceptance, and it is not used for any synthetic evidence.
- **Validation before any output.** `run_analysis` validates every run first, and `main` prints nothing until all
  runs have been validated and computed. A successful run needs:
  - its raw report (webview: `run.report`; native window: `probe.report` plus its `wmPointer`, `rawInput` and `rts`
    listener records);
  - every required report field. In v3 that includes the contact endpoints, their wall-clock pair and the focus
    snapshots;
  - per-frame arrays (`injectEpochMs`, `injectReturnEpochMs`, `pressure`, `tiltX`, `tiltY`, `rotation`, `screenX`,
    `screenY`) whose length equals `frames`, with numeric values;
  - a 4-element `screenRect`;
  - injected pressures equal to the identifying sequence `1 + (i mod 1024)`;
  - for webview runs, `environment.timeOrigin` and `webRange`/`nativeRange` inside the streams.
- **Three outcomes, stated in the output:**

  | Outcome | Handling |
  |---|---|
  | (a) explicitly failed run (`run.error` or `probe.error`, e.g. `spike.notForeground`) | analysed; the run table shows `**FAILED**: <error>` and the header counts ok/failed runs |
  | (b) no synthetic runs | analysed; prints "No synthetic runs: outcome (b), a manual/hardware log. There is no injection reference, so loss is "unknown, gap heuristic only"" |
  | (c) malformed or missing evidence | exit 2 with the reason on stderr, e.g. "successful run has no raw report (missing evidence, not an empty result)" or "raw report is missing fields […]". It is never a zero-loss row |

- **Tests:** the reviewer's three `C02-R2-01` methods (both subcases) and the failure/lossless controls pass. Mine
  (`desktop/src/spikes/tablet/analyzer.test.ts`) add v4 and v1 rejection, failed-run labelling, the missing-report
  refusal and the outcome-(b) wording.

## C02-R2-02 — `achievedHz` copied — **fixed**

- **Host (`simulate_windows.rs`).** The report now carries:
  - `contactStartNs` / `contactEndNs`: a monotonic `Instant` relative to a process anchor (`monotonic_ns`), taken
    before the first contact frame and after the last frame period;
  - the wall-clock pair `contactStartEpochMs` / `contactEndEpochMs`.

  `achievedHz` is now defined as exactly `frames · 1e9 / (contactEndNs − contactStartNs)`, so it can be reproduced
  from the log.
- **Analyzer.** It computes, prints and labels:
  - the **host estimator** from those endpoints (v3);
  - the **first-to-last estimator** `(frames−1)·1000/(last−first)` from the per-frame injection times.

  It **rejects** the log if the saved aggregate differs from the host estimator by more than 1e-9 relative (same
  formula, float noise only). Version-2 logs have no endpoints. For them it says "host estimator not reproducible",
  checks the saved value against first-to-last within a stated 1%, and rejects beyond that. The reviewer's
  regression (123456789 Hz) is rejected as `LogError`. My v3 test checks exact recomputation (250 Hz) and rejection
  of 251 Hz.
- **On CI** (matrices 3–5, v3), every run's saved value equals the recomputed host estimator. Both estimators are
  printed, e.g. matrix 5 sine 500 Hz: 499.235 / 499.309 Hz. The reviewer's `audit()` reproduces the first-to-last
  values.

## C02-R2-03 — experiment claims — **fixed**

1. **No measurement at WebView2's WM_POINTER boundary.**
   - The handoff now says "not measured" for WebView2's WM_POINTER.
   - It describes the raw listener as a hidden, page-wide background sink (`RIDEV_INPUTSINK | RIDEV_PAGEONLY`) whose
     1046 reports show what that listener received, not what the webview received.
   - "Loss is inside WebView2" is rewritten as a **hypothesis** about target-dependent delivery.

   **The suggested trace is not feasible under the stated constraints**, so it is left as named open experiment
   **E1** for C0.4:
   - `GetPointerFrameInfoHistory` and the other pointer-info functions return data only for the pointer message the
     calling thread retrieved;
   - the webview's input window and its thread belong to `msedgewebview2.exe`;
   - our top-level window would receive at most a `WM_PARENTNOTIFY` at pointer-down, and only through a subclass,
     which is excluded like hooks are.

   The handoff names two candidates that respect the boundary: a WebView2 DevTools-protocol trace (CDP `Tracing`,
   `input` / `latencyInfo` categories), or an elevated ETW Win32k trace on the runner.
2. **Geometry.**
   - The round-1 claim is corrected in the handoff: at 500 Hz the rectangle was `[16,151,1012,240]`, with no
     repeated pixels, and matrix 2 received all four indices.
   - Every run of a matrix now uses **one** rectangle: CSS 1012 × 275 from the canvas origin (the round-1 canvas size
     whose sine path repeats frames 92/421/604/933). Each run records it with the canvas rectangle at run time.
   - The page refuses with `spike.geometryChanged` if the canvas moved. That guard caught a header wrap in run
     39114898213. The header and status are now single-line, and the readout and run table have fixed heights.
   - Matrices 3–5 share `[16,109,1012,275]`. On it, both webview sine rates miss all four repeated-pixel frames
     (4/4 each, in all three matrices); the plain window receives them on the identical trajectory; zigzag has none.
3. **Pressure-only.**
   - A new `pressureOnly` pattern holds position, tilt (20/−10) and rotation (90) fixed. It ran in matrix 5:
     - webview: **1/1024** (the pointerdown);
     - plain window, WM_POINTER: **1024/1024**.
   - The `stationary` runs are labelled "non-position-changing updates (pressure, tilt and rotation vary)" in the
     handoff, and the analyzer prints each run's varying axes.

   Getting there needed two fixes, both in the log:
   - matrices 3 and 4 refused the webview pressure-only run because a WebView2 top-level `Chrome_WidgetWin_2` covered
     the canvas centre. That was the context menu opened by pen press-and-hold after the stationary stroke; refusals
     now name the covering window;
   - the canvas now suppresses and logs `contextmenu`. It fired once, at lift, in each stationary and pressure-only
     run.
4. **Foreground/focus.**
   - Every v3 report records, at the start and end of the stroke: `GetForegroundWindow` and its PID/class, and the
     foreground thread's `hwndFocus`/`hwndActive`/`hwndCapture` via `GetGUIThreadInfo`, with the focus PID/class.
   - The unsupported "with the webview focused" claim is removed.
   - The handoff now states what the log shows: the foreground window was the app's main window, and keyboard focus
     was in the WebView2 process's `Chrome_WidgetWin_1`, in every run. During native-window runs the probe popup was
     not foreground.
