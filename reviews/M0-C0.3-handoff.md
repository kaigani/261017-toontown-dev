### Estimators

Stated in the analyzer and the page:
- **frame interval** = consecutive rAF timestamps during pan/zoom; **fps** = (n−1)·1000/(last−first);
- **display refresh** = *mean* idle rAF interval. The median would be biased by WebKit's 1 ms timestamp rounding;
- **long frame** = interval > 1.5 × refresh;
- **target met** = fps ≥ 57;
- **CPU frame** = JS update + record + submit;
- **GPU frame** (WebGPU only) = submit → `onSubmittedWorkDone` (includes queueing behind presentation);
- **transfer** = `performance.now()` around one binary invoke (host encode + IPC + envelope check);
- **IPC-per-frame ceiling** = 1000 / p50 transfer: the frame rate if the whole list crossed IPC every frame;
- percentiles are nearest-rank.

What these numbers show:
- **Target: met.** 60 fps pan/zoom at 100 000 paths on this machine, with both WebGPU and WebGL2 (also with
  WebGL2 forced on its own). There were no long frames in ~600 per run. The
  display caps the rate. CPU frame time is p95 ≤ 0.3 ms and max ≤ 1.6 ms. WebGPU GPU time for 100 k paths is
  p50 8.5 ms, about 2× headroom under 16.7 ms.
- **IPC.** Binary `Response` transfers run at **128–172 MB/s** on WebView2: 8.7 MB in p50 50–57 ms. Sending the whole
  100 k list every frame would cap at ~17–20 fps, and the brush scene at ~15 fps, before decode (85–250 ms).

  stroke segments) and 30.2 MB for brush10k (1.06 M triangles).

### Fallbacks (plan §2.3), measured as far as cheap

Plan §2.3 names one fallback for canvas throughput, a native `wgpu` child surface. I measured or estimated two:
- **(a) Host-side CPU raster, bitmap per frame over IPC** (the cheapest alternative to build). Per frame this costs
  CPU raster time plus pixel transfer plus texture upload:
  - **pixel transfer + upload**, measured: 1904×757 (5.77 MB) takes **p50 36–39 ms + 0.3–1.6 ms upload** on this
    machine. That alone caps the rate at ~25 fps;
  - **CPU raster**, from `c03_raster --canvas-bench`: `vello_cpu` renders the same scenes at the starting camera in
    the times below.

    | Scene | 1280×720, 1 thread / 3 threads | 1920×1080, 1 thread / 3 threads |
    |---|---|---|
    | paths100k | 559 / 197 ms | 1152 / 398 ms |
    | groups1k | 77 / 26 ms | 82 / 30 ms |
    | brush10k | 75 / 35 ms | 85 / 34 ms |

    The CI runners are similar or slower (`raster-comparison.md`).

  **Not viable for 60 fps** at these scene sizes (paths100k ≈ 2–4 fps).
- **(b) Native `wgpu` child surface: estimate only, not built** (as ruled). It would remove the IPC copy
  (≈150 MB/s) and the JS decode, keeping tessellation and upload in Rust. The per-frame GPU work would be of the
  same order as WebGPU's measured 4–9 ms (p50) on this GPU. The real costs would be in the windowing and
  composition with WebView2/WKWebView (a child HWND/NSView above or below the webview, input routing, resize
  synchronisation), which this spike did not measure. Given (a) and the 60 fps result in the webview, no fallback
  is needed on this machine.

  - CI run 39126796883 (the round-1 head), two processes each: Windows **AVX2**, macOS **NEON**, Linux **AVX2**
    (levels as recorded per configuration in the reports; reviewer audit
    `reviews/evidence/M0-C0.3-r2/artifact-audit.json`).

  So on the 39-scene corpus with the f32 configurations, AVX-512 has run only on Linux (39126106552). The Windows
  AVX-512 runner in round 1's audit (run 39122666863) rendered the **original 23-scene corpus without the f32
  configurations**; it is not coverage of the current corpus.

  Reproduce with `python scripts/compare-raster-reports.py crates/render/examples/c03_raster/hashes.json reviews/evidence/M0-C0.3/raster-r1-report-*.json`.
- **But the configurations do not agree with each other (C03-R1-04).**
  - Scalar `Level::fallback()` ≠ detected SIMD on **4 original scenes** (`aa_edge_angles`, `glyph_nonzero`,
    `glyph_evenodd`, `perf_2000_cubics_512`) and on **all 16 stress scenes**. The same holds in the u8 and the f32
    pipelines.
  - Detected AVX2, AVX-512 and NEON agree with each other on every scene. Detected single-threaded equals 3 threads.

  So "identical across OSes" is true for each fixed configuration, **not** across arithmetic paths: a renderer that
  picks its SIMD level at run time would produce different pixels on a scalar-only CPU. That is a C0.4 decision,
  ticketed.
- **Opacity (C03-R1-05).** Over an opaque background, the u8 pipeline leaves alpha at 254 in 4 scenes, 251 in the
  performance scene and **250** in `many_small_paths`. The f32 pipeline and `ttraster` keep 255 everywhere. Source-over
  on an opaque destination must stay opaque (spec 06 §6.4, §6.7), so the u8 pipeline is a known limitation, not a
  candidate final pipeline as configured.
  - No upstream issue reports this. The closest is linebender/vello#904 (closed), which adopted a ±1 approximate
    division by 255 in `vello_cpu`'s u8 path; that is a plausible cause, not established. I did not file an issue.

## C0.4 decision inputs — my position on the reviewer's three assessments (round 1)

1. **Fallbacks (reviewer: the host-raster bitmap path is a valid second fallback experiment and a useful
   reduced-performance software path, not a 60 fps fallback; native `wgpu` stays an estimate).** **Agreed.** I would
   go one step further for C0.4:
   - on hardware like this machine's, no fallback is needed: both webview back ends hold 60 fps at 100 k paths, and
     the reviewer's doubled-geometry probe still holds 60 fps;
   - the host-raster path should be kept as the **software path spec 06 §6.9 requires** ("MUST work when GPU
     acceleration is unavailable, falling back to a software path … with reduced performance"). It is not a
     throughput fallback: pixel transfer + upload alone is 36–39 ms at 1904×757, and 100 k-path raster is 196–393 ms;
   - the Windows-runner software-WebGL2 results (0.8–17 fps) show that WebView2's own software rendering is a
     comparable reduced-performance path. C0.4 should compare the two on a GPU-less machine rather than pick one now.
2. **GPU-resident scene + deltas (reviewer: strongly supported; does not choose the wire protocol; the final CPU
   renderer must consume the same render list, spec 06 §6.1).** **Agreed**, including the spec 06 §6.1 point:
   residency is a transport/cache decision, and both renderers consume the same logical render list.
   - The evidence: full re-send costs 8.7 MB in ~50–60 ms plus 85–100 ms decode, against a 16.7 ms budget. A
     resident redraw with per-frame transform updates (groups1k) holds 60 fps.
   - My position for M4: version the render list per drawing (geometry by stable id, tessellated and resident on
     the GPU), send per-frame deltas (transforms, palette colours — spec 06 §6.3 already resolves colours at draw
     time, so palette edits need no re-tessellation — and dirty drawings), and draw in-progress strokes in an
     overlay (spec 06 §6.9 overlay buffering).
   - I dispute nothing here. The protocol (identities, backpressure, resync) is M4 design work, not a C0.4 decision.
3. **`vello_cpu` vs `ttraster` (reviewer: neither is ready for spec 09 §4 / 06 §§6–9 without more work; decide SIMD
   policy and opacity/quality correctness rather than select on matching hashes).** **Agreed on both conditions.** My
   position, for the C0.4 ADR:
   - **Feature gap against spec 06 §6.3/§6.5–6.7 and 09 §4.6.** Spec 06 §6.3 requires solid, linear, mirrored linear
     and radial gradients, vector and bitmap textures, and alpha textures with their own transforms. §6.5 requires
     colour transforms (mult/add, constant colour, washes), §6.6–6.7 AA clip masks (also inverted), exact flatten
     and radial/directional blur, and 09 §4.6 RGBA export.
     - `ttraster` has solid/linear/radial paint, non-inverted nested clips and bevel/butt strokes. Everything else
       would have to be written here.
     - `vello_cpu` offers layers, clip/mask layers, opacity layers, image paints with transforms, gradients with
       extend modes and a filter framework. Mirrored gradients (`Extend::Reflect`), inverted clips (masks) and
       blur look mappable, but **none of that is tested by this spike's adapter**. Colour transforms and washes would
       be our own pre-pass on paints (spec 06 §6.5's fixed evaluation order), in either renderer.
   - **Determinism (spec 06 §6.7 and decision 14).** The spec requires byte-identical output on the same machine and
     build, and says it SHOULD hold across machines. Decision 14 says to avoid "fused or reordered floating-point
     operations where results could differ". The evidence shows `vello_cpu`'s SIMD paths change pixels relative to
     scalar. My recommendation is to **pin one arithmetic path for the final-quality renderer**:
     - `Level::fallback()` with the f32 pipeline is identical on Windows, macOS and Linux;
     - it costs ≈1.4× the SIMD time (6.9 vs 4.8 ms on the performance scene). Whether that fits export is not
       established: no export budget exists yet (see round-2 assessment 4 below);
     - the interactive renderer is GPU-based and not bound by this (§6.10).

     A pinned SIMD level would also work only if every supported CPU had it, which a scalar-only CPU breaks.
   - **Opacity.** The u8 pipeline fails spec 06 §6.4/§6.7 source-over on an opaque background (alpha 250). The f32
     pipeline passes. So the candidate configuration is **`vello_cpu`, scalar, f32**, if `vello_cpu` is chosen.
   - **Recommendation for the ADR:** `vello_cpu` (scalar f32) as the final-quality rasteriser, behind our own
     render-list adapter. Keep `ttraster` as an independent reference for coverage/compositing goldens. Conditions:
     - the version is pinned and upgrades are gated on the golden PNGs;
     - an adapter test matrix covers the §6.3/§6.5–6.7 features before M3 C3.3;
     - the dependency exposure is accepted explicitly (35 crates, MIT/Apache, `unsafe` only in transitive crates).

     The alternative is to grow `ttraster` to the full feature set. That means owning gradients, textures, blur,
     flatten layers and performance (it is ≈3–10× slower than scalar `vello_cpu` today). I would not recommend it.

## C0.4 decision inputs — the reviewer's four round-2 assessments, next to my positions

Source: `reviews/M0-C0.3-r2.md`, "Evidence for C0.4". Each item summarises the reviewer's assessment, then my position.

1. **Fallbacks.**
   - *Reviewer:* the evidence rejects full host-raster/bitmap transfer as a 60 fps throughput fallback (transfer +
     upload alone ≈36–39 ms, plus CPU raster), but it remains a plausible reduced-performance software path under
     spec 06 §6.9. Native `wgpu` remains a hypothesis: child-window composition, input, resize and Mac behaviour were
     not measured. Keep the measured webview GPU paths, compare host bitmaps with webview software rendering on a
     GPU-less machine after R2-02 is fixed, and require an integration prototype only if Mac/device evidence makes
     native `wgpu` necessary.
   - *Me:* **agreed in full**; it matches my round-1 position. R2-02's fix is a precondition for that comparison:
     software WebGL2 runs far below 10 Hz (paths100k at 0.8 fps on the Windows runner), which are exactly the runs
     the version-1 completion rule could reject. Version-2 logs record them as complete, missed-target observations.
2. **Resident scene.**
   - *Reviewer:* the evidence strongly supports per-drawing GPU residency and deltas (a full list exceeds the frame
     budget before decode; resident redraw with local group updates holds 60 fps). It does not establish a
     host-to-GPU delta protocol: the spike animates transforms locally in JS. Adopt residency as the M4 direction
     (stable identities, revision checks, batching/backpressure, resync, overlay), benchmark real edits and upload
     stalls, and keep spec 06 §6.1's one logical render list: residency must not create a second authoritative scene
     model.
   - *Me:* **agreed**, including the qualifier that the delta transport is unmeasured. groups1k's transforms are
     computed in the page (`animateGroups`), not sent from the host. So the spike shows that resident geometry
     redraws at 60 fps, not that a delta stream arrives in time. The full groups1k transfer (2 MB, ~14 ms) bounds a
     transform-only delta from above; it is not a measurement of one.
3. **Final rasteriser.**
   - *Reviewer:* provisionally choose **`vello_cpu` f32 with `Level::fallback()` behind the project's adapter**, with
     `ttraster` kept as an independent reference. Neither adapter is spec-complete: mirrored/transformed/image/alpha
     paints, inverted masks, flatten/effect layers, blur, colour transforms, correct stroking and export conversion
     need a feature matrix before M3 C3.3. Pin version, lockfile and arithmetic policy, gate upgrades with goldens,
     and explicitly accept the transitive dependency exposure. The cross-OS scalar tests and the compiler experiment
     support this bounded recommendation, not the correctness of untested upstream features.
   - *Me:* **agreed**; it is my round-1 recommendation with the same conditions. The reviewer's compiler experiment
     (default release, `target-cpu=native`, and `opt-level` 1 vs 3 for `ttraster` all reproduce the committed scalar
     hashes) strengthens the case for pinning the scalar level; I had not tested that. I would add one row to the
     feature matrix: the conversion from `vello_cpu`'s premultiplied output to spec 09 §4.6's RGBA export. Its
     rounding is ours to define, since the C0.3 driver hashes premultiplied bytes.
4. **Scalar cost.**
   - *Reviewer:* spec 09 §4.4 sets the camera size and 25/50/100/200 % scale presets, not a fixed export resolution or
     a real-time requirement. Pixel-area extrapolation of the 512×512 scene (6.9 ms scalar f32 / 4.8 ms SIMD f32 /
     18.5 ms `ttraster`) gives about 24 / 17 / 65 ms at 1280×720, **55 / 38 / 146 ms at 1920×1080** and
     218 / 152 / 585 ms at 3840×2160. Scalar's ≈44 % raster cost is a defensible offline-export trade-off, but "well
     within export budgets" is not established: the spec gives no budget, and the spike omits effects, encoding,
     memory pressure and real scene density. Pin scalar initially; measure real 1080p/4K export latency and
     cancellation before setting budgets.
   - *Me:* **agreed; I withdraw "well within export budgets"** (corrected above). The extrapolation is arithmetic on
     my numbers and I reproduce it (6.9 ms × 1920·1080 / 512² ≈ 54.6 ms). Measured evidence I already have supports
     the reviewer's caution that scene density, not pixel count, decides. `c03_raster --canvas-bench` rasterises the
     canvas scenes at 1920×1080 with detected-SIMD u8 `vello_cpu` on one thread in 82 ms (groups1k), 85 ms
     (brush10k) and 1152 ms (paths100k). That is ≈2× and ≈30× the 38 ms SIMD extrapolation. A budget therefore has
     to come from production-density scenes with effects and encoding, which is M3 work, not a C0.4 decision.

## Known gaps

1. **No macOS hardware measurement**: the macOS runner has a paravirtual GPU and no WebGPU adapter. Pending user.
2. **The spike renderer is not a product renderer.**
   - Cubics are flattened once at a fixed world tolerance, so deep zoom shows facets.
   - Strokes are per-segment quads: joins overlap, so translucent strokes double-blend at joins, and there are no
     real caps or joins.
   - Draw order is all fills, then all strokes.
   - There is no clipping, gradients or effects on the GPU path.
   - Decode runs on the main thread.
   - These choices favour throughput measurement; M4 must preserve painter's order and correct stroking.
3. **GPU timing on WebGL2 is not measured** (no timer query used); fps and CPU time are. WebGPU's "GPU time" is
   submission-to-completion notification latency, including queueing, not a timestamp-query duration.
4. **IPC-per-frame streaming was measured as sequential transfers.** `1000 / median transfer` is a typical
   sequential transfer-only estimate, not an upper bound for every pipelined design.
5. **Determinism coverage:**
   - x86-64 AVX2 and AVX-512 (on the current corpus, Linux only) and arm64 NEON (detected), plus the scalar
     fallback level; no SSE4.2-only hardware has been tested;
   - the u8 and f32 pipelines with the adapter's subset (no blur, filters, round joins/caps or images);
   - this exact toolchain and lockfile;
   - the SIMD policy is a C0.4 ticket.
6. The pixel-frame fallback used a synthetic pattern; real raster plus transfer is an estimate (sum), not an
   end-to-end run.
7. The spike commands are registered in release builds (gated by the launch flag, like C0.2's); remove or dev-gate
   them with the other M0 diagnostics.
