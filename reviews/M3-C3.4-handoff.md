## 1. Built

- **`scripts/e1-bouncing-ball.py`**: E1 (11 §14.8) end to end against the release `toontown-headless` through the
  official SDK `mcp==2.0.0`. Every step is a registered command or a generic tool. Every expected value is computed
  in the script. It makes 53 checks, writes a shallow delivery folder (plan §3), takes about 20 s locally in release,
  and runs identically twice. Process A, one MCP session, runs:
  - build, validate and read back;
  - evaluate frames 1-30 against the script's own 05 §9.1-9.2 path and 05 §10.4-10.5 timing (1e-9 field);
  - the 24-frame sequence and manifest;
  - centres measured from the PNG pixels (0.05 px);
  - single renders equal to the sequence frames;
  - the contact sheet, cell by cell;
  - delivery conflicts, a late read-only target, sidecar-owned recovery and a cancelled export;
  - records through `job_status`, `job.wait` and `job.list`;
  - describe, hit test and convert at frame 12;
  - undo and redo; save, close and reopen; re-render;
  - the parent-transform / camera-roll / default-FOV variant.

  Process B is the recorded script (`e1-commands.json`, stable symbolic references) run with `--run` into a fresh
  project. It gives the same canonical content and the same 24 frame bytes, and it does not see A's job records.
- **CI:** an E1 step in `c33 render release` (Windows, macOS) with artifact `e1-<OS>`. `c33 cross-OS` compares every
  E1 output byte for byte, except `report.json`, the packages and the delivered manifest (its normalised copy is
  compared).
- **Builder tests** `crates/executor/tests/c34_e1.rs` (5 tests):
  - swatch paths as colour IDs;
  - `wait: true` in a sequential batch;
  - E1 edits, undo and redo announce every changed frame (`anim.changed` conservative coverage);
  - one evaluation per node per frame for render, describe, hit test and a 24-frame contact sheet;
  - a dead job's sidecar recognised in any letter case of the host name.
- **Gaps E1 exposed, fixed** (§3): swatch paths where colour IDs are accepted, `wait: true` in sequential batches, and
  host-name case in sidecar liveness.
- **CI budget ruling** (`7216cb9`): three reviewer corpora move from debug `check` to release, bodies unchanged (§3).

## 2. Behaviour notes a reviewer will want

- **E1's motion:**
  - The ball is a straight vertical bounce: top (y = 2.5 field) at frame 1, the floor (−2.5) at 12, the top at 24.
  - The easing is explicit on the `velocity` channel: `slowAcceleration` for 1-12, so it falls faster and hits the
    floor at speed, then `slowDeceleration` for 12-24. The scene is 30 frames, so frames 25-30 show the hold.
  - The straight path keeps the expectation exact without a TCB reimplementation for curvature. The script still
    implements 05 §9.2's 64-sample arc length, because on any curve, a straight one included, the point at distance s
    differs from the exact distance by up to 3.4e-4 field here. The script checks both: agreement with the spec'd
    sampling to 1e-9, and the sampling within 1e-3 of the exact eased distance.
- **Rendered centres** are coverage-weighted centroids of the ball's pixels (line and fill in the same swatch) at pixel
  centres +0.5. Worst error measured locally is 0.0003 px for the 24 frames and 0.0001 px for the variant, against a 0.05 px
  tolerance; evaluated positions agree with the script's §9-§10 implementation to 4e-15 field. The ball's measured radius is 86 px: 80 px
  (0.5 field) plus half the default line.
- **Canonical content** for save/open, undo/redo and replay comparisons:
  - Object IDs (type prefix + ULID) are replaced by names in order of first appearance.
  - Volatile fields are dropped: times (`createdAt`, `modifiedAt`, `exportedAt`, …) and revision counters (`rev`,
    `documentRev`; an undo and a redo are two more edits, 10 §2).
  - `renderMs` is volatile (C33-R1-06); PNG bytes and SHA-256 are the contract.
- **Colours in the script** are named `palette:#1/swatch:#N` (the default palette's red). The recorded script is
  replayable in any new project, and the stored drawings carry the resolved colour IDs.
- **MP4** (E1's "export MP4 → manifest lists one file of 24 frames") is replaced by the PNG sequence, whose manifest
  lists 24 frame files. MP4 encoding is **M10 C10.1** per plan §4 and ADR-0008 (sidecar built in M8 C8.3). The C3.4
  brief says M9; M9 is Library and storyline in plan §4, so the deferral is recorded with the plan's owner.
- **Readiness item 9's deep/broad budgets** are the inherited reviewer and builder suites (`c33_r2_stress` in release,
  `c33_r1_limits`, `c33_round1::known_sizes_are_refused_before_work_and_render_ms_is_reported`). E1 adds the E1 rig's
  counts.

## 5. Known gaps and deferrals (with owners)

- MP4 export: M10 C10.1 (ADR-0008; sidecar M8 C8.3).
- Attached-session byte gate: M4 C4.2. Thumbnails: M5 C5.2. Bones: M6 C6.3; effects: M7; views and draft: M4 C4.2;
  xsheet composition: M5 C5.1; sounds: M8; importers: M10; C22-T2 and R1-12: M11 C11.1.
- **Lock files compare host names case-sensitively** (`tt_persist::lock`, C1.3/C1.4). Found while fixing the sidecar
  case and not changed here: a lock written by `K-AI` is treated as another machine's by a process that reads `k-AI`.
  That is the safe direction (no takeover), but a stale lock is not recognised. Owner: M11 C11.1 (hardening), or
  earlier by ruling; the fix is `host::is_this_host` in `lock.rs`.
- Open spec issues: see [M3-merge-note.md](M3-merge-note.md) §4. No new SI; the next free id stays SI-111.

## 6. How to run

```
cargo build --release --locked -p tt-headless
python -m venv .venv && .venv/Scripts/python -m pip install "mcp==2.0.0"   # bin/python on macOS
PYTHONIOENCODING=utf-8 .venv/Scripts/python scripts/e1-bouncing-ball.py target/release/toontown-headless.exe out/e1
cargo test --locked -p tt-executor --test c34_e1
cargo test --release --locked -p tt-executor --test c33_r2_depth --test c33_r2_stress --test c31_r3_hierarchy
```

`out/e1/report.json` lists every check. `E1_DEBUG=1` keeps the scenario's work folder.
