## C43A-R1-01, P2: `draw.viewMapping.get` for the Camera view

02 lines 101-104 make the Camera view's drawing-plane mapping queryable. `draw.viewMapping.get {view: <a Camera view>}`
now answers for the current drawing. `drawingToView` is the element's plane through the camera at the current frame,
composed with the view transform: the same matrix as the scene answer's occurrence matrix followed by `cameraToView`,
which the gestures and the addressing parameters also use (`camera_view::element_to_view`). `viewToDrawing` is its
inverse; `zoom`, `rotation` and `viewSize` are the view window's. It refuses as follows:

- a plane at or behind the near plane: `inspect.behindCamera`;
- no current element: `arg.invalid`;
- Top and Side views: `command.notImplemented`, owner M6 C6.1, as before.

Test: `c43/mapping.rs` `c43a_r1_01_draw_view_mapping_get_publishes_the_camera_views_mapping`. Over five states (plain;
zoomed and rotated; a rolled camera with a pan; a moved and rotated element; a later frame exposing another drawing),
each point mapped by the published matrix equals `view.coordinates.convert` for the same point (1e-6). The two matrices
are each other's inverse and equal the occurrence matrix through `cameraToView` (1e-9). `drawingId` names the current
drawing. The seeded V6 table below uses the matrix in 40 more states. The reviewer's
`part_c_mapping::camera_drawing_mapping_is_queryable` passes.

## C43A-R1-02, P2: scene and Camera-view points of an addressed element

The addressing normaliser now resolves the call's target before converting: `crate::addressing::target`. This is the
C4.2a ruling's order, written into SI-146 first:

1. With `drawingId`: the element showing that drawing. That is the call's `elementId` if it shows it, else the current
   element if it does, else the first element of the drawing's bank.
2. Else with a qualified object id: the same rule for that id's drawing.
3. Else `elementId`.
4. Else the current element.

The frame is the call's `frame`, else the current frame. The executor keeps that element and frame for the running
command (`Cx::addressed`). Scene points then go through that element's plane at that frame. A Camera view's view points
go through that element's plane and the camera, both at that frame (`camera_view::chain_at`), and so do its view-pixel
tolerances. The colour commands convert in their handlers through the same entry (`camera_view::addressing`). The
reviewer's `draw.pivot.set {elementId: Addressed, frame: 1, space: "scene"}` case now puts the pivot at (0, 0).

**The extended addressing matrix**, `c42/addressing.rs`
`c43a_r1_02_every_point_taking_command_by_every_naming_in_scene_and_camera_view_space`: **264 cells, every cell
succeeds**.

- **Cells:** the 27 point-taking commands × the five namings (`drawingId`, `elementId` + `frame`, `frame` alone,
  current, `drawingId` winning over `elementId` + `frame`) × two spaces (`scene`, and `view` naming the Camera view).
  `draw.repositionAll.apply` takes only its two element namings.
- **Setup:** Bob is the addressed element. Another element (`Other`) is current in the `drawingId`, `drawingId`-wins
  and `elementId` + `frame` cells; the `frame`-alone and current cells name the current element by definition. The two
  elements differ in position, depth, scale and rotation, and the Camera view is zoomed.
- **Points:** each cell's points are the drawing-space reference points, carried into the cell's space by an
  independent mapping of the element and frame its naming addresses. That mapping is `inspect.coordinates.convert` to
  `scene` or to `image`, then the scene answer's `cameraToView`.
- **Comparison:** each cell is compared with the call that uses `drawingId` and drawing-space points: the same answer
  and the same saved content, to the rounding of a conversion (1e-6).
- **Fixture change:** the fixture's keyed motion of Bob and its peg is removed in this world, so Bob's plane is
  axis-aligned at every frame and the rectangle fields convert. A rotated rectangle is refused by its own rule
  (C42A-R2-01).
- **Unchanged:** the C4.2a matrix (`c42a_r4_01_…`, drawing and Drawing-view spaces) is untouched and passes.

## C43A-R1-03, P2: a drawing tool on a plane the camera cannot project

- **The cause.** A Camera-view press took the drawing mapping from `press_matrix`, which fell back to the identity when
  the current element's plane had no mapping. The Brush therefore drew into the drawing in view pixels.
- **The press.** `press_matrix` now returns the chain's refusal. A drawing tool's press on such a plane (behind the
  near plane, or on the camera's plane) refuses the whole `pointer` call with `inspect.behindCamera`, and nothing is
  created. This holds for `space` `view`, `scene` and `camera`. The scene tools and the navigation tools work in view
  pixels and are not affected. The final hover's drawing point is null there.
- **Direct commands.** A point-taking command with Camera-view points already refused in the normaliser, before its
  handler; it is unchanged.
- **Availability.** `host::unavailable` now evaluates the **common addressing check** (`crate::addressing::check`, the
  conversion the call makes first) for every complete reference of the 27 point-taking commands, after the static
  checks and before the precheck. So these commands are unavailable with the call's own message while the addressed
  element's plane is unprojectable.
- **Inventory.** The availability inventory's header records this. The script counts `inspect.behindCamera` of those
  commands as answered by a static check (as `project.none` is), and the eight rows that classed it as `parameter` are
  gone. The `view.coordinates.convert` row stays.
- **Test.** `c42/addressing.rs` `c43a_r1_03_camera_points_on_an_unprojectable_plane_are_unavailable_and_refused` sweeps
  both states for every one of the 27 commands, against a dry run (ruling O-24's rule):
  - plane behind the near plane, or on the camera's plane: availability refuses with the dry run's message, the call
    refuses `inspect.behindCamera`, and the document is unchanged;
  - plane in front: neither gives that refusal, and 27 of 27 run.
- **The reviewer's test.** `part_c_mapping::case4_unmappable_planes` passes unchanged. SI-145's rule for scene points
  stays (SI-145 amended).

## C43A-R1-21, P2: the temporary Skew

- **SI-151, written first.** The modifiers are read at the press. The Transform tool with the alternate modifier runs
  the Skew tool for that gesture (gesture tool `scene:skew`), and the stored scene tool stays Transform. With the
  temporary-select modifier also held, Select wins (05 line 393 lists Skew among the tools it overrides).
- **Top or bottom side.** A drag from the side midpoint or the skew handle outside it is 05 §5.4's horizontal shear:
  `{target: key, frame, skew, relative}`, labelled "Skew Element".
- **Left or right side.** A drag is the vertical shear y' = y + k·x. The first selected node's R·K·S, premultiplied by
  the shear, is decomposed by 05 §2.5, and only the changed channels are sent (rotation, skew, scale.x, scale.y),
  keyed. The label is "Transform Element", by SI-144, since several groups change.
- **Anywhere else.** A drag commits nothing; a click selects.
- **Tests.** `c43/spec_values.rs` `every_scene_drag_has_the_spec_value_keys_and_label`, rows "temporary Skew, top
  side", "temporary Skew, right side", "temporary Select over the temporary Skew" and "the alternate modifier with
  Select". Each states 05 line 393 or 394 and §5.4, and asserts the parameters to 1e-9 against values derived in the
  test (the vertical shear in closed form: tan θ = k, κ = θ, sx = √(1 + k²), sy = 1/sx). It also asserts the channels

  directly gives the same document. `the_temporary_skew_acts_only_from_a_side` covers the other drags and the click.

## C43A-R1-04: rejected, ruling D-28

The four tests carry the ruled attribute and nothing else changed (see "Reviewer files" below). On the ruling's note:
**changed.** A move's delta is now a vector through the linear parts of the chain:

1. view pixels to output pixels;
2. output pixels to camera space at the node's depth, by `2 · depth · tan(fov / 2) / width` (05 §2.6);
3. camera space to the world, then the world to the parent, through the linear parts of their matrices.

It is no longer the difference of two converted points. With that change `case1_position_only` and
`case2_existing_new_static` pass bit for bit when run with `--ignored`: the 20-pixel drag is exactly 0.125.
`case5_transform_handles` and `case6_select_handles_labels` still differ in the last bits of a skew angle
(13.771599717082415 against ...418, the arc tangent of a box ratio), which D-28 leaves to round 2's tolerance.

## Performance (found while measuring plan §6's kernel budget)

Three costs grew with the square of the scene's elements; all are linear now:

- the evaluator read the scene's length once per node;
- the render list searched the tree once per element for hidden ancestors;
- a pick ran every drawing's hit test at nine points.

A pick now skips a drawing whose `extent` (its bounds counting invisible strokes) does not contain the point, and a
scene gesture builds one render list instead of two.

| 1,000 elements (debug) | Before | After |
|---|---|---|
| scene answer | 94 ms | 7 ms |
| pick | 85 ms | 20 ms |

The test `a_fill_bounded_by_invisible_strokes_is_hit_outside_the_visible_strokes_box` covers the prefilter's edge. The
budgets go in the handoff.
