### C41-R3-01 ? P2 ? session helper threads omitted from promised bound

Requirement: design note I-1 section 3 explicitly promises at most `3 + C + S` threads and says no other thread is ever created by the server; ADR-0022 decision 2 repeats the bound; response O-15 ratifies it. `http.rs:1189` calls `serve`, which creates `mcp-writer`, `mcp-reader`, `mcp-events`, and `mcp-calls` at `server.rs:362,403,411,421`. A session therefore costs five persistent threads, not one (additional work threads are possible too).

Permanent test **fails at 64970ec**: `saturated_pools_obey_thread_formula_and_unread_refusals_do_not_stall`. With C=8, U=2, L=8, S=32, process baseline 9, measured 179, permitted total 52. A token holder initializing sessions consumes 128 extra persistent threads beyond the declared budget, observable as process thread/resource growth. Builder counter tests miss this because `Stats.sessions` counts map entries. The test checks service and stop cleanup before its failing formula assertion; all server counts and process threads returned to baseline. Builder must pass its body unchanged.

Full saturation used 32 sessions, six authenticated streams and two pending workers. A subsequent 64 unread-connection burst exercises refusal and lingering alongside them; snapshot workers 7/pending 1/lingering 6/sessions 32. The closer can drain during observation; simultaneous L=8 occupancy is not claimed. No runtime socket-handle census was performed; socket formula was checked by ownership tracing and bounded counters.


## A3 ? Session lifetime

The guard is taken under the session lock before reading a named body (`http.rs:1022,1121`), and insertion and initial guard share the cap critical section (`1177`). GET installs its route under that same lock (`1075`). Guard Drop (`1008`) decrements and resets last_seen, including parse failures, body failures and unwinding; absent/deleted sessions are harmless. Expiry (`987`) checks zero guards. There is no route-to-map inversion in these paths.

Runtime evidence:

- Earlier reviewer body-expiry test passes unchanged. Builder stream/body lifetime test passes: 300 ms idle, 900 ms open stream and then 900 ms slow body, followed by expiry after the answer.
- Own `executing_command_holds_session_past_idle_bound`: a registered handler signals entry and waits on an atomic gate; session remains mapped for 600 ms with a 250 ms idle policy. Release returns its result, then the session expires. No sleep inside timing bounds.
- Own `many_guards_release_and_expire_after_last_disconnect`: twelve simultaneous partial bodies hold the same session over twice its 250 ms idle interval; disconnect all; workers reach zero and expiry follows (at least 180 ms after observing worker completion). Builder mid-body disconnect test also passes. These prove guard count returns to zero through observable expiry, rather than relying on an inaccessible counter.
- Own `in_flight_sessions_still_count_against_session_cap`: 32 sessions each with a partial body; the 33rd initialize gets 503 and the map remains at 32.
- Own `delete_during_body_does_not_resurrect_request_routes`: DELETE gets 200, map becomes empty; completing the previously admitted ping body yields a finite response and EOF, without reinsertion. The old request can still complete through its cloned sender. No specified cancellation/error envelope for that caller was found, so this is not a finding. Builder DELETE/open-SSE and stop/open-SSE test passes.
- Stop with streams, pending and refusal sockets cleans up counts and OS threads in the saturation test. Stop with an authenticated partial body fails independently (02). No claim of a test with literally every socket state sampled simultaneously is made.

### C41-R3-02 ? P2 ? stop leaves authenticated body workers and session loops alive

Requirement: admission design section 6, I-7 Server stop: every session leaves the map, **their loops end**; pending connections are evicted, closer sockets close, and workers still writing end within their write timeout. ADR-0022 decision 5 says disabling the server stops it. This is a transport body reader, not a running command that cannot safely be preempted.

`HttpServer::stop` (`http.rs:199?217`) signals only pending heads, drains the session map and wakes cleanup. An authenticated body reader is no longer pending and waits in `read_body` (`519?533`) until the original request deadline, with no stop check or socket shutdown. Its `Entered` tuple retains the protocol input sender (`1028,1121`), so removing the map entry cannot close that protocol loop's input either.

Permanent test **fails at 64970ec**: `stop_releases_authenticated_body_workers`. Initialize, admit a partial authenticated body, synchronize on worker=1/pending=0, stop. With request deadline 15 s and write timeout 100 ms, after a measured 3 s grace the server still reports worker=1/sessions=0. At defaults this can retain a socket, its worker, and the session machinery for the remainder of 60 s after the user disables attached mode. The test closes its client after recording failure so cleanup can finish. Builder must pass its body unchanged. The assertion grants substantially more than the configured write timeout and does not require stop to join threads synchronously.

## Observations (not findings)

- The design promises a lock-free closer channel (section 7), but `linger` takes `Mutex<VecDeque<...>>` at `http.rs:761`, also held by the closer while draining. Accept therefore can contend on a lock. No user-visible stall was established (64 unread sockets still allowed service in 13.9036 ms on the final run); this structural mismatch is recorded without a failing test or severity.
- A request admitted before DELETE can finish afterwards through its retained sender; no requirement specifies a different caller envelope, and the session stays absent.
- The active flood exclusion means continuously racing a fresh idle connection between every refusal and retry has no bounded-service guarantee. No new fairness requirement is inferred from that probe suggestion.
