CI follow-up. Run 41163880282 (at `57e0b70`) failed `check (macos-latest)` in two M1 reviewer tests of
`c13_r2_persistence` (unchanged): (1) `gigabyte_package_inspection_is_bounded_with_and_without_validation` measured a
peak of 152 698 880 bytes against the probe's 128 MiB bound. Cause, introduced with C2.1: the executor lists the
system fonts on a background thread at start, and without fontdb's `memmap` feature every font file is read whole
(the macOS emoji font alone is larger than the bound), so the peak depends on how far the scan gets before the
probe's process exits. Fix: fontdb's `memmap` feature (memmap2, MIT OR Apache-2.0; ADR-0003 allow-list, `cargo deny`
clean) — the files are mapped and only their name tables are touched. (2)
`thirty_two_concurrent_lock_acquisitions_keep_exactly_one_owner` saw no owner in one of 128 trials (stale=true,
trial 17). It passed on the next run (41166897844) and failed again on the run after (41170158603, trial 13), so it
was not a one-off. Cause, a latent M1 race in `tt-persist` (`lock.rs::create_protected`, Unix): the lock file is
created exclusively and then `flock`ed; when another opener's `probe` held its momentary shared lock at that
instant, `try_lock` returned `WouldBlock`, the caller treated it as "exists" and retried, and the **empty,
unprotected file it had just created stayed behind**. Every opener, the creator included, then read it as an
unreadable live holder: 32 × `HeldByOther` with empty info, exactly the logs. Fix (`fix(persist)` commit): a
conflicting lock on a file just created exclusively can only be a probe's, so it is waited out (up to 200 × 1 ms);
giving up removes the file just created. Windows (share-mode protection) is unchanged. The reviewer test is
unchanged. Checked by `cargo clippy --target aarch64-apple-darwin -p tt-persist` and the persistence and lock
suites (`tt-persist`, `c13_r1/r2/r3_persistence`, `c13_r4_closure`, `c14_lock_races`, `c13_projects`) locally; CI
runs them on macOS.

**CI:** [run 41166897844](https://github.com/kaigani/261017-toontown-dev/actions/runs/41166897844) at `353513e`
had all 10 jobs succeed ([job list](evidence/M2-C2.1/ci-41166897844.txt)); the lock race then recurred on the next
run, so the closing run is the one after the persistence fix, recorded in the handoff commit that follows.
