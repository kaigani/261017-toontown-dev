## New findings

### C03-R2-01 — P1: contradictory headers still produce successful workload evidence

**Location:** `scripts/analyse-canvas-log.py:175–203`, `:205–216`. **Target: C0.3 before closure.** This is the remaining portion of C03-R1-01, not an additional count for the same old defect.

Start with the fresh builder RTX automatic log. In every transfer of its first `paths100k` run, replace `points` with zero and add `8 × old_points` to `verbs`. This preserves the exact encoded byte length, the declared groups and paths, but claims a path stream with **no points** while decode still reports **200,000 cubics and 2,832,713 segments**. The analyzer exits **0**, prints the successful 100 k-path row and reports its target met. It checks only groups/paths against the table; equality of the combined byte length cannot establish the other counts or reconcile them with decoded geometry.

A second bypass changes the parameter/run/header seeds to 2 and every transfer to a **72-byte, zero-group/zero-path/zero-point/zero-verb header**. The original decode counts and successful timing rows remain. This also exits **0**, because seed 2 sets `want=None` and no header-to-decode consistency check replaces the skipped workload table. Both examples are internally contradictory regardless of whether arbitrary seeds are intended to be supported.

**Permanent failing assertions:** `test_c03_r2_01_compensating_point_verb_counts` and `test_c03_r2_01_nondefault_seed_does_not_bypass_workload` in [c03-r2-tooling.py](../tests/adversarial/c03-r2-tooling.py), registered with ordinary assertions in `desktop/src/test/c03-r2-tooling.test.ts`. [Transcript](evidence/M0-C0.3-r2/analyzer-attacks.log). They require nonzero exit and empty stdout; no skip/xfail is used.

**Required correction:** reconcile all header counts with the actual supported workload and with decoder counts; explicitly reject unsupported evidence rather than disabling checks for another seed. Keep complete validation ahead of all reporting. This violates the binding analyzer ruling and plan §5.2 evidence requirement. It does **not** invalidate the independently verified actual RTX/artifact measurements.

### C03-R2-02 — P1: valid slow runs from the current page are rejected as incomplete

**Location:** `scripts/analyse-canvas-log.py:226–227`, interacting with `desktop/src/spikes/canvas/CanvasSpike.tsx:230–244`. **Target: C0.3 before closure**, because C0.4's software-path comparison needs valid slow observations.

The page records `start = await nextFrame()`, then awaits another frame before storing its first sample. It stops when `t - start >= 10000`. The analyzer instead requires `lastStored - firstStored >= 9900`, allowing only 100 ms for that omitted first interval. At a legitimate **1 Hz cadence**, the page completes ten seconds of pan/zoom but stores ten samples spanning **9,000 ms**. The analyzer exits **2**: `frame timestamps non-monotonic or shorter than 10000 ms`.

The permanent [c03-r2-page.test.tsx](../desktop/src/test/c03-r2-page.test.tsx) mounts the **unchanged CanvasSpike component in Vitest/jsdom**, runs its real button handler and real save/log construction, and feeds the saved log to the unchanged analyzer. Host payloads/decoder statistics, GPU operations and the clock are controlled test doubles; the page's timing loop and log serialization are not rewritten. Completed runs have `error:null`. The real-page **manual save** and **60 Hz interactive** controls pass; the **1 Hz interactive** assertion fails. [Saved slow log](evidence/M0-C0.3-r2/page-slow.json), [test output](evidence/M0-C0.3-r2/review-vitest.log). The same duration validation applies to automatic runs.

**Required correction:** record and validate explicit phase start/end timestamps (or an equivalently sound completion contract), keeping raw frames for cadence estimation. Do not merely remove duration validation or reject slow-but-complete measurements. This violates the requested legitimate-log compatibility check and undermines evidence collection precisely for the GPU-less fallback under consideration. The actual downloaded CI logs happened to validate; this is a controlled counterexample, not a claim that the green CI run failed.

### C03-R2-03 — P2: the new encoder's structural validation can report success for invalid packets

**Location:** `desktop/src-tauri/src/spikes/canvas/renderlist.rs:341–375`, `:379–435`. **Ticket target: M3 C3.3, before reusing this encoder/protocol in the product; preferably fix during the analyzer response.**

Append a single NaN to an otherwise valid even-length `Scene.points`. `as_chunks::<2>().0` ignores the leftover coordinate, the header floors the point count with `/ 2`, but encoding writes every float. `encode` returns `Ok` containing an unchecked NaN and a packet **four bytes longer than its counts imply**. Separately, `PathRec.style=3` returns `Ok`, although the decoder rejects styles above 2. These contradict the new claim that validation checks every decoder prerequisite. Neither currently arises from the trusted generated scenes; the TS boundary rejects both packets, so this is a contained spike/API-contract issue, not an external exploit.

**Permanent failing assertions:** `c03_r2_03_unpaired_coordinate_must_be_refused` and `c03_r2_03_unknown_style_must_be_refused` in [c03-r2-encoder.rs](../tests/adversarial/c03-r2-encoder.rs). `python reviews/evidence/M0-C0.3-r2/final_audit.py` compiles and runs them with `CARGO_MANIFEST_DIR` set to `desktop/src-tauri`; [encoder-attacks.log](evidence/M0-C0.3-r2/encoder-attacks.log) has **9 passes / 2 assertion failures** including the included original encoder tests. Refusal-path probes did not panic inside product code, and no new unchecked `unwrap()` was added to those product paths; the failures are the review assertions.

**Required correction:** reject incomplete coordinate pairs and unknown styles with typed errors. Make the encoder's structural contract agree with the certified decoder before promoting it out of the spike. Plan §5.2 correctness/error-handling review applies.

**Fallback assessment.** The evidence is sufficient to reject full host-raster/bitmap transfer as a 60 fps throughput fallback at these workloads: transfer/upload alone is about 36–39 ms in the handoff, plus substantial CPU raster time. It remains a plausible reduced-performance software path under spec 06 §6.9. Native `wgpu` remains a hypothesis: removing IPC/JS work is plausible, but child-window composition, input, resize and Mac behaviour were not measured. I would retain the measured webview GPU paths, compare host bitmaps with webview software rendering on a GPU-less machine after R2-02 is fixed, and require an integration prototype only if actual Mac/device evidence makes native wgpu necessary.

**Resident-scene assessment.** Evidence strongly supports per-drawing GPU residency and deltas: a full list already exceeds the frame budget before decode, while resident redraw and local group updates meet 60 fps. It does not establish a host-to-GPU delta protocol; the spike animates transforms locally in JS. I would adopt residency as the M4 direction with stable identities, revision checks, batching/backpressure, resync and an overlay, while benchmarking real edits and upload stalls. Preserve spec 06 §6.1's shared logical render list for interactive and CPU renderers; residency must not create a second authoritative scene model.

**Final-rasterizer assessment.** I would provisionally choose **vello_cpu f32 with `Level::fallback()` behind the project's adapter**, keeping ttraster as an independent reference. The corrected opacity and determinism evidence supports that choice; the current ttraster subset is slower and transfers substantial unimplemented feature ownership to this project. Neither adapter is yet a spec-complete final renderer: mirrored/transformed/image/alpha paints, inverted masks, flatten/effect layers, blur, colour transforms, correct stroking and export conversion need a feature matrix before M3 C3.3. Pin the version, lockfile and arithmetic policy, gate upgrades with goldens, and explicitly accept the transitive dependency exposure. Cross-OS scalar tests and the new compiler experiment support this bounded recommendation; they do not establish correctness of untested upstream features.

**Scalar-cost assessment.** Spec 09 §4.4 uses the project camera size and 25/50/100/200% scale presets; it does not impose one fixed export resolution or a real-time export requirement. Using the handoff's **512×512** performance scene and its roughly **6.9 ms scalar f32 / 4.8 ms SIMD f32 / 18.5 ms ttraster**, a simple pixel-area extrapolation gives approximately **24 / 17 / 65 ms at 1280×720**, **55 / 38 / 146 ms at 1920×1080**, and **218 / 152 / 585 ms at 3840×2160** (200% of a 1080p camera). Scalar's roughly 44% raster cost is a defensible offline-export trade-off, but “well within export budgets” is not established: the spec gives no such budget, and the spike omits effects, encoding, memory pressure and production scene density. I would pin scalar initially and measure actual 1080p/4K export latency and cancellation before setting budgets; area scaling is an estimate, not a measured benchmark or a promise of linear scaling.
