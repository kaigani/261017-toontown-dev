## The capture waiter test

- **What happened on the review machine:** the test raced. Under the short budget the holders' calls end at their
  budget at the same moment as the waiter's, so the waiter can take a freed slot and start a capture (it answered
  `job.waitTimeout` there).
- **The rewrite asserts no wall-clock figure near a budget:**
  - Cancellation: the holders have a long budget, so the waiter really waits. It cancels 20 ms after it starts. It must
    answer `command.timeout` within 10 s, and the capture jobs stay at the holders' two.
  - Budget: every legitimate outcome is accepted. `limit.exceeded` must have started nothing; a capture or
    `job.waitTimeout` must have started exactly one. The waiter answers within ten times its budget, and a sampler
    thread checks that running capture jobs never exceed two.
- **Twenty local runs: 20 passed, 0 failed** (each run's budget waiter answered `limit.exceeded`; peak running capture jobs 2).

## Example results: which pointers vary, and what still catches a change there

- **Classified as varying** (`recorded::varying`):
  1. pointers whose values differ between two executions of the same code in one recording (generated ids,
     confirmation and session ids, tokens);
  2. timestamp and duration keys (`time`, `createdAt`, `startedAt`, `connectedAt`, `exportedAt`, `durationMs`,
     `renderMs`, and the other TIME_KEYS);
  3. machine facts (`platform`, `locale`, a confirmation's path-dependent projected byte count);
  4. the bounds of text objects, which depend on the installed fonts.
- **Narrowed:** the recorder now keeps a retained value only for classes 1 and 2, values no code change can make
  semantic: the code is the same in both executions, and the clock decides the timestamps. Classes 3 and 4 are written
  fresh on every regeneration, so no semantic value hides behind a retained one.
- **What catches a change at a varying pointer:** in every check run, the same test
  (`c21_example_results::every_implemented_example_has_a_retained_executed_result`) validates each live result, values
  at varying pointers included, against the command's result schema and the envelope schema. A change of type or shape
  there fails it. The content of text bounds is covered by the text commands' own tests (`c22`/`c23` text suites).
