Method (changed during the work, declared): the fixture's ink is the box's own rectangle, so the held overlay's

### 5.6 The missed Perspective press (D-76 item 3)

Reproduced on a small drawing (an 80 x 60 du rectangle, real OS input):

- **What the missed press changes:** the selection only. A Perspective drag that starts off the handles is a marquee
  (SI-188, as Select's): `draw.selection.set {by: rect, mode: replace}`; with nothing inside, the selection empties and
  the box goes (`toolBox` absent). The current element and the tool are unchanged; no undo step.
- **A person is not stuck:** a marquee drawn around the shape with Perspective still active selects it again, the box
  returns, and the next corner drag commits `draw.envelope.apply` ("Perspective Tool"). A press where a handle used to
  be is a marquee, not a handle.
- **Why the window differed from the kernel test:** the measuring script, not the product. After each drag it ran
  `edit.undo`, even after a drag that committed nothing: after the missed press (a selection change, no step) the undo
  removed the 50,000-point stroke, so the next Perspective press found no selection (`drawing.noTarget`); later undos
  removed the drawing and then the element (`drawing.notVectorElement` for Reposition All). Reproduced exactly: four
  undos after a missed press remove "Perspective Tool", "Rectangle Tool", "Create Drawing" and "New Elements", and
  Reposition All is then refused `drawing.notVectorElement`. The script now undoes only a drag that committed an
  edit, and counts release-to-committed only for those drags.
- **D-39 row** "Perspective › a missed press, then a marquee and a corner drag": the miss empties the selection, the
  marquee selects the square again, the corner drag sends `draw.envelope.apply` with "Perspective Tool"; green in the
  OS form and the MCP form.

## 6. `c13_r1_persistence` LOCK-02 "0 owners" (D-76 item 4)

**A defect in lock takeover, not the test's timing.** The test (M1, `crates/executor/tests/c13_r1_persistence.rs`
lines 218-252) runs 64 trials of 8 threads taking over one stale lock at once and asserts exactly one owner. Zero
owners happens through the takeover's arbitration file (`crates/persist/src/lock.rs`):

1. `Arbiter::drop` (lines 476-483) reads that the file is still its own, **closes the file (releasing its `flock`)
   and then removes the file by name**. Between the close and the removal, a second contender's `try_take`
   (lines 440-453) finds the file existing, unprotected (`probe` gets the shared lock) and written, judges it
   abandoned and removes it; a third contender then creates a fresh arbitration file and takes the lock path; the
   first contender's delayed `remove_file` now deletes the **third's** arbitration file. (The second's removal by name
   after its probe has the same window against a file created in between.)
2. The third contender publishes its lock file and reads it back as its own, but `still_ours()` is false, so
   `acquire` (lines 602-611) returns `HeldByOther` with its own lock information, and drops the handle that protected
   the lock file.
3. Every other contender saw the lock file held while that handle was open and returned `HeldByOther`. Result: no
   owner, and a lock file left unprotected with a fresh heartbeat (the next open takes it over as stale).

On macOS this is a microsecond window between `close` and `unlink` with 8 threads spinning 5 ms apart: rare, which
fits one failure in M4. On Windows the protection is the open handle itself and the file is deleted while open
(`FILE_SHARE_DELETE`), so the same order applies. Safety holds (never two owners); liveness does not (all contenders
told "held by another" at once; in practice two instances opening the same stale project together).

**Proposed fix (not built; persistence is M1's and outside C4.4b):** (a) `Arbiter::drop` removes the file **before**
closing it (unlink while holding the `flock`; on Windows delete while the handle is open), so no unprotected file of
a live holder is ever visible; (b) `try_take`'s abandoned-file removal re-checks identity before removing (open,
take the exclusive lock, compare the open file's identity with the path's, then remove), or renames the file to a
unique name first and removes only that; (c) in `acquire`, when the read-back lock is its own but the arbiter is no
longer, remove its own lock file and retry instead of returning `HeldByOther`. Test: the existing LOCK-02 test, plus a
boundary hook (`Boundary::ArbiterTaken` exists) that pauses a holder between close and removal.

  receipt's `keyToGlyphBound` gives the control median, the bound and the margin).
- **Headless agent (D-75 item 8):** cannot read caret positions, line boxes or the edit session; it places the caret
  with `pointer` and `key`, types with `type_text`, and reads the text and runs with `draw.drawing.get`. An attached
  agent reads the session in `inspect_ui` (`canvas.textEditor`, the Text panel's role). Neither can read a pre-edit
  (composition) string: the webview holds it until it is committed. `draw.text.layout.get` is proposed to the user.
