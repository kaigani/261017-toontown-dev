### 5.3 Preview against commit, within 1 view px (PV2)

`scripts/c44b-preview-e2e.py`, **12 of 12 rows on WebGL2 and 12 of 12 on WebGPU** (`preview-webgl2/`,
`preview-webgpu/`):

| Row (Drawing view and Camera view) | Map | Distance (view px) |
|---|---|---|
| Contour Editor › anchor drag; two selected anchors | — | 0.0 (previewed anchors against committed anchors) |
| Perspective › keystone | projective | 1.0 |
| Perspective › concave corner | bilinear | 1.0 |
| Reposition All › rotation | affine | 1.0 |
| Reposition All › alternate corner | projective | 1.0 |

Method (changed during the work, declared): the fixture's ink is the box's own rectangle, so the held overlay's
quadrilateral lies on the mapped ink. The held capture's mask is every pixel darker than the background; the
committed capture's is the black unsaturated ink. What covers ink is left out of both: the eight held handle squares
(6 view px around each, positions from the summary's `toolPreview`), the selection box the Drawing view keeps under
the drag, the committed selection box (accent) and the capture's 3 px edge; 2 view px around them from the set
measured to and 6 from the set measured from. The distance is the symmetric Hausdorff distance divided by the device
pixel ratio; 1.0 is one pixel of the capture grid. Limit: for a strong projective map a 1 du line's far side thins
below the ink threshold in the held capture (SI-190's width scaling), so there the overlay's quadrilateral stands in
for it; the rows still check every map kind against the commit. `--recheck <dir>` recomputes a run's distances.

### 5.4 Budgets (D-33 form: n, p50, p95, max from the population; release build, real OS input, 60 Hz display)

| Quantity (plan §5.5) | Bound | WebGL2 | WebGPU | Verdict |
|---|---|---|---|---|
| Drag feedback, input to ink | ≤ 16.7 ms p95 | Contour 0.7 (n 653), Perspective 0.3 (n 710), Reposition 0.3 (n 709) | 0.9 (655), 0.5 (712), 0.5 (714) | pass |
| Release to committed, small drawing | ≤ 50 ms p95 | Contour n 30, p50 25.7, p95 33.1, max 33.2; Perspective 30, 27.3, 32.5, 33.6; Reposition 30, 25.5, 34.4, 34.5 | Contour 30, 26.9, 33.8, 34.3; Perspective 30, 26.7, 34.9, 35.3; Reposition 30, 27.1, 32.9, 34.4 | pass |
| Work per frame during drags | ≤ 8 ms p95 | 0.2 / 0.2 / 0.2 (n 1322-1325) | 0.3 / 0.3 / 0.3 (n 1322-1328) | pass |
| **Keystroke to glyph** | ≤ 33 ms p95 | **n 30, p50 30.0, p95 34.8, max 36.6** | **n 30, p50 26.5, p95 34.7, max 35.2** | **fails** |

**Keystroke to glyph does not meet its bound** (ten runs on this machine during the work, p95 30.6 to 35.2 ms; one passed). Where the time goes,
from the canvas's new stage metrics (WebGL2 run, p50 / p95 from the key's timestamp): the engine's event 6.3 / 8.9;
the `text_input` answer 12.1 / 17.9; the scene's answer 12.5 / 18.2; the drawing applied 29.6 / 34.2. The engine's
own work per keystroke is about 2 ms (measured in a kernel test: input 1.2 ms, payload 0.8 ms, scene 0.1 ms), the
host's `canvas_load` about 1 ms (timed in the host), and the page's main thread is idle 92 % of the time while typing
(a CPU profile over the debugging port). The rest is the webview's IPC delivery: answers arrive just after a frame,
so the drawing is applied one frame later; the glyph lands two frames after the key, which is the bound itself. A
prefetch of the drawing with the scene request was built, measured (no change) and removed. Options for a ruling: the
bound as "two frames at the display's cadence", or the glyph's geometry pushed through the event channel (events
arrive in about 3-7 ms), a design change.

### 5.5 The 50,000-point case (reported, not asserted: D-75 items 2 and 6; M11 C11.1)

A pencil stroke of 50,000 points with straight segments (`fit: false`) on its own layer:

- Kernel (release build, `canvas_drawing`): the stroke's payload is **17.3 MB and takes 4.0 s** to build at bucket 0
  (3.99 s at bucket -1); `draw.repositionAll.apply` itself 0.54 s; `draw.stroke.add` 0.42 s.
- Window (WebGL2): a Contour Editor anchor drag committed and was drawn **36.0 s** after the release (one drag;
  `measure-50k-webgl2/`). The Perspective and Reposition All rows did not commit in the scripted run: after a
  Perspective press that missed the box (a selection click), the next presses were refused with `drawing.noTarget`,
  and the Reposition All presses with `drawing.notVectorElement`. A kernel test of the same sequence (a missed
  Perspective press, then a Reposition All drag) commits; the window's sequence is **not diagnosed** and is listed in
  §8.
- The 150 ms bound of the plan is far away for this drawing: the payload's size (about 345 bytes per point) and its
  build time dominate. For M11 C11.1.

## 6. Defects found on the way (fixed, declared)

- The canvas's text editor never attached its listeners (its effect ran before any session existed).
- The Tool options page's line properties read a `drawingId` that `draw.selection.get` does not return.
- The Text panel's role was stale after a command (the kernel now notifies when the session stays).
- The Camera view's Perspective preview left the ink in place (the split load asked for a Drawing-view selection the
  Camera scene does not carry).
- The canvas did not count Perspective's and Reposition All's drag feedback (their map is the feedback).
- The measuring script read ring buffers by count (a full ring mixed rows), had no window to send input to, and added
  no 50,000-point stroke (`smoothing` is not a parameter).

## 7. For a person, and what a headless agent cannot read

- **Manual scripts:** `reviews/manual/M4/C4.4b-text-input-method.md` (input methods, dead keys, composition, on
  Windows and macOS) and `reviews/manual/M4/C4.4b-tools-pen-and-macos.md` (the four tools with a pen or tablet, and
  on macOS: Option as the alternate, ⌘ as temporary select, the Text tool's keys).
- **Headless agent (D-75 item 8):** cannot read caret positions, line boxes or the edit session; it places the caret
  with `pointer` and `key`, types with `type_text`, and reads the text and runs with `draw.drawing.get`. An attached
  agent reads the session in `inspect_ui` (`canvas.textEditor`, the Text panel's role). Neither can read a pre-edit
  (composition) string: the webview holds it until it is committed. `draw.text.layout.get` is proposed to the user.
