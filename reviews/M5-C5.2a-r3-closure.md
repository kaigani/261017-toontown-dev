## Findings
### C52A-R3S-01 - P2 - Snapshot pruning leaves the same document in back
Citation: E-73(3), reviews/M5-C5.2-plan.md:388-391 requires a memory
budget weighing what each kept revision really holds alone.
Path: session.rs:159-178 counts and clears only RevRecord.before; the
RevRecord.back field (session.rs:43) is neither counted nor cleared.
run.rs:563-565 gives every checkpoint restore and its undo/redo a
Back::Snapshot clone of precisely the same before document. doc.rs:1487
explicitly uses that document after before is cleared.
Concrete sequence: on a crowded drawing, create two checkpoints differing
in a note, then alternate restoring them for 300 committed changes. Each
restore retains the previous document/index in back. Once the 256 MiB
budget is exceeded, clearing before cannot release that document because
back still owns it. Continue restoring: snapshots older than the 256
window also retain their indexes, up to the record-retention limit (and
last-save retention). The displayed/counted snapshot total can fit while
the log still holds all these documents. This defeats the new memory
bound; it is separate from the explicitly deferred undo snapshot issue.
The same budget also omits owned back-patch values and earlier_revs.
No crash is asserted; the concrete defect is failure of E-73's bound.

## Observations
- Case 1: heap.rs:38-43 counts string capacities, array capacities and nested
  heaps; numeric values are inline (no arbitrary-precision feature enabled).
  Objects include entry storage, index buckets and key capacities. Many small
  strings and nesting retain their container/node costs; map capacity is
  inferred from length, not directly measured. Excess retained map capacity
  could be underestimated for a manually depleted Value, but no new product
  path producing that shape in held patches was established.
- history.rs:154-160 records one cached step size; extend_top and replace_edit
  recompute it and adjust the parallel sizes/bytes accounting. Replay defers
  pruning until fixed replay indices have been consumed.
- c52a_history_size.rs:107-162 measures freed history allocations and checks
  held/count within [1/1.5, 1.5] for small notes, medium notes and large strokes.
  An estimate several times too low fails that assertion. This is inspection
  of the test, not evidence of a run. Snapshot sole ownership remains E-73(2).

- Case 2: ordinary before eviction preserves records and back-patches, so
  doc.diff reconstructs exactly (doc.rs:1480-1504), rather than claiming a
  lost revision succeeded. The allocator test checks ordinary note edits,
  not Back::Snapshot eviction (c52a_history_size.rs:183-219).
- expectRev compares live object revisions, independent of snapshot retention
  (run.rs:498-528); mismatches return rev.conflict (11:484). doc.state.get
  takes no historical-revision parameter (A:1026), reports current state
  and historyFromRev. Bases outside retained records fail doc.diffUnavailable
  (doc.rs:1471-1478; 10:1115-1117). Budget eviction alone changes no base.
- The newest before is kept even over budget (session.rs:173). Calls are
  serialized on the document thread; batches stage their own documents and
  check expectations before commit (run.rs:1892-1895, 711). Snapshot eviction
  does not invalidate their base or any record needed for reconstruction.

- Case 3 / R2S-01 closed: host.rs:899-904 pauses after the document-thread
  snapshot; after replacement flush installs B (lib.rs:1083-1091), read
  compares under the same state lock and returns stale with empty lists
  (thumbnails.rs:210-215). It cannot restore A or queue its drawing.
- R2S-02 closed: thumbnails.rs:299-333 checks, caches and sends while holding
  the lock follow takes. A paused beforeSend prevents replacement flush from
  finishing. A's notice enters the bus before replacement events and reply;
  if replacement acquires the lock first, A's completion is discarded.
- Generation assignment is confined to installation's follow and new project
  IDs (session.rs:125). Closing uses the explicit 0 sentinel; the next
  installed project has a fresh increasing ID. Reads/cached/keep only compare
  (thumbnails.rs:212, 353, 368; derived.rs:252-261).
- Publication takes state then bus.subs (lib.rs:1224-1225). Subscribers use
  unbounded mpsc::channel (lib.rs:1002-1004), so send does not wait for a
  receiver to drain. Other bus holders only send/register; none inspected
  takes thumbnail state under bus.subs. No new deadlock or current-project
  notice loss established in the changed paths.
- c52a_thumbnails.rs:278-300 forces afterSnapshot, replaces A, then releases
  the read and asserts stale plus B-only notices. Lines 307-337 force
  beforeSend, wait for replacement's followWaits, then assert A's notice

- host.rs:875-886 rejects more than MAX_READ_ITEMS=1024 before taking a

- Remaining changed padding spends budget before resizing (cell.rs:1945,
  timing.rs:218). Media matching now indexes old sequences and consumes
  each candidate once (timing.rs:353-387), preserving exact-first then
  stored-order fallback; map operations add logarithmic lookup cost.
