## 2. Architecture

1. **Render list** (`crates/executor/src/commands/render_list.rs`, new): for (scene, frame, camera, output size) it walks
   the scene tree, evaluates every node once through `tt_anim::eval::Evaluator` (the C3.2 work account, ADR-0019), and
   produces `RenderList { frame, camera, width, height, entries }`. Each entry: element, kind, role, exposed drawing (or
   bitmap), world matrix, depth (world Z of the origin), Timeline rank, the 2-D map drawing units → output pixels
   (elements lie in planes parallel to the table plane — rotation is about Z only — so the perspective projection of an
   element's plane is affine: three projected points fix it exactly), camera-space bounds, and visibility verdict with a
   reason. Order (SI-106): role tier (background, normal, foreground; 04 §6.1) → world Z ascending (05 §2.8; ties within
   1e-6 field) → Timeline order (displayed rows bottom to top: index 0 of a level is the front, a parent's row above its
   children). Visibility exactly as `anim.evaluate` (SI-100): hidden element or hidden ancestor, annotation elements,
   no exposed drawing, plane at or behind the near plane. Effects pass the transform through (M7); bones none (SI-097).
2. **Rasteriser** (`crates/render`): one additive item, `Item::Layer { transform: [f64; 6], items }`, so each element's
   drawing items stay in drawing units and vello applies the element's affine (anisotropic stroke widths and skew come
   out right). The drawing content builder of `draw_render.rs` is shared (made crate-visible and parameterised by a
   drawing → pixel map); `draw.drawing.render` keeps its exact current path, so the M2 `c23_render` goldens do not move.
   Bitmap nodes (SI-105): decoded once per render (`tt_render::decode_png`), drawn as `Paint::Image` over their quad.
3. **Encoding**: PNG through `tt_render::encode_png` (no metadata, deterministic); JPEG/TGA/BMP through the workspace
   `image` crate in `tt-io` (pinned, pure Rust).
4. **Never block**: every render charges a `Work` account (path elements + pixels / 1024, the M2 rule) and observes
   the caller's cancellation inside the rasteriser (`keep_going`); requests over the pixel or frame limits are refused
   before work starts (`limit.exceeded`); `render.range.run` runs as a job off the document thread on a snapshot, with
   per-frame progress and cancellation (`job.cancel` deletes staged files).

## 3. Decisions to record

- **ADR-0020 (new) — compositor and render list**: the order, visibility, affine-per-plane projection, the layer item,
  sharing of the drawing builder, the bitmap rule, encoding, never-block budgets, determinism gates.
- **SI-105 — bitmap placement and native size**: a bitmap node's local space is y-up with the image's top-left at the
  origin, the image covering `[0, width] × [−height, 0]` in pixel units; `transform` maps it to drawing units (this is
  how the M1 fixture's `[1, 0, 0, 1, −960, 540]` places a 1920 × 1080 image centred and upright). *Native size* is the
  scale `1200 / cameraWidth` du per pixel, so through the default camera one image pixel covers one output pixel
  (05 §1.3); 100 du per field is unchanged. Importers (M10) write that scale; the renderer honours any stored transform.
- **SI-106 — composite order**: role tier → world Z → Timeline order; background elements extend their last exposure
  to the scene length at render time (04 §6.1); envelope elements draw as normal until bones (SI-097).
- **SI-107 — `render.frame.run` coverage**: compositions, `quality: "draft"`, `cameraFrame` (draws the camera frame
  outline only for compositions larger than the frame; a no-op for `camera`), `cameraId` (extension so `render_frame`'s
  `camera` keeps its meaning), overlays never drawn in final renders (06 §6.10).
- **SI-108 — contact-sheet labels and layout**: built-in vector digits, label band height, gaps, background.
- **SI-109 — coordinate-space names** for `convert` and `hitTest` beyond 11 §5.3 (`local`, `parent`, `field`,
  `cameraNormalized`), and what `drawing` needs (`elementId`).

## 6. Golden-image strategy

- **What**: a small set of fixture scenes built by commands in the test (no text, no fonts): vector art with fills,
  brush and pencil strokes, gradients, a texture and a bitmap; nested/mirrored/skewed pegs, pivots, depth ties, roles,
  arbitrary roll, a dynamic FOV, near-plane culling; at fixed frames and sizes; plus a contact sheet and a range.
- **Where**: `crates/executor/tests/golden/c33/<name>.png` with `index.json` (name, frame, size, sha256, bytes).
- **Recording**: `TT_UPDATE_GOLDEN=1 cargo test -p tt-executor --test c33_goldens` rewrites the PNGs and the index; a
  normal run compares bytes and, on mismatch, writes the actual PNG and a diff summary under `target/c33-golden-diff/`.
- **Cross-OS byte identity**: the same committed files are compared on Windows and macOS (`check`, debug) and in release
  (`c33 render release`, both OSes); the release job also renders the goldens through the real headless binary over MCP
  (`scripts/c33-render-gate.py`) and a `c33 cross-OS` job compares both OSes' artefacts byte for byte (as `e4 cross-OS`
  does). Attached versus headless: the desktop host's in-process executor path is the same code; the gate renders the
  goldens through the desktop host crate's invoke path in its Rust tests as well, where the toolchain allows (§8).
- **A legitimate change**: re-record with `TT_UPDATE_GOLDEN=1`, and declare it in the handoff (§3 declared edits) with
  old and new sha256 per file and the cause; no golden changes silently.
