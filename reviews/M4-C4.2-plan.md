  `draw.erase.apply`, `draw.cut.apply`, the paint commands. Their prechecks and the availability inventory

  shipped in C4.1 (reviews/M4-C4.1-plan.md:167-168); C4.2 adds the tool keys to `key` (C4.1 plan line 220).
- **Renderer.** The final renderer and the compositor's render list (ADR-0006, ADR-0020) render headless and are
  byte-deterministic across OSes. The interactive canvas exists only as the C0.3 spike (`desktop/src/spikes/canvas`:
  WebGPU and WebGL2 back ends, the TTRL v1 spike format, the log analyzer) plus ADR-0007's decisions and open questions.
- **Tablet.** ADR-0009 chose nothing (line 68); product tablet code waits for physical-pen evidence (lines 214-220).
  C4.2 builds the single input-source abstraction (lines 70-72) on pointer events; native sources wait for the evidence.
- **Registry drift fixed in passing:** `crates/registry/src/owners.rs` maps `view` to C4.1 (line 95), `inspect.ui.tree`
  to C4.2 (lines 74-75, delivered in C4.1) and `drawAid` to M2 C2.3 (line 98); the `pointer` not-implemented message
  names "M2 C2.3" (C4.1 handoff line 128).

## 3. Architecture

### 3.1 One rule, kept from C4.1

The kernel owns every document and session change; the webview renders and collects input. A gesture in progress is a
local overlay (ADR-0007 decision 1; 06 §6.9) and ends in exactly the registered command an agent would send (02 §13.3;
10 REV-06). The interactive renderer is a preview: exported pixels come only from the final renderer (ADR-0006; 06
§6.10).

### 3.2 Render-list transport (part A)

- **Product format.** A versioned binary format replaces TTRL v1 (ADR-0007 decision 4): a header validated against its
  schema, byte lengths checked against counts, one encoder in Rust and one decoder in TypeScript with a shared corpus of
  golden byte files (decoded by Vitest, encoded by `cargo test`), unknown major versions refused.
- **Identity and revisions** (questions 1-2): resident entries keyed by drawing id and the drawing's `rev` (REV-02); a
  delta names the revision it applies to; a mismatch resyncs that drawing, never applies silently.
- **Deltas and backpressure** (question 3): per frame, transforms coalesce (latest wins); geometry, deletions and
  resyncs are never dropped; the queue to the webview is bounded (64 messages, stated and measured); when it is full
  the host coalesces instead of growing it.
- **Tessellation placement** (question 6): pre-tessellation in Rust (stroke outlines, triangulated fills), so the webview
  decodes and uploads only and the IPC boundary's no-worker rule stands (no ADR-0001 amendment); measured and recorded
  as an ADR-0007 amendment.
- **Painter order and strokes** (question 7): the render list's order, real caps and joins, zoom-dependent flattening in
  Rust per zoom bucket.
- **Eviction** (question 5): a resident-memory budget per back end from 06 §6.9's caps; off-screen drawings evicted
  least-recently-used and rebuilt from the render list.

### 3.3 Frame loop (part A)

`requestAnimationFrame` drives one frame: apply the deltas received since the last frame, within a work bound per frame,
draw resident drawings in render-list order, then the overlays in 02 §4.2's order. WebGPU and WebGL2 ship with the same
features; the canvas rule set chooses (≥ 57 fps per cell; at first launch and after a GPU, driver or webview change;
user override in preferences). No frame waits on IPC.

### 3.4 Views and coordinates (part B)

One view state per view panel (SI-112: the four panel ids) in the kernel's UI state (not undoable, 02 §12.1; persisted
per workspace): zoom, pan, rotation, flip, type. `view.*` change it; the canvas follows the announced state. The mapping
drawing ↔ view pixels is one pure function in Rust, used by the kernel and sent to the canvas as a matrix (the canvas
never derives it on its own), queryable through `view.transform.get` and `view.coordinates.convert`. View space becomes
available to `colour.pick`, hit tests and `view.coordinates.convert` (SI-065, SI-109); `draft` quality and the
`activeView` composition are settled for the Drawing view (SI-107).

### 3.5 Tools and gestures (part C)

- **Tool state** in the kernel (`tool.active.set`, `tool.group.select`, options, pens; user scope except pens, which are
  project scope, 02 §12.3). The rail, the keymap and the `key` tool reach the same commands.
- **Gesture code in Rust.** The mapping from a gesture (press, samples as given, release or cancel) to the equivalent
  command lives in Rust, used by the webview through IPC and by the headless `pointer` path, so both produce the same
  command. The webview keeps only the overlay and the sample collection. The view mapping is taken at the press (02
  §13.3); navigation is refused during a gesture; the pen's eraser end gives a temporary Eraser (§5.2). On release the
  command states every current setting explicitly (02 §13.3 lines 1202-1203) and is invoked once: one undo step labelled
  with the tool's name.
- **Busy arbitration** (11 §6.4): from press to commit the session is "user mid-gesture" (C4.1's `ui.busy` mechanism).

### 3.6 `pointer` (part F)

Attached: agent events enter an input queue per view on the front end that serialises agent and user gestures (an agent
gesture never interleaves with a user's; a user press during an agent gesture cancels the agent's with a typed error).
Headless: the kernel's virtual view (SI-069) and the same Rust gesture code. `dt` is simulated time. Result: the envelope
of the commands produced and the final hover information.

### 3.7 `screenshot` (part F)

Attached: the webview captures its canvas and chrome region to PNG; headless: the virtual view rendered by the software
rasteriser (11 §3). `{png, width, height, sha256}`; inline limits 2048 px and 8 MB; `region` in view pixels.

## 4. Design notes before code (each pushed before its code; one builder test per invariant)

1. **`M4-design-render-transport.md`.** Invariants: (T1) a resident drawing is never shown at a revision other than the
   one the kernel announced last, except during a resync, which shows the previous one; (T2) geometry, deletions and
   resyncs are never dropped or reordered with respect to each other; (T3) the queue never exceeds its bound;
   (T4) encode/decode round-trips the golden corpus byte for byte; (T5) evicted drawings are rebuilt identically.
2. **`M4-design-frame-loop.md`.** (F1) a frame's delta work is bounded; (F2) no frame awaits IPC; (F3) the overlay order
   is 02 §4.2's; (F4) the back end is the rule set's output for the measured cells.
3. **`M4-design-gestures.md`.** (G1) one gesture ends in exactly one command (or none when cancelled); (G2) the command
   from the webview path and from the headless `pointer` path are equal for the same samples and settings; (G3) the
   mapping is the one at the press; (G4) one undo step with the tool's label; (G5) a gesture's samples are applied as
   given; (G6) navigation during a gesture is refused.
4. **`M4-design-pointer.md`.** (P1) agent and user gestures on a view never interleave; (P2) a user press cancels an agent
   gesture with a typed error and leaves the document unchanged; (P3) `dt` never reads the wall clock; (P4) agent
   mutations during a user gesture wait at most `waitForUserMs`, then `ui.busy`.
5. **`M4-design-screenshot.md`.** (S1) the PNG is decodable and its sha256 matches; (S2) the inline caps are enforced
   before encoding; (S3) the headless and attached calls take and answer the same shapes.
6. **`M4-design-views.md`.** (V1) one mapping function, identical results in kernel and canvas for the same state (the
   canvas receives the matrix); (V2) view state is not undoable and persists per workspace; (V3) "let the agent move my
   view" off refuses agent view changes with a typed error.

## 5. Tests

- **Kernel (`crates/executor/tests/c42.rs`, one binary; an isolated binary only for process-wide quantities):** every
  `view.*`, `tool.*`, `drawAid.*` command; the mapping function; the gesture-to-command mapping per tool; `pointer` and
  `screenshot` headless; the render-list encoder against the golden corpus.
- **Wire level:** every new IPC message and MCP tool through its real serialisation (absent, `null` and cleared values
  distinguished), both directions across the boundary.
- **Gesture equivalence per tool (02 §13.3):** a recorded gesture through the webview (attached e2e), through `pointer`
  headless, and the equivalent command sent directly: `draw.drawing.get` identical within 1e-6 du, the same ids, one
  undo step with the same label; the saved project bytes identical.
- **Front end (Vitest):** the decoder, the overlay and sample collection with a fake clock, the back-end rule set.
- **Running application on both CI OSes:** the C4.1 e2e harness extended with tool gestures, aids, navigation,
  `pointer`, `screenshot`; receipts kept.
- **Portable:** every test runs on Windows and macOS; any platform-specific executable or API behind a `cfg` split.

## 6. Budgets (asserted with a monotonic clock, CI-safe margins, no sleeps inside bounds)

"Small" is the sample document's drawing; "large" is a drawing of 50,000 points (brush strokes) built through commands.
Margins: CI runners measured about 1.6 times slower than the workstation in C4.1, so asserted bounds are at least twice
the workstation's measured value or the stated limit, whichever is lower.

| Quantity | Small | Large | How measured |
|---|---|---|---|
| Interactive frame time, Drawing view, idle and during a gesture | ≤ 17.5 ms p95 (≥ 57 fps, ADR-0007) | ≤ 17.5 ms p95, or the rule set's fallback row recorded | attached e2e, `performance.now()` per frame over 300 frames, both back ends |
| Input-to-ink (sample received to overlay drawn) | ≤ 1 frame (16.7 ms) p95 | ≤ 1 frame p95 | front-end timestamps on the sample and the frame |
| Release-to-committed (pointer-up to the committed drawing rendered) | ≤ 50 ms p95 | ≤ 150 ms p95 | e2e: pointer-up to the render-list delta applied |
| Document-thread hold per request (render-list production, deltas, view commands) | ≤ 20 ms | ≤ 20 ms | `availability_holds`-style hold measurement in `c42.rs` |
| Render-list host memory for one drawing | measured | ≤ 64 MB for 50,000 points | counted bytes of the encoded list in `c42.rs` |
| Resident GPU memory | within 06 §6.9 caps | within 06 §6.9 caps | back-end counters in the e2e |
| Delta queue length | ≤ 64 | ≤ 64 | counter in a `c42.rs` and a Vitest test |
| Full resync of the large drawing | — | ≤ the C0.3 envelope re-measured on the product format (transfer + decode) | e2e |

## 7. Experiments and the back-end decision (ADR-0007)

ADR-0007 names E-C1 to E-C3 without pass criteria. Proposed criteria, recorded in the ADR with the results:
- **E-C1** (host-driven deltas, groups1k-like scenes, transforms from Rust every frame): delivery latency p95 within one
  frame; ≥ 57 fps on both CI runners' software paths and on the workstation's GPU; coalescing never drops geometry or
  deletions (counted).
- **E-C2** (sustained edits, dirty-drawing re-tessellation and upload, resync): a dirty large drawing re-tessellates and
  uploads without a frame over 33 ms; a full resync of the large drawing within the re-measured envelope; brush10k
  re-measured (rule row 4).
- **E-C3** (GPU-less machine or VM; webview software rendering against tiled host bitmaps): the software path holds
  ≥ 30 fps on the rule-set scenes, or the comparison picks tiled host bitmaps; result and choice recorded.
The back-end decision is the rule set's output per machine class.

## 8. Availability (part H)

- Every new command (`view.*`, `tool.*`, `drawAid.*`, `inspect.screenshot`) enters the inventory with its refusals
  classified; every state refusal gets a precheck and both states in the second sweep.
- **Rows the Drawing view or C4.2's commands make constructible, to be built in the sweep:**
  `draw.centreLine.apply` / `drawing.centreLineOnFill` (closed strokes and a paint, buildable through commands today:
  the row's "untestable" is withdrawn in C4.2). Not made constructible by C4.2, and why: the three
  `colour.fillMapping.set` rows and the copied-mapping row (a texture swatch; no palette command is implemented); the
  three `colour.noCurrentColour` rows (no command empties a palette); the two image-element rows (an image import); the
  two image-clipboard rows (M10); the 31 "current element" and 13 + 2 "current scene" rows (a project always has both).
- **The `deferred` row** (`element.mediaLength.set` / `command.disabled`: the natural length needs the media decoder,
  M8 C8.3) is not a Drawing-view state; I propose it stays deferred to M8 C8.3 (ruling requested, since the C4.1 pass
  message names me as its owner now).

## 9. UI conventions (bound for M4 to M7)

The tool palette is the left vertical rail (02 §5.1 groups, one button per group showing the last-used tool); view
toolbars inside their view; workspace toolbars at the top; tool options in the Properties panel; pens and text in the
`pen` and `text` panels (01 §5.2); the status bar shows the pointer in drawing space (02 §2.2). Where the spec is silent
(rail placement and order, a Drawing-view toolbar, the static light-table panel's place while the Exposure Sheet is M5,
aid controls beyond the toolbar items, cursor shapes) a spec issue records a conservative default.
