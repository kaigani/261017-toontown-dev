## C02-R1-08 — macOS NSEvent accessors — **fixed**

`native_macos.rs` reads each accessor only for the event types its documentation lists:
- `subtype` only for mouse events;
- `pressure` only for mouse down/up/dragged and `TabletPoint`, never for `MouseMoved` (hover) or proximity;
- tablet fields (tilt, rotation) only for `TabletPoint`, or for mouse events whose subtype is `TabletPoint`.

`convert`, the part compiled by the reviewers' contract test, uses only the prelude's types. The contract test
passes.

As ruled, also:
- **raw tilt** (`NSEvent.tilt`, −1..1) is logged next to the converted degrees (`rawTiltX/Y`);
- **right and other mouse buttons** are in the event mask and converted (`convert_button`);
- the **proximity tool** (pen/eraser/cursor) is kept in `CURRENT_TOOL` and labels later poses, so an eraser is no
  longer reported as `pen`;
- **conversion inputs:** `windowNumber` per packet, `deviceID` for tablet events, and the window geometry with
  backing scale in the listener's start info and in the log environment;
- the host buffer's drop counter and the channel's send-failure counter travel with every batch (`hostDropped`,
  `sendFailures`).

The first push failed macOS clippy on one unused import; fixed in `f0d00e8`, and run 39111989749 is green on
`check (macos-latest)`.

Not claimed: AppKit execution. The tests are contract doubles. Real event delivery, exception behaviour and
coordinates remain pending the user's run (handoff, known gap 2).

## C02-R1-02 — Windows frame/pose association — **fixed**

The `pump` function in `native_windows.rs` now holds packets in a thread-local group until the `ToolEvent::Frame(t)`
that terminates it arrives. That can happen in a later pump. Every held packet then gets that frame's time. The
reviewer's deterministic replays (`Pose, Frame(100), Pose, Frame(104)` → `[100, 104]`; one packet per pump across
three pumps → `[100, 104, 108]`) pass against the unchanged production body.

Clock domains are explicit:
- `NativeStartInfo.deviceClock` names the domain of `deviceMs`;
- the page and the analyzer use **one clock per summary**: the device clock if every contact packet has it,
  otherwise host wall time, and never a mix. A test covers the switch.

## C02-R1-01 — logs — **fixed**

- **Version 2** (`TabletSpike.tsx`, `LOG_VERSION = 2`). The analyzer accepts versions 1 (or no field) and 2, and
  rejects anything else with exit status 2 (`analyzer.test.ts` checks version 3).
- The log contains:
  - every run's **raw host report** verbatim (`runs[].report`; also `simulations[].report`, as the reviewer test
    expects), or the raw probe result for native-window runs;
  - **run boundaries** as index ranges into the raw streams (`webRange`, `nativeRange`), with `perfStart`/`perfEnd`
    and the **requested geometry** (`request`);
  - `performance.timeOrigin`;
  - **environment:**
    - user agent, `hardwareConcurrency`, DPR, screen and viewport;
    - `navigator.gpu` adapter info (vendor/architecture/device/description; `available: false` on the runner);
    - from the host (`spike_environment`): OS build (`ver` / `sw_vers`), WebView2/WebKit version
      (`tauri::webview_version`), CPU count and window geometry;
  - **pointer ids** (web `pointerId`; native `seq`, `tool`, `deviceId`);
  - **truncation and channel counters** (`web.truncated`, `native.truncated`, `hostDropped`, `sendFailures`,
    `invalidBatches`).
- **The analyzer recomputes every number from the raw samples.** It never reads the stored summaries;
  `analyzer.test.ts` plants wrong summaries and still gets the page's results.
- **The injection time is taken before the inject call** (`simulate_windows.rs`); the return time is recorded too.
  On the runner, the call takes p50 0.03–0.05 ms.
- **Latency estimator stated, all three reported** (handler time − event time). Over all web samples of matrix 2,
  p50 / p95 ms:

  | Estimator | p50 / p95 ms |
  |---|---|
  | oldest coalesced sample per dispatch | 13.9 / 16.0 |
  | newest sample per dispatch | 2.1 / 4.3 |
  | all samples | 8.0 / 15.1 |

  The readout labels them as such. Synthetic runs add event − injection and handler − injection for the first
  sighting of each frame.

## C02-R1-03 — contact episodes — **fixed**

- **Segmentation before rate/gaps:**
  - web: pointerdown .. pointerup/pointercancel per pointer id;
  - native: `down` or the first pose with pressure .. `up`, proximity-out, or a pose whose pressure returns to 0.

  The page (`analysis.ts`) and the analyzer apply the same rules. The reviewer's three cases pass, including
  pose-only AppKit input (`native path: 2 strokes`).
- **Per-stroke results** appear in both places: the live readout's stroke table (last 6 strokes, `*` = cut off by
  the window) and the analyzer's Markdown tables.

  "heuristic" everywhere. Loss is reported only against a reference:
  - for synthetic runs: injected frames − received, with the missing indices;
  - for the native channel: host sequence numbers. The analyzer labels that loss "host-to-page channel loss only"
    explicitly.

  Otherwise the loss reads **`unknown, gap heuristic only`**.

## C02-R1-04 — C0.4 conclusions — **fixed**

The handoff's findings are rewritten with both of the reviewer's qualifications:
- **(a)** zero RTS packets from a synthetic device does not show that an in-process listener cannot see real pen
  input;
- **(b)** the Safari 18.2 API dates do not establish Mac tablet value delivery. Wacom's Safari 15 results and
  WebKit's `WebEventFactory.mm` force source are cited as evidence the other way.

The discriminating experiment ran in the non-blocking CI step, synthetic only. The same injector and the same RTS
manager were aimed at:
- a plain same-process native window, recording WM_POINTER with pen history and RTS together, and then without RTS;
- the current webview, with RTS on the main window.

A raw-input listener for the HID digitizer page (`WM_INPUT`, `RIDEV_INPUTSINK`) ran as the third listener in every
run.

The full matrix is in the handoff. What it shows:
- **RTS sees injected input on a plain window**; there, RTS and WM_POINTER together account for 1024/1024 frames
  (RTS takes over after 0–23 frames);
- **RTS on the webview window: 0** in every run;
- **WM_POINTER alone on a plain window: 1024/1024**, sine and stationary;
- **raw input: 1046 reports in every run** (one per injected frame, hover included), webview runs included. The
  contents are not decoded.

The handoff draws no native-path conclusion beyond that. It names raw input and RTS on a dedicated window as the
candidates for a one-tablet test, and states that no architecture choice follows.

**Locally:** checked first, never dismissed. The two Windows Security prompts (`PickerHost`, since 2026-10-17 17:11
and 17:55) are still open, so the experiment ran only on CI: matrix 1 = run 39111452505, matrix 2 = run 39111989749.
Logs are in `reviews/evidence/M0-C0.2/tablet-spike-windows-runner-r1-matrix{1,2}.json.gz`.
