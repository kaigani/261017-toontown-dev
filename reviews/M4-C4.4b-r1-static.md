Rule: ADR-0014 section 11.4, lock.rs:14-22: a protected live lock is never removed
by a taker; LOCK-01/02 require exclusive ownership. This is a pre-existing persistence

State and Unix interleaving (each pause is between the named operations):

1. Two reapers R and S probe the same abandoned arbitration file as free. S removes

   pauses at TakeoverDecided. R's delayed remove_file(:451) unlinks D's arbiter.
2. W creates a new arbiter, removes the stale project lock, publishes and validates

## Lock takeover assessment

(a) The handoff's zero-owner explanation is correct: drop checks token, closes the
arbiter protection, then removes by name. A free-file reaper can remove it first,
a new publisher can create a replacement, and the delayed unlink can delete that
replacement. Its publisher reads its own lock but fails still_ours; other contenders
already saw that lock protected and returned HeldByOther. Nobody retains ownership.
The same name race exists with share-delete handles on Windows.

(b) Its universal safety claim is not correct on Unix: finding 07 gives a delayed
stale decision which unlinks a newly protected owner. flock protects an inode, not
its pathname. There can be two returned Acquired handles before the old owner next
checks its fence. On Windows, delete sharing also does not forbid the unlink request;
legacy delete-pending semantics can delay recreation until old handles close, so
the Unix two-return schedule must not be claimed verbatim there. A universal safety
proof for the present cross-platform code therefore fails; token checks still help
prevent an old owner from successfully saving after detecting loss.

(c) Removing the arbiter while protection is held closes the drop window on Unix;
on Windows retain the handle through the deletion request and handle delete-pending
as contention. Reaping must acquire protection on the opened abandoned file,
compare its identity with the current pathname, and retain that protection through
unlink. All deletion paths must follow that protocol. Competing reapers must
revalidate identity after acquiring protection: an old inode lock alone cannot
authorize unlink of a replacement pathname. With those conditions and no delayed
name-removal path left, there is no overlapping live arbiter and the stale decision
in 07 cannot race another publisher. This closes both cases on local Unix/Windows
filesystems honoring these primitives; unrelated/network filesystem failures remain
fail-closed. A blind unique rename by itself is not an identity/protection proof.

(d) Do not close protection before unlink, unlink solely from an earlier probe/token
read, rename a fresh live file and then decide whether it was abandoned, or retry
after deleting a lock based only on cached ownership. The proposed acquire cleanup
must prove the current lock is its own under a valid arbiter before removal, and
must not drop its protection then remove by name. Merely adding retries at :611
does not repair the stale-decision safety defect. Test both reaper ABA and delayed
TakeoverDecided, on both systems, without assuming Windows unlink equals Unix unlink.
