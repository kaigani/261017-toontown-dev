### 1.3 `shownInTimeline` on `timeline.rows.list` rows

On the list of spec A additions for the user (`plan/spec-issues.md`, "Spec A additions proposed by M5").

**Can the window do without it? Not entirely, so it is kept, pending your ruling.** The window must draw the rows the
timing-gesture interpreter hit-tests, in the same order, or a press lands on another row than the one drawn under it.
The interpreter's rows (`timing_gesture::visible_rows`) leave out (a) the descendants of collapsed rows and (b)
effect-parameter rows their effect's setting hides (`timeline.effectParameterRows.set`, 04 §2.9, §9.4).

- (a) the window can derive from each row's `depth` and `collapsed`;
- (b) it cannot: the effect-parameter setting is session state that no query reads (`timeline.effectParameterRows.set`
  answers only the value it was given), so a window that mounts after the setting changed, or follows an agent's change,
  cannot know which parameter rows are hidden.

Alternatives, for the ruling: (1) keep `shownInTimeline` (the spec A addition); (2) `timeline.rows.list` leaves out the
rows the Timeline does not show (no new member, but the read model would no longer list every row, which 04 §17.5's
"timeline object" may intend); (3) a read of the effect-parameter setting (a new query, also a spec A addition). Until
effect elements exist (M7) no effect-parameter row exists, so today (a) alone would draw the same rows; the member is
kept so the rule does not change silently when they arrive.

## 5. Ruling E-35: the hit-zone rule

Written in the kernel note §12 and in `timeline-layout.json`'s comment: the priority where zones overlap (a keyframe in
its band, then the end column, then the start handle, then the body, then a cell; in the ruler the start marker before
the end marker) and that every zone includes its edge pixels. **The 6 px end zone is intended, not an off-by-one**: the
end column is one zone shared by the end handle (lower half) and the loop handle (upper half), whose half-width is 6;
the constants are renamed for what they are (`barHandleWidth` → `startHandleWidth`, 5; `loopHandleWidth` →
`endHandleWidth`, 6), and `zone_at` uses `endHandleWidth` for the whole column instead of `max(bar, loop)`. No pinned
pixel of `f2_pixel_zone_matrix` changes, so no authorisation is needed. Code, constants and the case table agree: the one
function `timing_gesture::zone_at`, and 322 zone cases in `timeline-geometry-cases.json` (written by
`scripts/gen-timeline-zone-cases.py`: each zone's edge pixels and the pixels just outside, every overlap the rule
orders, both halves, loopable and not, three zoom levels), checked by the kernel's unit test and by the window's
Vitest (from C5.1b, whose window files carry the byte copy).

## 7. A defect CI found on the way: `timeline.rows.list` grew with the square of the rows

Run 45139823182 (`5853903a`) failed `check (macos-latest)` at the builder's
`c51_gestures::rows_list_stays_linear_at_one_thousand_elements`: 1 010 rows took 188 ms against 1.05 ms for 20 (ratio
179, bound 150). Not noise: measured in one process, 250, 500 and 1 000 rows took 6.8, 22 and 90 ms. The cause: every row's
keyframe read (`data_of`) computed the scene length, which walks every element of the scene, so the read was quadratic
(C5.1a, round 1 had not seen it: the ratio stayed under its bound until then). Fixed: `timeline.rows.list` computes the
scene length once for all the rows' key reads and passes it with the scene's tree (`anim_common::data_in`); with the
reported length that is two walks of the scene per query, a constant (corrected under ruling E-38: this said "once");
250, 500 and 1 000 rows now take 3.0, 5.2 and 9.8 ms. The test also checks the doubling (1 000 rows against about 500, at most 3; it measures about 1.9).
