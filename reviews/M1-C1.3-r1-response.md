### Dispute: the C13-R1-03 fixture cannot be satisfied (the finding itself is fixed)

The test hand-writes the following state:
- `project.json` already holds `new-project`;
- the second temporary is missing;
- `palettes/p.json` still holds `old-palette`;
- the journal has the version-1 shape `{format, renames[{tmp, target, size, sha256}], deletions}`.

It then calls `recover_journal(…).unwrap()` and requires both entries to be all old or all new. Neither is
possible:
- **Rolling back** needs the bytes `old-project`. The fixture overwrote `project.json` directly and kept no copy, so
  those bytes exist nowhere.
- **Completing** needs the bytes `new-palette`. The only temporary holding them is missing.

So every implementation must either return an error (the `unwrap` panics), or return `Ok` and leave the files
mixed, or invent content. The test cannot pass. It encodes the defect, though, and the defect is real:
version 1 of the journal kept no old copies, so a crash after the first rename really could leave a mixed folder.

**The fix (ADR-0014 §2, `crates/persist/src/journal.rs`).**
- Before the journal is written, every entry about to be replaced or removed gets an old copy (a hard link, or a
  copy).
- The journal (version 2.0) records the new and old versions with their sizes and SHA-256 hashes.
- Recovery completes the save when every new version is present, and rolls it back when every old version is
  present.
- Anything else — which a save written by this code can only reach through outside damage — fails closed with
  `reason: "unrecoverableSave"` and changes nothing. The journal and every file stay.

The reviewer's fixture is a version-1 journal, so this version refuses it at validation (`reason: "journal"`). That
is the fail-closed behaviour C13-R1-04 asks for.

**Proof on states the save actually produces.** `crates/persist/tests/journal.rs`, 3 tests:
- `a_save_interrupted_after_any_rename_recovers_to_one_whole_version` interrupts a real folder save after 0, 1, 2,
  … renames, using the new `FolderOptions::crash_after_renames`. The save has three replacements and one removal.
  For each stopping point, it recovers either with the pending temporaries intact, or with one pending temporary
  deleted, which simulates the reviewer's lost temporary. The result is byte-for-byte the whole new folder in the
  first case and the whole previous folder in the second.
- `a_journal_whose_versions_are_both_incomplete_changes_nothing` loses a pending temporary and the old copy of an
  already-replaced entry: the state in which neither version can be rebuilt. Recovery and `load` both fail with
  `unrecoverableSave`, and the folder is byte-for-byte unchanged.
- `journals_are_validated_before_anything_changes` covers eight malformed journals: wrong format or version, path
  escapes, old copies outside the entry's folder, control-file targets, nested drive prefixes, bad hashes, and a
  non-object journal. Each fails with `reason: "journal"`, and the user's content and the journal stay.

**Requested ruling.** Either:
1. accept the replacement fixture — the reviewer's state written as a version-2.0 journal, with
   `old: {file: ".project.json.x.old", …}` present on disk — and expect the all-old result; or
2. keep the test as written, with an explicit statement of which result is required.
