## Findings

### C02-R1-08 — P1 — The macOS converter violates NSEvent accessor preconditions

**Locations:** `desktop/src-tauri/src/spikes/tablet/native_macos.rs:142`, `:155`; event mask at `:42`. Requirement: plan §2.3 native fallback; the handoff's claim that it calls only valid accessors; manual strokes C/E.

The converter unconditionally reads `e.subtype()` after admitting a native `TabletPoint`. Apple's [subtype contract](https://developer.apple.com/documentation/appkit/nsevent/subtype) permits mouse and specified system/application/periodic events, and documents an exception otherwise. It also reads `e.pressure()` for an ordinary `MouseMoved`; Apple's [pressure contract](https://developer.apple.com/documentation/appkit/nsevent/pressure) lists mouse down/up/drag, tablet-point and pressure events, excluding ordinary mouse movement. Both events are admitted by the monitor. Moving the mouse after starting the listener, or receiving a native tablet-point while changing pressure without moving, therefore reaches a documented exception path. An Objective-C exception across this uncaught callback is a process-abort risk.

**Repro/test:** `python tests/adversarial/c02-r1-tooling.py`, case `test_C02_R1_08_macos_accessor_contracts`, compiles the **unchanged production `convert` and `device_name` bodies** against [contract-enforcing event doubles](../tests/adversarial/c02-r1-macos-accessors.rs). Both bad-access cases fail; proximity is a passing control. This establishes invalid calls against the documented contracts, **not an observed AppKit crash**: this reviewer has no Mac. Source snapshots `apple-pressure.md` and `apple-subtype.md` preserve Apple's Markdown documentation. Before the user run, add actual AppKit event tests and avoid these accessors for unsupported event types. Native tablet-point delivery is not hypothetical API coverage: [Apple's tablet-event guide](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/HandlingTabletEvents/HandlingTabletEvents.html) explicitly describes it, including pressure-only changes.

### C02-R1-02 — P1 — Windows native timestamps belong to the preceding frame, but are assigned to the next pose

**Locations:** `desktop/src-tauri/src/spikes/tablet/native_windows.rs:68`, `:72`, `:95`; downstream `desktop/src/spikes/tablet/analysis.ts:164`. Requirement: native/web comparison and rate/drop measurements, plan §2.3.

In locked octotablet 0.1.0, `ToolEvent::Frame(t)` terminates the **preceding** group. Its Ink backend explicitly emits `Pose` then `Frame(timestamp)` for each packet (`src/platform/ink/mod.rs:497–504`; retained in `octotablet-contract.txt`). The host instead copies the previous frame timestamp into a new pose, then updates `frame_ms` on `Frame`. Each pump resets it to `None`.

**Repro/test:** [native replay prelude](../tests/adversarial/c02-r1-native-timestamps.rs), run by `c02-r1-tooling.py`, executes the actual unchanged `pump` body with documented event sequences. `Pose, Frame(100), Pose, Frame(104)` produces pose times **`[None, 100]`**, expected `[100, 104]`. One packet in each of three pumps produces **`[None, None, None]`**, expected `[100,104,108]`. Analysis substitutes Unix wall time for null device time but uses boot/device-relative time for other poses, combining incompatible clocks within a stream. Rates and gaps become invalid when real packets finally arrive. The runner's zero-packet result never exercises this defect. Associate each pose with its terminating frame and keep clock domains explicit; zero-packet tests are insufficient.

### C02-R1-03 — P1 — Contact-rate and drop criteria count pen-up pauses as missing input

**Locations:** `desktop/src/spikes/tablet/analysis.ts:106–124`; `TabletSpike.tsx:156`; `scripts/analyse-tablet-log.py:97–105`; manual document's instruction not to Clear and its pass table. Requirement: measurable pressure/rate/no-drop criteria on the user's Mac.

### C02-R1-04 — P1 — The C0.4 conclusions overstate what the native-zero and Safari compatibility evidence proves

**Repro/evidence:** independent `EnumChildWindows`/PID observations, three CI artifact logs, captured MDN/WebKit sources and cited Microsoft/Apple/Wacom documents. ### C02-R1-07 — P2 — Offline percentile rounding disagrees with the frontend

**Location:** `scripts/analyse-tablet-log.py:27`; comparison `desktop/src/lib/latency.ts:15`. Requirement: the manual's claim that log analysis and readout show the same measurements.

Python uses `round(p*n/100 + .5) - 1`, which is not nearest-rank `ceil(p*n/100) - 1` because Python rounds ties to even. On `[1,2,3,4,5,6]`, p50 is **4**, while the frontend correctly returns **3**. Rounded handoff figures happen to agree for these distributions; that does not validate the formula.

## Evidence for C0.4

**Windows native path.** Established: octotablet 0.1.0 is an Ink **RealTimeStylus** implementation; it attaches to the host HWND; the actual rendering descendant belongs to WebView2; RTS produced zero packets in all three CI runs. Its empty startup tablet list precedes synthetic-device creation. Neither source nor the reviewed Microsoft injection documentation promises that `InjectSyntheticPointerInput` also populates the RTS tablet stream. Therefore synthetic invisibility, HWND targeting, or both remain hypotheses. I did not establish the handoff's asserted universal same-process RTS restriction independently from Microsoft documentation.

- Ordinary [WM_POINTER messages](https://learn.microsoft.com/en-us/windows/win32/inputmsg/messages) target the hit-tested/capturing window. Merely replacing RTS with a parent WndProc does not establish receipt of the complete descendant stream; pointer-down parent notification is not every update/history sample.
- [RegisterPointerInputTarget](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerpointerinputtarget) can redirect real **and injected** pen input to a caller-owned window, but requires UIAccess, permits only one global target per pointer type, and redirects rather than passively duplicates input. It is not a normal unsigned-app drop-in solution, and the injecting owner's own input is exempt from its redirection.
- [Raw Input](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input) registers HID collections and can deliver `WM_INPUT` to an input-sink HWND even in the background. Webview child-process ownership is therefore not a universal prohibition on a host native listener. Actual digitizer collection exposure, driver permissions, HID decoding and pressure/tilt quality still require a physical tablet; synthetic pointer injection is not documented as synthetic HID traffic.
- **Cheapest discriminating experiment:** the same injector and RTS manager on a plain same-process native window, then on the current webview, recording WM_POINTER history and RTS together. If bare RTS also sees zero, the original test cannot attribute zero to WebView2. Follow with one real tablet in both targets; test raw HID availability before selecting composition hosting/overlay/wintab. No injection experiment beyond the authorized covered-app attempt was performed on this machine.

**Safari/WKWebView floor.** [MDN BCD](https://github.com/mdn/browser-compat-data/blob/main/api/PointerEvent.json), [WebKit's release article](https://webkit.org/blog/16301/webkit-features-in-safari-18-2/) and [Safari 18.2 notes](https://developer.apple.com/documentation/safari-release-notes/safari-18_2-release-notes) agree: `getCoalescedEvents`, `getPredictedEvents`, `altitudeAngle` and `azimuthAngle` arrive in Safari **18.2**; BCD lists pressure/tilt/twist property support from **13**. This establishes API surface dates, not hardware value delivery. Apple Pencil/iOS examples do not establish external-tablet support in Mac WKWebView. The current Mac WebKit source and Wacom's Safari 15 results are evidence **against treating generic BCD support as proof of Mac pen pressure/tilt/twist**. Force Touch's separate pressure path is not proof of pen support; I cannot establish actual tablet values or even `pointerType=pen` on the user's WKWebView from Windows.

**Cheapest experiment:** after fixing the native monitor, run one instrumented WKWebView on the user's Mac with their tablet, logging native and web pressure/type/tilt/twist plus API presence, coalesced/predicted lengths and angular properties. Record exact macOS/WebKit/tablet/driver versions. Compare an available older-floor machine/runtime with a current one before proposing a floor change. Merely seeing the methods exist on 18.2 does not prove they return intermediate Mac tablet samples, and absence before 18.2 alone does not quantify loss without measuring dispatch behavior. ADR-0005 stays macOS 12.0/Safari 15.0 pending the user decision.

## Residual risks for C0.3/C0.4

- Do not choose the Windows fallback architecture or raise the Mac floor from these synthetic-zero/API-surface observations. Preserve the existing Tauri/Qt decision sequence and Electron exclusion.
- Fix clock-domain/frame association and retain raw evidence before combining input with C0.3 rendering/binary-channel throughput. Per-sample drawing, JSON/channel validation and a CPU-spinning injector can themselves affect the path being timed.
- Capture buffers silently stop storing after 200,000 samples; the Mac host queue also has a silent 100,000-packet cap, and failed channel sends are ignored. Short prescribed runs are below these limits, but future stress/no-drop work needs explicit overflow/delivery counters. No longer stress run is claimed here.
- Neither native nor web logs retain pointer/device IDs; cancel is recorded as up. This limits multi-device, cancellation and future MCP gesture-equivalence work (spec 11 §7.6); this spike is not the M4 input pipeline.
- Mac runtime testing remains pending the user, including after R1-08 is fixed. Zero native packets do not validate conversion, tool identity, coordinates or pressure.
- Carry the accepted C0.1 proxy/worker boundary tickets forward unchanged. The new channel did not bypass the three established boundary layers.

**Disposition:** fix the five P1 findings before accepting C0.2; P2s may be explicitly ticketed, but retain their failing regressions unless an authorized ruling changes the requirements. Real-tablet and Mac measurements remain pending and must be labeled as such in C0.4.
