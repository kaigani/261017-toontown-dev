## New findings

### C13-R2-01 — P1: Atomic close/quit with save loses staged work or writes a revision that never commits

Locations: `crates/executor/src/persistence.rs:299`, `crates/executor/src/cx.rs:542`, `crates/executor/src/run.rs:1013` and `:1046`. Spec: 11 §7.3 atomic batch/one transaction and §7.2 revision/change envelope; 10 SAVE-04; 01 §3.4–§3.6; standing commit-only persistence ruling.

Repro A: create a clean saved project; execute one atomic batch containing a scene metadata edit and `project.close {onUnsaved:"save"}` (or `app.quit`). The batch succeeds but reopening the file shows no edit. `resolve_unsaved` consults only the live project's dirty marker, ignoring the staged batch.

Repro B: first make the live project dirty, then batch another edit and close-save. The file contains revision 3, while the successful batch returns documentRev 2, no changes and no `doc.changed` commit event. `stamp_modified` seals the staged work into `cx.txns`; `batch_atomic` only commits its final `finish_staged` return and never consumes those sealed transactions. `finish_save` consequently runs against the older live document before Close. This is a commit/revision error, not merely missing notification text.

Permanent tests in R2E: `clean_project_atomic_close_saves_staged_edits`, `clean_project_atomic_quit_saves_staged_edits`, `successful_atomic_close_with_save_commits_and_emits_the_saved_revision` — **all fail**. Evidence: `variants.log` and `workspace-final.log`. Fix the staged dirty check and preserve the atomic batch's one committed revision before applying save/clean/close effects; keep the full integrity and frozen-entry gate.

### C13-R2-02 — P1: Save As drops media needed by undo when the blob container changes

Locations: `crates/executor/src/persistence.rs:196` and `:249`. Spec: 10 MED-04, SAVE-04; 07 §2.3 shared media; 11 P2/undo guarantees; ADR-0014 §8 and the round-1 closure requirement to retain live undo bytes.

Repro: open a package or folder with a referenced embedded sound and real bytes; force-remove the asset (one undoable edit), Save As to a different package, undo, then `doc.blob.get` the restored asset. Undo succeeds structurally, but the bytes fail with `project.mediaMissing`. Same-path saves pass in both base forms.

`write` only carries omitted base entries to cache when base and target paths are equal. `finish_save` always replaces the blob base with the new container, retaining only `extra` and `carried` entries. A different target omits the removed media and drops the only live reference to its old source. The old source file remains on disk but is no longer reachable by the restored asset through the session store.

Permanent tests in R2E: `save_as_package_retains_removed_asset_bytes_for_undo`, `save_as_folder_retains_removed_asset_bytes_for_undo` — **both fail**; same-path controls pass. Evidence: `variants.log`. Retain omitted base bytes or their live source handles across every base switch, including recovery-source changes, while keeping MED-04 serialization filtering.

### C13-R2-03 — P1: Import replace still appends conflicting assets

Location: `crates/executor/src/commands/bundle.rs:1014`. Spec: 10 §6.8 / §10.2 `doc.import.json` conflict policy; spec A `doc.import.json`; ADR-0014 §7; explicit round-2 asset-replacement charter.

Repro: import a valid embedded sound named `same.wav`, then import the same bundle with `onConflict:"replace"` (default `idPolicy:"new"`). Both calls succeed; `doc.asset.list` contains two same-named assets with distinct IDs and usable payloads. The asset loop unconditionally appends, unlike the new scene/element/palette conflict handling. Replacement must keep references coherent and undo must restore the prior subtree; the test stops at the first unmet requirement (one asset), so it does not claim the subsequent undo assertion executed.

Permanent test: R2E `asset_name_conflict_replace_keeps_one_asset_and_undo_restores_original` — **fails**. Evidence: `variants.log`. Cover name and preserved-ID conflict paths without silently substituting append/rename semantics.

### C13-R2-04 — P1: Folder external-change detection excludes preserved nested hidden entries

Location: `crates/executor/src/store.rs:282`. Spec: 10 RO-02, ZIP-04/FMT-01; 01 §3.6; ADR-0014 §2 defines control files by the **first** path segment.

Repro: close a folder project, add `vendor/.metadata`, reopen, externally change that file, make a local scene edit, and save. Save starts successfully instead of returning `project.changedOnDisk`. `FolderIndex` accepts this file as preserved project content, but `walk` skips any hidden basename at any depth. Maintenance uses that same incomplete fingerprint, so waiting for a watch tick does not resolve the gap. Root `.git`/lock/journal exclusion is appropriate; nested extension data needs to follow the actual container entry classification.

Permanent test: R2E `folder_hidden_preserved_entry_change_blocks_save` — **fails**. Visible rename/delete/add/touch/palette controls all pass. Evidence: `variants.log`.

### C13-R2-05 — P2 ticket: Entry portability accepts overlong individual components

Location: `crates/persist/src/zip.rs:97`. Spec: 10 FMT-01 equivalent forms; ADR-0014 §2 portable entry names. Owner: C1.3 container portability hardening.

`safe_name("vendor/" + "a"*256 + ".bin")` returns true because only total UTF-8 length and segment count are bounded. The 260-character component cannot be created as a plain Windows file; the independent filesystem probe fails with invalid argument. Such an accepted package entry cannot be represented in the promised folder form. This is a portability/Save As edge case, not a demonstrated path escape.

Permanent test: R2F `overlong_component_is_not_a_portable_folder_entry` — **fails**. Evidence: `format-final.log`, `portability.json`. Define component limits in platform units before accepting entries, or explicitly resolve the equivalent-form requirement. No GitHub issue was opened.

### C13-R2-06 — P2 ticket: Manifest rename occurs before removal renames

Locations: `crates/persist/src/journal.rs:240` (replace loop) and `:248` (remove loop); `crates/persist/src/save.rs:537`. Spec: 10 SAVE-02, ADR-0014 §2 (“manifest.json last”). Owner: C1.3 folder writer.

Repro: save a valid folder, add a reserved stray palette file that the next save removes, advance documentRev so the manifest changes, then interrupt the real writer after one rename. The new manifest is already installed while the obsolete entry still exists. Sorting manifest last within `replace` does not put it after `remove`; `apply` processes the whole replacement list before removals. Journal recovery still reaches a whole version, so this is P2 ordering conformance rather than a reproduced mixed-version/data-loss defect.

Permanent test: R2F `actual_folder_writer_keeps_manifest_after_removal_renames` — **fails**. Evidence: `format-final.log`. Move the manifest step behind both ordinary replacements and removals, and exercise that order using a changing manifest. No GitHub issue was opened.

## Residual risks / C1.4 handoff

- C1.3 builder owns all four P1 fixes and both P2 tickets above before a persistence pass. The permanent failures should be used unchanged except the already ruled journal fixture replacement.
- C1.4 owns SI-045 conversion of `project.changedOnDisk` into the confirmation protocol, attached/headless user control, and final native quit integration. Resolve C13-R2-01 in the kernel before wiring those flows.
- SI-044 still needs an explicit spec-owner ruling for the non-undoable repair base. Clean MAX and repaired MAX−1 are valid persisted states but further edits must fail under REV-03; no saturated repair was observed.
- PID reuse, clock jumps, and arbitration files left behind by a paused/crashed taker remain liveness risks. The new tests establish contention exclusivity at observed scheduling points and actual-child death expiry, not proof against every interleaving. No multi-machine/UNC share contention test was performed.
- Local execution is Windows only. The reviewed macOS CI proves inherited suites, not the new round-2 fixtures; filesystem Unicode normalization collisions, device spellings beyond the tested matrix, and platform durability still need macOS/real-filesystem coverage.
- Folder stat fingerprinting is O(files) per watch tick (default 2 s), and is not a content hash. Visible mutations are blocked synchronously at save; a content change that deliberately retains both size and mtime is outside the evidence here.
- Backup index commit errors remain non-fatal after a successful save; there is no disk-full/power-loss injection at every package/backup boundary. Hard-linked old copies protect rename crashes, not in-place external writes to both links.
- Autosave's existing between-transaction scheduling tests pass. This review did not establish a worst-case wall-clock latency bound for a long synchronous atomic batch, exhaustive frozen typed-array schema evolution, or a constant working set for valid 1 GiB JSON content.

No GitHub issues or PR were opened. P2 owners/tickets are recorded only in this report. Timings and hashes are finalized in `review-receipt.json`; finished deliverable is this report with its companion evidence folder.
