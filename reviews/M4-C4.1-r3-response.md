## 2. Rulings

- **O-19.** The checker's header and ADR-0021 (decision 10, *Message help coverage*) state the limit: a text scanner
  cannot see a code built at run time. The durable fix is recorded as a deferral with owner **M11 C11.1** in the M11
  row of `plan/IMPLEMENTATION_PLAN.md`: error codes constructed only from one catalogue type, with a Rust test that
  iterates the catalogue.
- **O-20.** K = 20 (`tt_mcp::server::SESSION_THREADS`): 5 for the session's life (the protocol loop `mcp-http-session`,
  `mcp-writer`, `mcp-reader`, `mcp-events`, `mcp-calls`); at most 4 `mcp-wait` (`job_wait`; a fifth answers
  `limit.exceeded`, `limit: "concurrentJobWaits"`); at most 2 `mcp-server-work` (a third answers `limit.exceeded`,
  `limit: "serverWork"`); at most 1 `mcp-roots` (requests during a refresh coalesce into it); at most 8 job threads (the
  session's `maxJobs`, domain 1..8, refused by the executor with `limit.exceeded`, `limit: "maxJobs"`). Calls create no
  thread (they run on `mcp-calls`). Formula `3 + C + K·S`: 707 with the defaults. Memory and sockets restated in the
  note §3 (memory: bounded by message counts times the inline payload limit, finite, not small; sockets `2 + C + L`).
  Measured at saturation (32 idle sessions, all workers busy, the pending pool full, 64 refusals held): exactly
  `3 + C + 5·S` above the baseline (171), within the formula's ceiling; the reviewer's test measures 219 against
  699. The declared edit to the reviewer's file is exactly the two literals (§8).
- **O-21.** As ruled; ADR-0022 decision 5 and the `--mcp-http` help (the argument's documentation in
  `desktop/src-tauri/src/diagnostics.rs` and `HostOptions`) say it. One more change was needed for the reviewer's
  probe to pass: a client polling the discovery file met a Windows sharing violation, or the host's rename failed
  while the client had the file open, so the new endpoint never landed. The host now rewrites an existing discovery
  file in place, as one write of a fixed size (the JSON padded with spaces to 4 KiB), so it is never absent,
  truncated or held by a rename; the first file is still created privately and renamed into place.

## 3. Observations

- **I-8 (lock order).** Construction is the test, and the note §7 now says why: there is exactly one nested
  acquisition (`sessions` then `routes`); every holder of `pending`, `routes` and `lingering` calls nothing that
  locks; the in-flight guard's `Drop` takes only `sessions`. A run cannot show the absence of a schedule. The note
  names the fourth lock (`lingering`), which the first version left out.
- **The closer mutex.** The accept thread can wait for the closer only for one pass of non-blocking reads over at
  most L sockets; the closer never writes and never blocks inside its pass, and refusals are written (non-blocking)
  before the hand-off, outside the lock. So it never waits behind a blocked write (note §7).
- **A request admitted before `DELETE`.** Intended, and stated in the note §6: its head was authenticated before the
  `DELETE`, it holds its own handle on the session's input and routes, it completes and its caller receives the full
  answer, then its stream ends; a request whose head arrives after the `DELETE` answers `404`; nothing brings the
  session back (reviewer `delete_during_body_does_not_resurrect_request_routes` passes).
- **Front-end tests added:** `a refused object preference keeps the window open with the refusal; only that one
  prefs.set is sent` and `a shortcut refused as ui.busy or ui.modalOpen is consumed silently: no command, no message
  box` (`desktop/src/App.test.tsx`).

## 4. C41-R3-03: state refusals and where availability evaluates them

**The rule now.** Availability evaluates (1) the pipeline's static checks: registered, not an event, a project when
the declaration needs one (`project.none`), the declared enablement rule (`edit.nothingToUndo`, `edit.nothingToRedo`,
the frame and element stepping rules), implemented; then (2), for a complete reference (no required parameter
missing), the handler itself, by running the reference through `run_step` as a dry run on a scratch copy of the
session (`host::refused_by_handler`). A refusal of either is the reason the menu, the toolbar, the key dispatch and the
MCP `key` tool report; there is no second predicate to drift. Two refusals mean "the GUI asks the user" rather than
"disabled" and keep the reference enabled: `project.pathRequired` (Save asks for a location) and
`project.unsavedChanges` (01 §3.5). References with required parameters missing are completed by a dialog; their
refusals depend on what the user enters and stay out of scope, as ruled.

**The inventory.** Every command reference the GUI offers: the native menu, the default keymap, and every implemented
command with a GUI location (11 §14.1: not agent-only), 269 references. The sweep met these state refusals with no
parameter missing; the full table (each reference, each refusal, each state) is
`reviews/evidence/M4-C4.1-r3-response/state-refusals.tsv`.
