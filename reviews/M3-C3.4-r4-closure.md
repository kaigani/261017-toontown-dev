## New findings

### C34-R4-01 - P2 - atomic batch wrapper loses the cancellation cause

Permanent reproduction: `crates/executor/tests/c34_r4_cancellation_shape.rs::atomic_work_account_cancellation_labels_the_nested_error_as_well_as_the_step` (0/1, exit 101).

An atomic batch starts `render.frame.run` under the work-account hook (20 ms per charge); its caller cancels after 60 ms. The document revision stays unchanged. The failed step's `command.timeout` correctly carries `details.reason: "cancelled"`. The outer `batch.stepFailed.details.error` is a separate copy of that same timeout, but its details contain only `budget` and omit the reason. Its retained hint instead attributes the refusal to the watchdog. Expected: the nested timeout preserves the same caller-cancellation cause, as SI-111 / ADR-0020 decision 8 require.

In `run.rs::batch_atomic`, the error is cloned for the step and serialized by `step_failed`. `lib.rs::label_cancellation` labels the step copy but does not visit the nested outer copy. Preserve the cause before cloning/wrapping, or label the known nested error shape too; do not label genuine watchdog expiry as cancellation. No partial document commit was observed. [Permanent failing receipt](evidence/M3-C3.4-r4/atomic-shape.log).

### C34-R4-02 - P2 - a late answer can bypass the unresponsive latch

Permanent reproduction: `crates/executor/tests/c34_r4_late_probe.rs::two_hundred_answers_after_the_bound_must_latch_after_one_question` (0/1, exit 101). The new single-action probe in `c34_r4_closure` also exposed this intermittently.

Run 200 sequential trials at normal load, without competing cargo commands or artificial CPU load. After a worker question exists, every probe callback holds for at least 260 ms, enforced with `Instant`, against the 250 ms question bound. All 292 recorded callbacks lasted 260.0125-268.3539 ms. Expected: the first unanswered question reaches its bound, proceeds as not cancelled, and latches the link so no more questions are asked for that request.

Observed: **79/200 trials (39.5%) asked again**. Histogram: one question 121 trials, two 71, three 3, four 5. The unrelated caller's p95 latency was 524.3802 ms and maximum 1053.183 ms. The request still commits whole; the defect is the extra questions/waits after the response is already late, not the few milliseconds of scheduler overhead by itself.

`caller::cancelled` relies on `recv_timeout(BOUND)` and trusts its `Ok(answer)` without an independent elapsed-deadline check around dispatch/reception. Under ordinary scheduling, a positively late response can be accepted and another question issued instead of latching. Enforce the question deadline when deciding whether an answer is timely, while retaining silence-as-not-cancelled, later token cancellation and the disconnected-link contract. [200-trial receipt](evidence/M3-C3.4-r4/late-probes.log), [metrics](evidence/M3-C3.4-r4/bound-latch-metrics.json).

This meets the charter's at-least-one-failure-in-200 normal-load criterion. The first unfiltered single 260 ms case asked twice and failed; its targeted repeat asked once and passed. The 200-trial reproduction establishes the failure frequency rather than treating either single result as decisive.

## Four additional response fixes

**(a) Deadline before reply: conforms.** The independent test passes: the caller held beyond its 200 ms watchdog answers `command.timeout` without a cancelled reason even though its change committed. Revision advances exactly once; retry under the same requestId returns the remembered successful envelope with undo information, is cached, executes nothing and leaves revision unchanged. Token counters settle to zero. This agrees with ADR-0015 History C23-R2-01/C23-R3-01: acceptance is withdrawn until commit; an already completed commit stands. ADR-0020 rule 3 plus its explicit held-caller paragraph clearly state this distinction.

**(b) Job acceptance: conforms.** Independent direct before/after-start cases and a sequential job-step case pass. Before handler: refusal, no job in the registry, no staging. After start: the cancelled wait identifies jobId; explicit job cancellation then reaches terminal state with staging removed. A batch cancellation between job start and acceptance leaves that identity intact and refuses its later query step. Request cancellation itself does not cancel the independently owned job. The existing builder job-start test also passes.

**(c) Standalone probed query: conforms in the required variants.** Independent tests pass for an initially cancelled fast query, a query held queued until its caller's cancellation token is positively marked, cancellation at a render work-account check, a watchdog-expired queued query, and a query step following a cancelled batch job step. The queued caller-cancelled query runs and caches its answer; the watchdog-expired query is dropped and its live retry is uncached. Notice-only links ask zero questions. The work-account refusal says cancelled. The batch's later query is refused. C34-R4-01 concerns a separate copy of the atomic batch error, not this standalone-query acceptance fix.

**(d) Passage touch: conforms under the closure's documented touch-band criterion.** The new Rust family and an independent 80-digit Decimal oracle pass, as does the exact-node case. The path is straight, so section 05's sampled arc length is exact. The first velocity segment is exactly `3*s*(1-s)`: local maximum 3/4 at frame 3/2. It falls to zero at frame 2, then rises linearly to one at frame 3. The exact first crossing is `1+(1-sqrt(1-4*arc/3))/2` at/below that maximum, and `2+arc` above it. The oracle uses exact binary input values, not product evaluations.

Here `arc = 0.75*(1+delta)`; the maximum/arc relation has the corresponding relative magnitude. Results are reported to three decimals:

| delta | Local maximum versus arc | Product | Adjudication |
|---|---|---|---|
| 0 | equal | 1.500 | Correct touch. |
| -1e-9 | above | 1.500 | Correct rounded first crossing; exact frame about 1.499984189. |
| -1e-12 | above | 1.500 | Correct rounded first crossing. |
| -1e-13 | above | 1.500 | Correct rounded first crossing. |
| -1e-15 | above | 1.500 | Correct rounded first crossing. |
| +1e-9 | below, outside touch band | 2.750 | Correct later crossing. |
| +1e-12 | below, inside documented band | 1.500 | Admitted approximate touch; exact mathematical crossing is 2.750. |
| +1e-13 | below, inside documented band | 1.500 | Same documented approximation. |
| +1e-15 | below, inside documented band | 1.500 | Same documented approximation. |

A node exactly at the arc reports frame 2.000. The builder's pinned 0.9-maximum counterexample reports frame 3.000 and passes. Section 05 section 10.5's existing 1e-4 tolerance is a **frame** tolerance; it alone would not justify the 1.25-frame difference for a below-arc maximum. The approximation above is admitted specifically by the closure's documented `PASSAGE_TOUCH * max(1,abs(arc))` band. No tested at/above-arc maximum is missed, and no tested below-arc maximum outside that band is reported as a touch. [Exact adjudication](evidence/M3-C3.4-r4/passage-adjudication.json), [product trace](evidence/M3-C3.4-r4/passage-oracle.log).
